# 루틴 작업 지시서 (병렬 워커 공용)

> 클라우드 루틴 워커 A~D 가 **이 파일을 읽고 그대로 수행**한다.
> 지시를 바꾸려면 이 파일만 고치면 된다 (루틴 4개를 각각 고칠 필요 없음).
>
> 루틴 자체를 걸고·끄고·**다른 계정으로 옮기는 방법**은 `docs/ROUTINE-OPS.md` 를 본다.
> (이 파일 = 워커가 무엇을 하는지 / 저 파일 = 루틴을 누가 어떻게 굴리는지)

---

너는 kuzuni/kkkkkk 저장소의 모바일 방치형 게임(index.html) UI를 레퍼런스 스크린샷과 동일하게 만드는 작업을 이어서 진행한다. 이전 세션의 대화 기억은 없다고 가정하고, 모든 상태는 저장소 파일에서 읽어라.

[중요] 이 작업은 **여러 세션이 동시에 병렬로** 돈다. 다른 세션이 돌고 있어도 정상이며, 너는 겹치지 않는 작업 단위를 하나 잡아서 그것만 한다.

[-2] git 준비 (맨 처음)
이 환경은 detached HEAD 로 체크아웃되므로 그냥 `git pull --rebase` 하면 실패한다. 반드시 아래로 시작한다:
  git checkout main 2>/dev/null || git checkout -B main origin/main
  git branch --set-upstream-to=origin/main main 2>/dev/null
  git pull --rebase origin main
이후 모든 push 는 `git push origin main`. push 전에는 항상 `git pull --rebase origin main` 을 먼저 한다.
세션 식별자를 하나 만들어 둔다: SID=sess-$(date -u +%H%M)-$RANDOM

[-1] 작업 단위 선점 (전역 락 없음 — 작업 단위로만 잠근다)
1. docs/PROGRESS.md 의 «병렬 세션 규칙» 과 «작업 단위» 표를 읽는다.
2. 순서(A1 → A2 → A3 → A4 → A5 → 01 → 02 → … 표의 마지막 번호까지)대로 훑으며 **아직 완료되지 않았고 docs/claims/<ID>.lock 도 없는** 첫 작업을 고른다.
   - lock 파일이 있어도 안의 UTC 시각이 **90분 넘게 지났으면 죽은 것으로 보고 뺏는다**(덮어쓴다).
   - **뺏은 작업은 «처음부터» 가 아니라 «이어서» 한다.** 앞 세션은 한도 소진·중단으로 죽은 것이고,
     거기까지의 결과물은 이미 커밋돼 있다. 뺏었으면 **반드시 먼저 읽는다**:
     `docs/review/<ID>-*.md`(몇 회차까지 돌았고 무엇이 지적됐는지) ·
     `docs/measure/<ID>-*.md`(측정 끝났으면 **재측정 금지**) · `git log --oneline -20 | grep '(<ID>)'`.
     3회차까지 간 작업을 1회차부터 다시 돌리면 남은 회차 예산을 통째로 날린다.
     비평 회차는 **이어서 센다**(3회차까지 돌았으면 다음은 4회차).
3. `echo "$(date -u +%Y-%m-%dT%H:%M:%SZ) $SID" > docs/claims/<ID>.lock` 후 커밋 + push.
4. push 가 거부되면 `git pull --rebase origin main` 후 다시 확인한다.
   - rebase 가 `docs/claims/<ID>.lock` 에서 충돌하면 **선점 경쟁에서 진 것이다**(다른 워커가 먼저 push 했다).
     `git rebase --abort` 후 `git reset --hard origin/main` 으로 내 클레임을 버린다 — 선점 단계에서는
     로컬 커밋이 클레임 하나뿐이라 안전하다. **충돌을 내 쪽 lock 으로 풀어서 남의 클레임을 덮지 마라.**
   - rebase 가 깨끗이 끝났어도 `<ID>.lock` 내용이 내 SID 가 아니면 남이 잡은 것이다.
   - 어느 쪽이든 **그 작업은 포기하고 다음 미선점 작업**으로 간다. (90분 지난 lock 을 뺏을 때도 같은 규칙 —
     뺏기 push 가 충돌하면 남이 먼저 뺏은 것이니 포기한다.)
   - 잡을 게 하나도 없으면 '선점 가능한 작업 없음'이라고만 보고하고 즉시 종료한다.
5. 작업을 마치거나 중단할 때는 성공·실패 무관하게 lock 을 **삭제**하고 커밋 + push 한다. 빼먹으면 90분간 그 작업이 막힌다.

[0] 시작 절차
1. docs/PROGRESS.md (단일 진실 공급원) 와 docs/UI-REFERENCE.md (화면 23종 스펙 + 24번 구현 체크리스트) 를 읽는다.
2. git log --oneline -10 / git status 로 직전 상태를 확인한다.

[1] 이번 실행의 목표
- **잡은 작업 단위 딱 1개만 끝낸다.** 다른 작업까지 손대지 마라 — 병렬 세션과 충돌한다.
- **레이아웃을 실제로 바꾸는 것이 목적이다.** 스케일 변환·상수 정리 같은 기계적 작업으로 회차를 통째로 쓰지 마라.
- 60분 안에 끝내는 것을 목표로 한다.
- 끝나면 PROGRESS.md 해당 행 + UI-REFERENCE.md 체크리스트 + docs/review/<ID>-이름.md 를 갱신하고 lock 삭제 후 커밋 · push.

[2] 작업 규칙 (상세는 문서 0·24·25번)
- **기준 해상도는 1080x1920 (9:16) 이다.** (2026-08-24 변경. 이전 기준 9:19.5 는 폐기)
- 레퍼런스 스크린샷(docs/ref/*.jpg)은 1080x2340 캡처지만 **폭이 1080 으로 같으므로 가로 수치(x·width·font-size·gap·radius)는 변환 없이 1:1** 로 쓴다.
  세로도 고정 요소(상단 HUD·튜토리얼 배너·패널·탭바)는 측정값 그대로 쓰고, 차이 420px 은 **전투 캔버스가 흡수**한다.
  **절대 전체를 1920/2340 비율로 축소하지 마라.** 눈대중도 금지.
- **기존 UI를 래퍼로 감싸 scale() 로 확대·축소하는 꾸수는 금지한다.** 각 요소의 CSS 값을 레퍼런스 측정치대로 직접 다시 적는다.
- 폭 1080 고정 · 세로 가변(#app 높이 = 1080 x 안전영역높이/폭, clamp 1600~2600). 남는 높이는 전투 캔버스가 흡수.
- 안전영역은 프레임 바깥에서 흡수(#wrap 에 env(safe-area-inset-*), fit()은 wrap.clientWidth/clientHeight 기준).
- 구현 전에 측정한다: docs/measure/NN-이름.md 에 요소별 x/y/width/height/gap/font-size/border/radius 를 절대 px로 기록. 이미 있으면 재측정 금지.

[3] 검증 — 작업 종류에 따라 다르게 한다 (중요)

(가) **기계적 작업**(단위 변환, 상수 일괄 치환, 리네이밍, 값 스케일링 등 레퍼런스 대조가 필요 없는 작업)
  → **비평가를 절대 띄우지 마라.** grep 으로 미변환분이 남았는지 세고, 헤드리스로 한 번 띄워 콘솔 에러 0건과 요소 겹침·잘림 0건만 확인하면 통과다.
  → 이런 작업에 비평 루프를 돌리면 회차 예산을 다 태우고 정작 레이아웃을 못 바꾼다. 실제로 이전 회차가 그렇게 날아갔다.

(나) **레이아웃 재구성**(레퍼런스와 배치·비율을 맞춰야 하는 작업) → 아래 루프를 최대 5회 돈다.
  1. 헤드리스 브라우저로 그 화면을 **1080x1920** 으로 캡처한다(playwright). 상태가 필요하면 임시 주입 스크립트로 상태를 만든 뒤 캡처.
  2. Task 도구로 서로 독립적인 비평가 2명을 띄운다. 각자에게 레퍼런스(docs/ref/NN-*.jpg)와 캡처본을 둘 다 Read 시키고 채점하게 한다.
     비평가에게 **레퍼런스는 1080x2340, 캡처는 1080x1920 이며 가로 수치는 1:1 로 비교하고 세로는 고정 요소만 비교하되 전투 캔버스 높이 차이는 감점하지 말 것**이라고 반드시 알려준다.
     항목은 ①요소 배치 ②상대 크기 비율 ③여백·간격 ④정렬·그리드 ⑤색·명암 ⑥폰트 크기 비율. 각 10점이며 최저 항목 점수를 그 비평가의 점수로 삼는다.
     지적은 '몇 px 어긋남 / 몇 % 큼'처럼 수치로만. 두루뭉술한 총평 금지. 후하게 주지 말라고 명시한다.
  3. 2명 중 최저 점수가 9 미만이면 수정 후 1번부터 반복.
  4. 최저 9 이상이면 통과 → 문서 갱신 + 커밋.
  5회 안에 9가 안 나오면 남은 문제를 PROGRESS.md 비고에 적고 lock 을 풀고 종료한다.

[4] 병렬 충돌 처리
- push 전 항상 `git pull --rebase origin main`.
- `index.html` 이 충돌하면 **양쪽 변경을 모두 살린다**(서로 다른 구간이라 대부분 자동 병합된다). 내 작업 구간이 아닌 곳은 남의 버전을 그대로 둔다.
- 병합 후 반드시 문법 검사 + 헤드리스 실행으로 에러 0건 확인. 깨졌으면 고쳐서 push 한다.
- `PROGRESS.md` 가 충돌하면 **양쪽 행을 모두 살린다.**
- `docs/claims/*.lock` 이 충돌하면: **내 <ID>.lock 이 아닌 lock 파일은 절대 건드리지 않는다** — 남의 lock 은
  남의 버전 그대로 살린다(생성이든 삭제든). 내 <ID>.lock 자체의 충돌은 [-1] 4 규칙(경쟁 패배 = 포기)을 따른다.
- 비평 기록은 `docs/review/<ID>-이름.md` 에 자기 파일로만 쓴다. 공용 `docs/review-log.md` 에는 추가하지 마라.

[5] 컨텍스트 관리 (매우 중요)
- 이미지는 절대 메인 세션에서 직접 Read 하지 마라. 측정·채점은 Task 서브에이전트에게만 시키고 텍스트 결과만 받는다.
- 서브에이전트를 띄웠으면 **결과를 기다렸다가 받아서 진행한다.** 기다리는 동안 세션을 끝내지 말 것.
- index.html 전체를 반복해서 읽지 말고 grep 으로 필요한 구간만 찾아 부분 편집한다.
- 컨텍스트가 70%를 넘으면 하던 작업을 마무리 짓고 PROGRESS.md 갱신 → lock 삭제 → 커밋 → 종료한다.

[6] 지켜야 할 것
- 매 편집 후 문법 검사 + 실제 브라우저 실행으로 런타임 에러가 없는지 확인한다.
- 저장 구조를 바꾸면 세이브 마이그레이션 또는 KEY 버전을 올린다.
- main 에 push 하면 GitHub Pages(https://kuzuni.github.io/kkkkkk/)로 자동 배포된다. 깨진 상태를 push 하지 마라.
- 모든 작업 단위가 완료되어 있으면 '완료됨'이라고만 보고하고 종료한다.
- 마지막에 3줄 이내로 요약한다. **어떤 <ID> 를 잡아 무엇을 바꿨는지**를 반드시 포함한다.
