# 루틴 운영 · 계정 교체 매뉴얼

> `docs/ROUTINE.md` 는 **워커가 무엇을 하는지**(작업 지시서)이고,
> 이 파일은 **루틴을 누가·어떻게 굴리는지**(운영 지시서)다. 계정을 갈아끼울 때 이 파일만 보면 된다.

---

## 1. 루틴 구조

이 프로젝트는 Claude Code 클라우드 루틴 **4개**를 15분 간격으로 엇갈리게 돌려 병렬 작업한다.

| 워커 | cron (UTC) | 역할 |
|---|---|---|
| A | `5 * * * *` | 매시 :05 |
| B | `20 * * * *` | 매시 :20 |
| C | `35 * * * *` | 매시 :35 |
| D | `50 * * * *` | 매시 :50 |

- 4개 모두 **완전히 같은 프롬프트**를 쓴다(워커 이름만 다름). 프롬프트는 §5 참고.
- 프롬프트는 짧게 유지한다 — 실제 지시는 전부 `docs/ROUTINE.md` 에 있고, 워커는 그걸 읽어서 수행한다.
  **작업 내용을 바꾸고 싶으면 루틴 4개가 아니라 `docs/ROUTINE.md` 만 고친다.**
- 한 세션 = 작업 단위(`docs/claims/<ID>.lock`) **1개**. 최대 60분 목표.
- 세션이 겹치는 건 정상이다. 충돌은 `docs/claims/*.lock` 선점으로 막는다(90분 지난 lock 은 뺏김).

### 루틴 설정값 (그대로 복사할 것)

| 항목 | 값 |
|---|---|
| 저장소 | `https://github.com/kuzuni/kkkkkk` |
| 브랜치 | `main` (워커는 main 에 직접 push, GitHub Pages 자동 배포) |
| allowed_tools | `Bash`, `Read`, `Write`, `Edit`, `Glob`, `Grep`, `Task`, `WebFetch` |
| 모델 | 계정마다 다름 — §3 참고 |
| environment_id | **계정마다 다르다.** 새 계정에서 `list_environments` 로 직접 조회해서 쓸 것 |

`Task` 는 반드시 넣어야 한다. 비평가·측정을 서브에이전트에게 시키는 구조라 없으면 지시서대로 못 돈다.

## 2. 계정 교체 절차 (한도 소진 → 다른 계정으로 넘김)

**핵심 원칙: 두 계정의 루틴이 동시에 켜져 있으면 안 된다.** 8개 워커가 `index.html` 한 파일에 붙어
rebase 충돌만 반복하고, 한도 나간 계정 쪽은 작업 중간에 죽어 lock 만 남긴다.

### 단계

**① (구 계정) 루틴 4개를 끈다**
```
루틴 A/B/C/D → 일시중지
```
- ⚠️ **웹 UI(claude.ai)에서 만든 루틴은 세션 안의 에이전트가 못 끈다.** 사람이 루틴 목록에서
  직접 꺼야 한다. 에이전트에게 "루틴 꺼 줘" 하면 `created_via: http_api ... Agents can only
  update routines they created` 로 거부된다. **끄는 건 사람 몫이라고 생각할 것.**
  (반대로 에이전트가 `create_trigger` 로 만든 루틴은 그 에이전트가 끌 수 있다.)
- ⚠️⚠️ **루틴을 끄면 그 루틴이 띄워 놓은 진행 중 세션도 같이 종료된다.**
  (2026-08-24 실측. "다음 실행만 막고 돌던 세션은 살아남는다" 고 생각했는데 **아니었다.**)
  따라서 끄는 순간:
  - 마지막 커밋 이후의 작업분은 **날아간다**(비평 루프 돌던 중이면 그 회차 통째로)
  - 세션이 lock 을 못 지우고 죽으므로 **죽은 lock 이 반드시 남는다** → ② 청소가 **필수**다
- 대신 좋은 점도 있다 — **빠져나갈 세션을 기다릴 필요가 없다.** 끈 직후 상황이 곧 최종 상황이라
  새 계정을 **바로** 붙여도 두 계정 워커가 겹치지 않는다.
- 아까운 작업을 살리고 싶으면 끄기 전에 `git log --oneline -5` 로 방금 커밋이 올라온 직후인지
  보고 끈다. 다만 어차피 한 세션 = 한 작업 단위라 손실 상한은 작업 1개다. 크게 아끼지 말 것.
- 삭제하지 말고 **일시중지만** 한다. 나중에 그 계정 한도가 돌아오면 다시 켜서 되돌릴 수 있다.

**② 죽은 lock 을 청소한다 — 필수, 끈 직후**
①에서 죽은 세션들이 lock 을 그대로 두고 사라진다. 안 치우면 그 작업들이 90분간 잠긴다.
```bash
git pull --rebase origin main
# 남아 있는 lock 전부가 죽은 lock 이다(루틴을 껐으므로 살아 있는 세션이 없다)
git rm -q docs/claims/*.lock
git commit -m "chore: 계정 교체 — 죽은 클레임 lock 청소" && git push origin main
```
- 구 계정 루틴을 **전부** 껐다면 위처럼 통째로 지우면 된다. 일부만 껐다면 살아 있는 세션의 lock 을
  지우지 않도록 **60분 넘은 것만** 골라 지운다:
  ```bash
  for f in docs/claims/*.lock; do
    t=$(cut -d' ' -f1 "$f")
    age=$(( ( $(date -u +%s) - $(date -u -d "$t" +%s) ) / 60 ))
    [ "$age" -gt 60 ] && { echo "stale($age분) $f"; git rm -q "$f"; }
  done
  ```
- 청소를 건너뛰어도 **치명적이진 않다.** 90분 지나면 자동으로 뺏기고(지시서 `[-1] 2`),
  그 사이 새 워커는 lock 없는 뒷번호 작업을 집는다. 청소는 **90분을 안 기다리려고** 하는 것이다.
- 지운 작업의 진행 상황은 `docs/PROGRESS.md` 와 `docs/review/<ID>-*.md` 에 남아 있으므로
  다음 세션이 그걸 읽고 이어서 한다. 커밋된 코드는 그대로 살아 있다.

**③ (새 계정) 사전 준비를 확인한다**
§4 체크리스트를 훑는다. 특히 push 권한과 `environment_id` 는 루틴 만들기 전에 반드시 확인.

**④ (새 계정) 루틴 4개를 만든다**
§5 의 프롬프트를 그대로 쓰고, cron 만 `5/20/35/50 * * * *` 으로 4개 만든다.
`environment_id` 는 그 계정에서 `list_environments` 로 조회한 값을 쓴다.

**⑤ 첫 사이클 확인 — 15~20분 뒤**
```bash
git log --oneline -10          # 새 계정 세션의 커밋이 올라오는가
ls docs/claims/                # lock 이 새로 잡히는가
```
- 30분이 지나도 커밋이 0건이면 §6 을 본다.

### 되돌리기 (구 계정 한도가 돌아왔을 때)
같은 절차를 반대로 한다 — 새 계정 4개 끄기 → lock 청소 → 구 계정 4개 다시 켜기.
**절대 양쪽을 동시에 켜 두지 말 것.**

## 3. 계정별 모델

| 계정 | 모델 ID | 비고 |
|---|---|---|
| 계정 1 | `claude-opus-5` | 초기 A~D 구성 |
| 계정 2 | `claude-fable-5` | Fable |

모델을 바꿔도 **`docs/ROUTINE.md` 지시서는 그대로 쓴다.** 지시서는 모델 중립적으로 쓰여 있다.

### Fable 로 돌릴 때 특히 지킬 것

지시서에 이미 있지만 모델이 바뀌면 제일 먼저 깨지는 항목들이라 다시 못박는다.

1. **이미지는 메인 세션에서 절대 Read 하지 않는다.** 레퍼런스 대조·채점·측정은 전부 `Task`
   서브에이전트에게 시키고 **텍스트 결과만** 받는다. 이걸 어기면 컨텍스트가 한 회차 만에 날아간다.
2. **한 세션 = 작업 단위 1개.** 남는 것 같아도 다음 작업을 집지 않는다. 병렬 세션과 충돌한다.
3. **기계적 작업에는 비평 루프를 돌리지 않는다**(지시서 [3]-(가)). 회차 예산을 다 태운다.
4. **`index.html` 전체를 읽지 않는다.** `grep` 으로 구간만 찾아 부분 편집한다(파일이 350KB 넘는다).
5. 컨텍스트 70% 넘으면 마무리 → PROGRESS 갱신 → lock 삭제 → 커밋 → 종료.

## 4. 새 계정 사전 준비 체크리스트

루틴을 만들기 **전에** 새 계정에서 아래가 다 되는지 확인한다. 하나라도 빠지면 루틴이 매시간 조용히 실패한다.

- [ ] GitHub 연동이 되어 있고 `kuzuni/kkkkkk` 에 **push 권한**이 있다
      (안 되면 claude.ai → 설정 → 커넥터에서 GitHub 재연결, 조직이면 저장소 접근 허용 필요)
- [ ] `list_environments` 로 environment_id 를 확보했다
- [ ] 그 환경의 네트워크 정책이 **playwright / chromium 실행**을 막지 않는다 (헤드리스 캡처가 필수다)
- [ ] 세션에서 `git push origin main` 이 실제로 되는지 **수동으로 1회** 확인했다
- [ ] 모델을 `claude-fable-5` 로 지정했다
- [ ] allowed_tools 에 `Task` 가 들어 있다

## 5. 루틴 프롬프트 (4개 공통 · 그대로 복사)

`{{워커}}` 자리에 `A` / `B` / `C` / `D` 만 바꿔 넣는다.

```
너는 kuzuni/kkkkkk 저장소 UI 작업의 **병렬 워커 {{워커}}** 다. 여러 워커가 동시에 돌아간다.

먼저 저장소를 준비한다 (이 환경은 detached HEAD 로 체크아웃된다):
  git checkout main 2>/dev/null || git checkout -B main origin/main
  git branch --set-upstream-to=origin/main main 2>/dev/null
  git pull --rebase origin main

그 다음 **`docs/ROUTINE.md` 를 읽고 거기 적힌 지시를 처음부터 끝까지 그대로 수행한다.**
그 파일이 이 작업의 유일한 지시서다. 여기 적힌 것과 다르게 행동하지 마라.
지시서가 사라졌거나 읽을 수 없으면 아무것도 수정하지 말고 '지시서 없음'으로 보고하고 종료한다.
```

루틴 이름은 `방치형 UI 병렬 워커 {{워커}} (:05)` 처럼 **실행 분(分)을 이름에 박아 둔다.**
나중에 목록만 보고도 cron 을 알 수 있어야 교체가 쉽다.

## 6. 문제 대응

| 증상 | 원인 | 조치 |
|---|---|---|
| 매시간 도는데 커밋이 0건 | 한도 소진, 또는 push 권한 없음 | 세션 로그 확인 → 한도면 계정 교체(§2), 권한이면 §4 |
| 특정 작업이 계속 안 잡힘 | 죽은 lock 이 남음 | §2-② 청소 스크립트 실행 |
| 같은 화면을 두 세션이 동시에 만짐 | 양 계정 루틴이 동시에 켜져 있음 | 한쪽을 즉시 끈다. 이게 제일 흔한 사고다 |
| `index.html` 충돌 반복 | 워커가 자기 구간 밖을 건드림 | 지시서 [4] 대로 **양쪽 변경을 모두 살린다**. 남의 구간은 남의 버전 유지 |
| 배포 페이지가 깨짐 | 깨진 상태로 push 됨 | 해당 커밋 revert 후 push. 워커는 push 전 헤드리스 실행으로 에러 0건 확인 의무 |
| 세션이 여러 작업을 한 번에 함 | 지시서를 안 읽음 | 프롬프트가 §5 원문 그대로인지 확인(작업 내용을 프롬프트에 직접 쓰면 이렇게 된다) |
| 에이전트가 루틴을 못 끈다 | 웹 UI 로 만든 루틴(`created_via: http_api`) | 정상 동작이다. 사람이 루틴 목록에서 직접 끈다(§2-①) |
