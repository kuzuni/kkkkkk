## 1. 루틴 구조

이 프로젝트는 Claude Code 클라우드 루틴을 분(分) 단위로 엇갈리게 돌려 병렬 작업한다.

### ★ 현재 가동 세트 (2026-08-30~) — 워커 8 + 감시견 1

`create_new_session_on_fire: true` · **`created_via: meta_mcp`**(= 에이전트가 만든 것이라

클론·커넥터 없이 `https://github.com/kuzuni/kkkkkk/commits/main.atom` 만으로 판정한다.
**이것이 «8시간 공백» 재발 방지의 본체다** — §2-⓪ 참고.

계정 5 분은 계정 3 의 wwwww 루틴 분(:07/:14/:22/:29/:34/:37/:44/:51/:59)과도 안 겹치게 골랐다.
⚠️ **`0 * * * *`(정각)은 못 쓴다** — 서버가 부하 분산으로 임의 분(관측: :16)에 재배치한다. update 로 다시 넣어도 같은 분으로 강제된다.

- **계정마다 분(分)을 엇갈려 둔다.** 같은 분을 쓰면 양 계정을 동시에 켰을 때 워커가 쌍으로
  동시에 떠서 매 사이클 같은 작업을 두고 락 선점 경쟁부터 한다. 락(`docs/claims/*.lock`)은
  계정을 가리지 않으므로 **양 계정 동시 가동 자체는 가능**하다 — 단, 죽은 계정(한도 소진)의
  루틴은 lock 만 남기고 죽으므로 반드시 꺼야 하고, 동시 가동 시 `index.html` rebase 충돌은
  늘어난다(지시서 [4] 로 해소).

- 4개 모두 **완전히 같은 프롬프트**를 쓴다(워커 이름만 다름). 프롬프트는 §5 참고.
- 프롬프트는 짧게 유지한다 — 실제 지시는 전부 `docs/ROUTINE.md` 에 있고, 워커는 그걸 읽어서 수행한다.
  **작업 내용을 바꾸고 싶으면 루틴 4개가 아니라 `docs/ROUTINE.md` 만 고친다.**
- 한 세션 = 작업 단위(`docs/claims/<ID>.lock`) **1개**. 최대 60분 목표.
- 세션이 겹치는 건 정상이다. 충돌은 `docs/claims/*.lock` 선점으로 막는다(90분 지난 lock 은 뺏김 — 회차마다 heartbeat 갱신. 2026-08-26 50→90 복귀).

## 1-b. ⚠ 워커를 «잠깐» 세울 때 — 재가동 누락 방지 (2026-08-29 사고)

**실제로 있었던 일**: 2026-08-29 **19:44Z**, 저장소 이력 재작성(`git filter-repo` 로 캡처 PNG 제거,
pack 3.36 GiB → 354 MiB)을 하려고 워커 4개를 손으로 일시중지했다. 이력 정리는 21:02Z 에 끝났는데
**루틴을 다시 켜지 않았다.** 다음 날 03:49Z 에 발견될 때까지 **8시간 5분 동안 사이클 0회**였다.

원인 판별은 쉬웠다 — `list_triggers` 에서 네 개의 `updated_at` 이 **19:44:18 / :20 / :37 / :52** 로
34초 안에 순차로 찍혀 있었고(사람이 하나씩 클릭한 모양), `ended_reason`·`suspension_reason` 이
둘 다 비어 있었다(= API 상 «user-paused»). 마지막 실행 4회는 전부 `SUCCEEDED` 였다.
**즉 실패도 한도 소진도 아니고, 끄고 안 켠 것이다.**

### 규칙

1. **끄기 전에 «켤 시각» 을 먼저 정한다.** 이력 재작성·대규모 revert 처럼 워커를 세워야 하는
   작업은 대부분 1~2시간이다. 세우는 순간 그 자리에서 재가동 알람을 걸어라
   (휴대폰 타이머든 `send_later` 든 무엇이든).
2. **끄더라도 감시견(`:10`)은 끄지 마라.** 감시견이 100분 뒤에 푸시·이메일로 깨워 준다 —
   이것이 이 사고의 실질적 안전망이다. 계획된 정지라면 알림 한 번 받고 무시하면 되고,
   잊었다면 그 알림이 유일한 구조 신호다.
3. **작업이 끝나면 «켰는지» 를 눈으로 확인한다.** `list_triggers(enabled: true)` 가
   **9개**(워커 8 + 감시견)를 돌려주는지 본다. 빈 배열이면 전부 꺼진 것이다.
4. 워커가 도는 중에 이력을 재작성하지 않는 것이 원칙이지만, **어차피 push 는 먼저 성공한 쪽이
   이기고 진 쪽은 포기하게 돼 있다**(지시서 [-1] 4). 정지 없이 강행하는 선택지도 있다 —
   8시간 공백보다 rebase 충돌 몇 건이 싸다.

## 2. 계정 교체 절차 (한도 소진 → 다른 계정으로 넘김)

**핵심 원칙: 한도가 소진된 계정의 루틴이 켜져 있으면 안 된다.** 그쪽 세션은 작업 중간에 죽어
lock 만 남긴다. 반대로 **양쪽 다 한도가 살아 있으면 동시 가동해도 된다**(2026-08-24 부터) —
락은 계정을 가리지 않고, cron 도 §1 처럼 계정별로 엇갈려 있고, 선점 경쟁은 지시서 [-1] 4 가
처리한다. 감수할 것은 `index.html` rebase 충돌 증가뿐이다(지시서 [4] 로 해소).

### 단계

**① (구 계정) 루틴 4개를 끈다**
```
루틴 A/B/C/D → 일시중지
```
- ⚠️ **웹 UI(claude.ai)에서 만든 루틴(`created_via: http_api`)은 세션 안의 에이전트가
  «끄지도 켜지도 지우지도 즉시실행하지도» 못한다.** 2026-08-30 에 넷 다 시도해 전부 같은
  메시지로 거부됐다 — `update_trigger` · `fire_trigger` · `delete_trigger` 공통으로
  `this routine was created via "http_api", not by an agent. Agents can only ... routines they
  created (via create_trigger)`. 에이전트가 할 수 있는 것은 **읽기와 «자기 자신 끄기»(enabled=false)뿐**이다.
  **사람 몫이라고 생각할 것.**
  (반대로 에이전트가 `create_trigger` 로 만든 루틴 — 현재 가동 세트 8개 + 감시견 — 은
  그 에이전트가 켜고 끄고 지울 수 있다. §5-2-b.)
- ⚠️⚠️ **끄면 진행 중 세션이 어떻게 되는지는 일정하지 않다. 로그로 확인해야 한다.**
  2026-08-24 교체 때 관측된 것:
  - 루틴 목록에서 4개를 끄자 **돌고 있던 세션 상당수가 그 자리에서 종료**됐다(사용자 관측).
    종료된 세션은 lock 을 못 지우고 사라졌고, 마지막 커밋 이후 작업분은 날아갔다.
  - 그런데 **전부 죽지는 않았다.** 끄고 2~3분 뒤에도 커밋을 이어간 세션이 있었다
    (`06:14:30 fix(12) …`, 루틴 비활성화 시각 이후).
  → 그러므로 **"껐으니 다 죽었다" 고 가정하고 lock 을 통째로 지우면 안 된다.**
    살아 있는 세션의 lock 을 지우면 그 작업을 두 워커가 동시에 만진다. ② 의 판별 절차를 따를 것.
- 좋은 점 — 새 세션은 더 이상 안 뜨므로 **"빠져나갈 세션 기다리기" 는 대체로 불필요하다.**
  살아남은 세션도 자기 작업 1개를 끝내면 lock 을 풀고 끝난다(최대 60분).
- 아까운 작업을 살리고 싶으면 끄기 전에 `git log --oneline -5` 로 방금 커밋이 올라온 직후인지
  보고 끈다. 다만 한 세션 = 한 작업 단위라 손실 상한은 작업 1개다. 크게 아끼지 말 것.
- 삭제하지 말고 **일시중지만** 한다. 나중에 그 계정 한도가 돌아오면 다시 켜서 되돌릴 수 있다.

**② 남은 lock 을 판별한다 — 지우기 전에 반드시**

**먼저 알아 둘 것: 이 단계는 급하지 않다.** 안 치워도 새 계정은 안 막힌다 —
lock 없는 뒷번호 작업이 남아 있으면 새 워커는 그걸 집고, 죽은 lock 은 90분 뒤 자동으로
뺏긴다(지시서 `[-1] 2`, heartbeat 기준). 청소는 **90분을 안 기다리려고** 하는 것뿐이다.
**살아 있는 lock 을 잘못 지우는 손해가, 90분 기다리는 손해보다 훨씬 크다.**

lock 파일 안의 시각은 **갱신을 안 해도 작업은 계속되므로 생사 판별에 못 쓴다.**
(12번은 lock 이 `05:56` 인 채로 `06:14` 에 커밋했다.) **커밋 로그로 판별한다:**
```bash
git pull --rebase origin main
git log --since='20 minutes ago' --format='%cd  %s' --date=format-local:'%H:%M:%S'
```
- 최근 20분 안에 `(NN)` 커밋이 있으면 **NN 은 살아 있다 — 건드리지 마라.**
- 아무 흔적 없는 lock 만 죽은 것으로 본다. 애매하면 **지우지 말고 90분 규칙에 맡긴다.**

죽었다고 확정된 것만 골라 지운다:
```bash
git rm -q docs/claims/13.lock docs/claims/15.lock   # 예시 — 확인된 것만 나열
git commit -m "chore: 계정 교체 — 죽은 클레임 lock 청소" && git push origin main
```
- 지운 작업의 진행 상황은 `docs/PROGRESS.md` 와 `docs/review/<ID>-*.md` 에 남아 있으므로
  다음 세션이 그걸 읽고 이어서 한다. 커밋된 코드는 그대로 살아 있다.
  (지시서 `[-1] 2` 에 «뺏은 작업은 기록부터 읽고 이어서 한다» 를 못박아 뒀다.)

### 한도 소진으로 세션이 죽으면 — 계정 2에 문제가 되는가

**안 된다. 이 구조가 애초에 그걸 전제로 만들어졌다.**

| 죽으면서 생기는 것 | 새 계정에 미치는 영향 |
|---|---|
| lock 이 안 지워짐 | 90분 뒤 자동 회수. 그동안 새 워커는 lock 없는 뒷번호를 집으므로 **놀지 않는다** |
| 깨진 코드가 main 에 | **생기지 않는다.** 죽은 세션은 push 를 못 한다. main 에 있는 건 살아서 올린 것뿐이며 최악이라도 «1회차 품질에서 멈춘 화면» 이지 문법 오류가 아니다 |
| PROGRESS.md 가 미완료로 남음 | 정상 동작이다. 다음 워커가 미완료로 보고 다시 잡는다 |
| 계정 1 한도 소진 | 계정 2 한도와 **별개**다. 영향 없다 |

유일한 실질 위험은 **뺏은 워커가 처음부터 다시 하는 것**이며, 위 지시서 보강으로 막았다.

**③ (새 계정) 사전 준비를 확인한다**
§4 체크리스트를 훑는다. 특히 push 권한과 `environment_id` 는 루틴 만들기 전에 반드시 확인.

**④ (새 계정) 루틴 4개를 만든다**
§5 를 그대로 따른다. 프롬프트는 §5-1, 빠뜨리면 안 되는 파라미터는 §5-3 에 있다.
`environment_id` 는 그 계정에서 `list_environments` 로 조회한 값을 쓴다.

**⑤ 첫 사이클 확인 — 15~20분 뒤**
```bash
git log --oneline -10          # 새 계정 세션의 커밋이 올라오는가
ls docs/claims/                # lock 이 새로 잡히는가
```
- 30분이 지나도 커밋이 0건이면 §6 을 본다.

### 되돌리기 (구 계정 한도가 돌아왔을 때)
구 계정 4개를 다시 켠다. **양쪽 다 한도가 살아 있으면 새 계정을 끌 필요 없이 8워커 동시 가동해도 된다.**
어느 쪽이든 한도가 다시 죽으면 **그쪽만** 끄고 lock 청소(§2-②)를 한다.

### Fable 로 돌릴 때 특히 지킬 것

지시서에 이미 있지만 모델이 바뀌면 제일 먼저 깨지는 항목들이라 다시 못박는다.

1. **이미지는 메인 세션에서 절대 Read 하지 않는다.** 레퍼런스 대조·채점·측정은 전부 `Task`
   서브에이전트에게 시키고 **텍스트 결과만** 받는다. 이걸 어기면 컨텍스트가 한 회차 만에 날아간다.
2. **한 세션 = 작업 단위 1개.** 남는 것 같아도 다음 작업을 집지 않는다. 병렬 세션과 충돌한다.
3. **기계적 작업에는 비평 루프를 돌리지 않는다**(지시서 [3]-(가)). 회차 예산을 다 태운다.
4. **`index.html` 전체를 읽지 않는다.** `grep` 으로 구간만 찾아 부분 편집한다(파일이 350KB 넘는다).
5. 컨텍스트 70% 넘으면 마무리 → PROGRESS 갱신 → lock 삭제 → 커밋 → 종료.

## 5. 루틴 만들기 (프롬프트 + 정확한 파라미터)

### 5-1. 프롬프트 (워커 전부 공통 · 그대로 복사)

`{{워커}}` 자리에 `A`~`H` 문자만 바꿔 넣는다. 문자는 이름표일 뿐 역할 차이가 없다.

```
너는 kuzuni/kkkkkk 저장소 UI 작업의 **병렬 워커 {{워커}}** 다. 여러 워커가 동시에 돌아간다.

먼저 저장소를 준비한다 (이 환경은 detached HEAD 로 체크아웃된다):
  git checkout main 2>/dev/null || git checkout -B main origin/main
  git branch --set-upstream-to=origin/main main 2>/dev/null
  git pull --rebase origin main

그 다음 **`docs/ROUTINE.md` 를 읽고 거기 적힌 지시를 처음부터 끝까지 그대로 수행한다.**
그 파일이 이 작업의 유일한 지시서다. 여기 적힌 것과 다르게 행동하지 마라.
지시서가 사라졌거나 읽을 수 없으면 아무것도 수정하지 말고 '지시서 없음'으로 보고하고 종료한다.
```

루틴 이름은 `방치형 UI 병렬 워커 {{워커}} (:05)` 처럼 **실행 분(分)을 이름에 박아 둔다.**
나중에 목록만 보고도 cron 을 알 수 있어야 교체가 쉽다.

### 5-2. 만드는 방법 두 가지 — **웹 UI 를 권장한다**

| | 웹 UI | 에이전트(`create_trigger`) |
|---|---|---|
| 새 세션으로 실행 | 기본 | **`create_new_session_on_fire: true` 를 직접 줘야 함** |
| 모델 지정 | 만들 때 선택 | **불가.** 만든 뒤 `update_trigger` 로 따로 지정 |
| allowed_tools 지정 | 가능 | **불가** (기본값으로 감) |
| 나중에 에이전트가 끄기 | **불가**(사람만) | 가능 |

계정 1 의 A~D 는 웹 UI 로 만든 것이다. **똑같은 모양을 원하면 웹 UI 로 만들어라.**

### 5-2-b. `create_trigger`(meta_mcp)로 만들면 빠지는 것 — 2026-08-30 실측

현재 가동 세트 8개는 이 경로로 만들었다. §5-2 표가 «불가» 로 적어 둔 것 중 **실제로 확인된 것과
아닌 것**을 갈라 적는다.

| 항목 | 실측 결과 |
|---|---|
| `allowed_tools` | **지정은 못 하지만 기본값에 `Task` 가 들어 있다** — `preset:default` + `Task`·`Bash`·`Glob`·`Grep`·`Read`·`Edit`·`Write`·`WebFetch` 등. §5-3 이 걱정하던 «Task 누락으로 비평 루프가 통째로 안 돈다» 는 **일어나지 않았다** |
| `model` | 생성 시점엔 `""` 로 비어 있다. 만든 직후 `update_trigger(model:"claude-opus-5")` 로 8개 전부 박을 것 |
| `connectors` | **이 조직에서는 파라미터 자체가 거부된다** — `the connectors parameter is not available for this organization. Omit the connectors parameter.` 넣지 말고 생략할 것 |
| **`sources`** | **파라미터가 없다.** 웹 UI/raw API 로 만든 루틴에는 `session_context.sources` 에 저장소가 박혀 있지만 이 경로엔 그 필드가 없다. 뜬 세션에 클론이 없으면 프롬프트 첫 줄 `git fetch origin main` 부터 실패한다 — **첫 사이클 로그로 반드시 확인할 것** |
| **MCP 커넥터** | 생성 시 경고가 뜬다: «this trigger stores no MCP connectors, so the sessions it fires will run without connector (`mcp__<server>__*`) tools». 즉 fired 세션에 `mcp__github__*` 가 없다 — 워커 프롬프트가 fetch 타임아웃 대비책으로 적어 둔 `mcp__github__get_file_contents` 폴백은 이 세트에서 못 쓴다 |
| 나중에 에이전트가 끄기/켜기/삭제 | **된다.** `http_api`(웹 UI) 루틴과 달리 이 경로로 만든 것은 세션 안의 에이전트가 관리할 수 있다 |

**공개 저장소라는 점이 폴백을 하나 준다** — `https://github.com/kuzuni/kkkkkk/commits/main.atom` 은
인증 없이 200 을 돌려준다(2026-08-30 확인). 커넥터도 클론도 없는 세션에서 커밋 최신성을 볼 때 쓴다.
감시견 루틴이 이 방법을 쓴다.

### 5-3. 에이전트로 만들 때 (`create_trigger`) — 빠뜨리면 안 되는 것

```
create_trigger(
  name:        "방치형 UI 병렬 워커 A (:05)",
  cron_expression: "5 * * * *",            # B=20 / C=35 / D=50
  prompt:      <5-1 의 프롬프트>,
  environment_id: <list_environments 로 조회한 이 계정 값>,
  create_new_session_on_fire: true,        # ★ 없으면 루틴이 새 세션을 안 띄우고
                                           #   «만든 그 세션» 으로 메시지를 보낸다.
                                           #   4개 다 그러면 워커 4명이 아니라
                                           #   세션 하나가 15분마다 찔리는 꼴이 된다
  initiation:  "human_request",
  connectors:  []                          # 이 작업엔 커넥터가 필요 없다
)
```
만든 **직후** 4개 전부 모델을 박는다 (`create_trigger` 에는 model 파라미터가 없다):
```
update_trigger(trigger_id: <위에서 받은 id>, model: "claude-opus-5")
```

`allowed_tools` 는 `create_trigger` 로 지정할 수 없다. 기본값에 `Bash`·`Read`·`Write`·`Edit`·
`Glob`·`Grep`·`Task` 가 들어 있는지 **첫 실행 로그로 확인**한다. 특히 **`Task` 가 없으면**
비평가·측정 서브에이전트를 못 띄워서 지시서 [3]-(나) 루프가 통째로 안 돈다 —
그때는 웹 UI 에서 다시 만들어야 한다.

### 5-5. raw API(`RemoteTrigger`)로 만들 때 — 계정 2 에서 실제로 성공한 body 원문 (계정 3 도 이걸 그대로)

MCP `create_trigger` 가 없는 세션(로컬 Claude Code 등)에서는 `RemoteTrigger` 도구로 `POST /v1/code/triggers` 를 직접 친다.
§5-3 의 평면 파라미터는 **400 «One of job_config or session_request must be set»** 로 거부된다. 아래 형태만 받는다.
raw API 는 §5-2 표와 달리 **model·allowed_tools 를 생성 시점에 넣을 수 있다**(update 불필요).

**environment_id 는** 그 계정의 기존 트리거를 `RemoteTrigger list` 로 보면 `job_config.ccr.environment_id` 에 있다
(트리거가 하나도 없으면 웹 UI 에서 루틴을 하나 만들어 보고 list 로 읽는다).

```json
{
  "name": "방치형 UI 병렬 워커 A (:02)",
  "cron_expression": "2 * * * *",
  "enabled": true,
  "persist_session": false,
  "job_config": { "ccr": {
    "environment_id": "<이 계정의 env_…>",
    "events": [{ "data": { "message": {
        "content": "<§5-1 프롬프트 원문, {{워커}} 를 A 로>",
        "role": "user", "type": "user" },
      "parent_tool_use_id": null, "session_id": "", "type": "user",
      "uuid": "aa000301-0000-4a00-9e00-000000000301" } }],
    "session_context": {
      "allowed_tools": ["Bash","Read","Write","Edit","Glob","Grep","Task","WebFetch"],
      "model": "claude-opus-5",
      "sources": [{ "git_repository": { "url": "https://github.com/kuzuni/kkkkkk" } }]
    }
  } }
}
```
- `persist_session: false` 가 곧 «매 실행 새 세션»(= `create_new_session_on_fire: true`). 빠뜨리면 §6 의 «세션 하나가 찔리는» 사고.
- B/C/D 는 `name`·`cron_expression`·`content` 의 워커 문자·`uuid` 끝자리만 바꾼다(계정 3: :17 / :32 / :47).
- 만든 뒤 모델을 바꾸려면 `RemoteTrigger update`, body `{"model":"claude-opus-5"}` 처럼 **평면 키**로 부분 갱신된다(job_config 안 건드림). cron·name 도 같은 방식.
- 확인은 §5-4. `list` 응답에서 4개의 `next_run_at` 분이 :02/:17/:32/:47 이고 `enabled:true`, `model`, `sources` 가 kkkkkk 인지 본다.

### 5-6. 계정을 늘릴 때 (3개 이상 동시 가동)

- **§4 체크리스트(push 권한·environment_id·playwright)를 그 계정에서 먼저** 통과시킨다. 안 되면 매시간 조용히 실패한다.
- cron 은 §1 표의 그 계정 열을 쓴다 — 다른 계정과 **같은 분을 절대 쓰지 않는다**.
- 나머지는 아무것도 바꿀 게 없다: 락(`docs/claims`)·선점 티어·회차 상한·heartbeat·smoke 게이트는 전부 저장소 규칙이라 계정을 가리지 않는다.
- 12세션이면 `index.html` rebase 충돌이 더 잦다 — 지시서 [4](양쪽 변경 살리기 + smoke 재통과)로 흡수된다. 충돌 커밋이 시간당 3건을 넘기면 계정 하나를 잠시 끄는 게 낫다.
- 어느 계정이든 **한도가 죽으면 그 계정만** 끈다(§2). heartbeat 덕에 죽은 lock 은 90분 안에 회수된다.

### 5-4. 만든 뒤 반드시 확인
```
list_triggers()   →  4개가 cron 5/20/35/50, enabled, 각자 다른 이름인지
```
- `next_run_at` 이 4개 다 **다른 분(分)** 인지 본다. 같으면 cron 을 잘못 넣은 것이다.
- 첫 실행 후 §2-⑤ 로 커밋이 올라오는지 확인한다.

## 6. 문제 대응

| 증상 | 원인 | 조치 |
|---|---|---|
| 매시간 도는데 커밋이 0건 | 한도 소진, 또는 push 권한 없음 | 세션 로그 확인 → 한도면 계정 교체(§2), 권한이면 §4 |
| **커밋이 몇 시간째 0건인데 실행 기록도 없다** | **루틴 자체가 꺼져 있다** (사람이 껐고 재가동을 잊음 — 2026-08-29 실제 사고) | `list_triggers(enabled: true)` 를 본다. 빈 배열이면 전부 꺼진 것이다. `updated_at` 이 수초 간격으로 순차로 찍혀 있으면 사람이 클릭한 것이고, `ended_reason`·`suspension_reason` 이 둘 다 비어 있으면 API 상 «user-paused» 다. §1-b |
| 에이전트가 루틴을 못 켠다 / 못 지운다 / 즉시실행 못 한다 | 웹 UI 로 만든 루틴(`created_via: http_api`) | 정상 동작이다. 사람이 루틴 목록에서 직접 한다(§2-①). 에이전트가 관리해야 한다면 `create_trigger` 로 다시 만들 것(§5-2-b) |
| 특정 작업이 계속 안 잡힘 | 죽은 lock 이 남음 | §2-② 로 생사 판별 후 죽은 것만 삭제. 애매하면 90분 규칙에 맡긴다 |
| 같은 화면을 두 세션이 동시에 만짐 | lock 절차 위반(지시서 [-1] 4), 또는 살아 있는 lock 을 사람이 지움 | 커밋 로그로 lock 소유 세션을 확인하고 아닌 쪽 작업을 revert. lock 은 §2-② 판별 없이 지우지 않는다 |
| `index.html` 충돌 반복 | 워커가 자기 구간 밖을 건드림 | 지시서 [4] 대로 **양쪽 변경을 모두 살린다**. 남의 구간은 남의 버전 유지 |
| 배포 페이지가 깨짐 | 깨진 상태로 push 됨 | 해당 커밋 revert 후 push. 워커는 push 전 헤드리스 실행으로 에러 0건 확인 의무 |
| 세션이 여러 작업을 한 번에 함 | 지시서를 안 읽음 | 프롬프트가 §5-1 원문 그대로인지 확인(작업 내용을 프롬프트에 직접 쓰면 이렇게 된다) |
| 루틴 시각이 됐는데 새 세션이 안 뜨고 만든 세션에 메시지만 옴 | `create_new_session_on_fire` 누락 | §5-3. 루틴을 지우고 그 옵션을 넣어 다시 만든다 |
| 비평 루프가 안 돌고 그냥 넘어감 | `Task` 도구 없음 | §5-3. 웹 UI 로 다시 만든다 |
