### 계측 ② — 같은 글자, 다른 크기
두 캡처 시점의 `.pcb-d>b` 를 그대로 읽으니 **텍스트가 양쪽 다 `"5,000"` 인데**

`font-family`·`font-weight`·`letter-spacing`·`transform`·`text-align` 은 **전부 동일**. `font-size` 단 하나만 달랐다.
→ 서체 로딩·`#shopw` 한정 규칙 같은 것이 아니라 **누가 인라인 `font-size` 를 눌러 놓은 것**이다. 그 자리는 `fitNum`(150) 하나뿐이다.

### 원인 — `fitNum` 의 **래칫**
`fitNum` 을 감싸 호출마다 찍어 보면(상점 바 다이아, 값이 세 번 바뀌는 동안):

```
FIT before t="178,279" cw=126 fs=      → after fs=31.4px cw=115
FIT before t="38,763"  cw=100 fs=31.4  → after fs=28.61px cw=91
FIT before t="5,000"   cw=77  fs=28.61 → after fs=26.04px cw=70
```

`const box = maxW || el.clientWidth` — **그릇 폭으로 「제 폭」을 쓴다.** 그런데 그 폭은 직전 호출이 이미 줄여 놓은 값이다.
게다가 잉크(`Range.getBoundingClientRect`)는 `scaleX(1.096)` 과 `-webkit-text-stroke` 를 **포함**하고 `clientWidth` 는 **포함하지 않으므로**,
넘칠 자리가 남아돌아도 `ink > box` 가 **항상** 참이다 → 값이 바뀔 때마다 한 계단씩 내려앉아 결국 바닥 `FITMIN 0.55` 에 눌어붙는다.

두 페이지가 갈린 이유도 여기서 나온다 — 던전 바는 **닫혀 있어** `clientWidth === 0` 이라 `if(!box) return` 으로 빠져나가 한 번도 안 줄었고,
상점 바는 **열린 채** 값이 세 번 바뀌어 세 계단 내려갔다. 그래서 「같은 5,000 이 두 페이지에서 다른 크기」가 됐다.

### 같은 결함의 두 번째 현장 (이 작업이 발견한 미등재 빨강)

(`전투력 높이 −47.8%` · `젬 높이 −53.6%` ← 0.55 바닥의 산술 그대로).

### 수정 — `index.html` 2곳 (`fitNum` 위 `fitRoom` 신설 + `fitNum` 앞 6줄)
그릇은 「제 폭」이 아니라 **「부모가 이 요소에 내주는 폭」** 이다.

```js
function fitRoom(el){          /* 부모 콘텐츠 폭 − 흐름에 있는 형제 − gap */
  ... position:absolute/fixed·display:none 형제는 자리를 안 먹으므로 제외
  ... 형제 폭은 offsetWidth(레이아웃 폭) — transform 걸린 형제도 자리는 원래 폭만 먹는다
  return room <= 0 || room - el.offsetWidth <= 0.5 ? 0 : room;   /* 내용에 맞춰 늘어나는 부모 = 가둘 그릇 없음 */
}
```
`fitNum` 은 `box` 가 0 이면 **전에 눌러 둔 인라인 `font-size` 를 되돌리고** 빠진다(래칫 잔재 청소).

## 2회차 — 「제 폭과 같으면 그릇이 없다」는 지레짐작을 걷어내고, 잉크와 그릇의 **단위**를 맞췄다

1회차의 `fitRoom` 은 마지막 줄에 지레짐작을 하나 달고 있었다:

```js
return Math.abs(room - el.offsetWidth) <= 1.5 ? 0 : room;   /* ← 틀렸다 */
```

「남는 자리가 제 폭과 같다 = 부모가 이 요소에 맞춰 늘어났다 = 가둘 그릇이 없다」로 읽은 것인데,
**클램프가 성공한 직후가 정확히 그 모양이다** — 잉크를 그릇에 딱 맞춰 놨으니 제 폭이 그릇 폭과 같아진다.
그래서 15자리 값(`987,654,321,098,765`)에서 이런 일이 벌어졌다:

1. 클램프 걸림 → `fs 18.98` · 레이아웃 폭 ≈ 187 ≈ 그릇 186.5
2. 다음 호출 → `|186.5 − 187| ≤ 1.5` → **그릇 없음(0)** 으로 판정 → 인라인 `font-size` 를 **되돌림**(34.5)
3. 롤링이 끝나 텍스트가 더 안 바뀜 → `renderPcb` 의 `d !== pcbDia` 가드에 걸려 **다시 안 불림** → 34.5 로 굳음

신설 게이트 ⑤ 가 이 자리에서 두 번 빨개져 잡았다(1회차 게이트로는 «12/14»).

### 고친 것 2가지

**(1) 지레짐작 제거 — 그릇이 없는 자리는 «호출부» 가 실제 한계를 넘긴다.**
암묵 `fitRoom` 을 타는 자리는 셋뿐이고, 그중 부모가 내용에 맞춰 늘어나는 것은 **전투력 `#cpN`(`.pcp`)** 하나다.
그 한계는 부모가 아니라 **우측 재화 알약 묶음 `.curs`** 이므로 `cpRoom()` 을 신설해 명시로 넘긴다
(`.pcp b` 는 `transform-origin:0 50%` 라 잉크가 좌변에서 오른쪽으로만 자란다 — 좌변부터 `.curs` 좌단까지가 쓸 수 있는 폭. 실측 **371px**).

**(2) 잉크와 그릇의 단위를 맞췄다 — 이건 150 부터 있던 잠복 결함이다.**
`fitNum` 이 재는 잉크는 `Range.getBoundingClientRect()` = **화면 px**(조상 `fit()` 배율 포함)인데,
옛 `box`(`el.clientWidth`)는 **레이아웃 px**(배율 미포함)였다. 배율 1 인 캡처·데스크톱에서만 우연히 같았고,
실제 기기(배율 ≈ 0.35)에서는 잉크가 그릇의 1/3 로 보여 **클램프가 아예 안 걸린다**.
`fitRoom` 이 `room × (부모 rect 폭 / 부모 offsetWidth)` 로 화면 px 을 돌려주게 했다 —
20751 `raidFitNums` 가 명시 `maxW` 를 화면 px 로 넘기며 「양변을 화면 px 로 맞춘다」고 적어 둔 것과 같은 공간이다.
