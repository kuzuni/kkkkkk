## 3. 처방 — 자리를 비우지 않고 방향을 뒤집었다(333)

`tools/probe325.js` 의 그 항 하나를 **두 항으로 갈랐다.** 좌표 상수는 한 개도 안 적었다 —
살아 있는 `--dot-in` / `--dot-r` / `--dot-bw` 로 **식을 묻는다**(규약값이 바뀌면 자가 따라온다).

| 새 항 | 묻는 것 |
|---|---|
| `471 규약 — 닷 중심이 알약 우상단 코너 안쪽 --dot-in` | 안쪽 우·상 = `--dot-in` (±0.5) |
| `알약 변을 넘는 양이 규약값(링R − --dot-in)뿐` | 걸침이 정확히 10px, 그보다 더 나가면 빨강 |
| `--dot-bw 가 알약의 실제 테두리 두께와 짝이다` | `.ifbtn{--dot-bw:var(--gb-bw)}` 6px ↔ 실 border 6px |

⚠ **1회차에 기준 상자를 틀려 «규약 5,5» 라는 헛빨강을 한 번 냈다.**
`getBoundingClientRect()` 는 **테두리 상자**이고 471 규약의 기준도 «테두리 바깥 상자» 인데,
CSS 식이 `--dot-bw` 를 되빼는 것은 «절대배치 오프셋이 **패딩 상자** 기준» 이라서다 —
그 되빼기는 rect 로 잴 때 **정확히 상쇄된다.** 그래서 안쪽 거리는 `--dot-bw` 와 **무관하게**
`--dot-in` 이어야 한다. 이 오해를 자에 남기지 않으려고 세 번째 항(«`--dot-bw` ↔ 실 테두리 짝»)을
따로 세웠다 — 짝이 어긋나면 안쪽 거리가 5 나 17 로 나와 즉시 빨개진다.

### §R 되돌림 시험 (무르게 푼 수리가 아님)

옛 325 좌표(`right:12px;top:12px`)를 `!important` 로 도로 주입한다.

```

      — blsC_atk 안쪽 31.5,31.5 vs 규약 11 · blsC_hp 안쪽 31.5,31.5 vs 규약 11
ok  주입을 걷으면 규약 자리로 되돌아온다 — blsC_atk 안쪽 11,11 · blsC_hp 안쪽 11,11
```
