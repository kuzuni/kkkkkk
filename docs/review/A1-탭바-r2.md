### 13회차에 반영하지 않은 것 — «ref 값에 우리에게 없는 아트가 들어 있다» 계열

이 라운드에서 **반복해서 발목을 잡은 오류 유형**이다. ref 는 완성된 아트라 우리 CSS 대체물에
**없는 부속**을 bbox 안에 품고 있고, 그걸 모르고 맞추면 멀쩡한 값을 망친다.

| 항목 | 겉보기 지적 | 실제 |
|---|---|---|
| **NEW 리본 밴드 폭** | R «ref 보다 16px 길다 → 잘라라» | Q 가 기각: **ref 폭에는 «뒷면 꼬리» 아트가 포함**돼 있고 그건 §10 «아트 필요» 등재분이다. «꼬리를 빼면 오히려 우리가 +13% 넓다» → **꼬리 아트가 오기 전엔 이 항목으로 크기를 움직이지 마라** |
| **던전 아이콘 폭** | N «ref 117 (−6%)» · O «ref 116 (−5.2%)» | R 이 해소: **ref 117 은 검정 키라인 5~6px×2 를 포함한 값**이고 코어끼리는 107 vs 우리 110 으로 **실질 동등**. M «ref 110» · P «ref 108» 과 갈렸던 것이 이걸로 설명된다 |

## ★★ 11회차 → 12회차 — 「내 수정이 오차를 3px 에서 7px 로 키웠다」

이 라운드에서 **가장 값어치 있는 회차**다. 10회차에 «2인 일치» 로 반영한 6건 중 **1건이 틀렸고**,
11회차 비평가 O·P 가 그것을 독립적으로 잡아냈다.

### 무슨 일이 있었나

10회차에 «NEW 리본 상변이 4px 위로 새어 바 상단 검정 테두리를 넘는다» 며 리본을 **4px 내렸다.**
근거는 셋이었다 — N «우리 rel −1 vs ref rel 3» · 자체 스캐너 «우리 2099 vs ref 2103» ·
측정표 §7-1 정오값 «ref 2103». 세 값이 일치했으니 안전해 보였다.

**전부 같은 오류를 공유하고 있었다.** 직접 재보니:

| | 적색 밴드 상변 (바 상단 기준 rel) |
|---|---|
| 레퍼런스 | **+1** |
| r10 (수정 전) | +4 (3px 낮음) |
| r11 (수정 후) | **+8** (7px 낮음 — 오차가 2배 이상 커졌다) |
| r12 (되돌림) | **+1** ✅ |

원래도 리본은 **3px 낮았다**. 그런데 «위로 샜다» 고 읽고 더 내린 것이다.

### 원인 — 「같은 마스크로 잰 값이 아니었다」

- 측정표의 ref `2103` 은 **적색만 잡는 마스크**(`r>80 · g<95 · r−g>55`)로 잰 값이다.
- 내 차분 스캐너의 우리 값 `2099` 는 bbox 라 **검정 `border-top` 4px 까지 문** 값이다.

즉 «검정 포함 상변» 과 «적색 전용 상변» 을 맞대어 **없는 4px 오차**를 만들어 냈다.
리본의 검정 테두리가 정확히 4px 이라 오차도 정확히 4px 이었고, 그래서 세 계측이
사이좋게 같은 크기로 틀렸다 — **일치한다고 맞는 게 아니다.**

> ### 일반화 (다음 세션이 반드시 볼 것)
> **두 수치를 비교하기 전에 «같은 마스크로 잰 값인지» 먼저 확인하라.**
> 특히 검정 외곽선·테두리가 있는 요소는 «포함/제외» 가 그대로 **테두리 두께만큼의 계통 오차**가 된다.
> 그리고 **여러 계측이 일치한다는 사실은 검증이 아니다** — 같은 도구·같은 정의를 공유하면
> 같은 방향으로 함께 틀린다. 일치를 봤으면 **정의가 서로 독립인지** 를 한 번 더 봐라.

  측정표 §3 의 «잉크 높이 32» 는 **흰 코어** 값이다. 코어로 환산하면 33~34 vs 32 = **+3~6%** 로
  사실상 일치한다(비평가 H 도 «흰 코어 높이 ref 32 vs 우리 32/33 — 일치» 로 독립 확인).
  `scanA1.py` 가 이제 코어로 환산해 찍는다.
- **«유물 라벨 폭 −50%»** — ref 는 «보물상자»(4자 121px), 우리는 «유물»(2자)이다. **대조 자체가
  성립하지 않는다.** 폭을 비교할 수 있는 칸은 ref 와 같은 단어인 **영웅·상점 둘뿐**이다
  (영웅 +10.7% / 상점 +1.7%). 스캐너가 나머지 칸에 «개칭 — 대조 불가» 를 찍게 했다.
- **«✕ 칸 폭 296 → 301»**(H ④) — ref 3장 실측이 296/299/297 이고 측정표 설계값이
  «296 + 196×4 = 1080» 으로 딱 떨어진다. 301 로 올리면 합이 1085 가 되어 그리드가 깨진다. 유지.

## 아직 남은 것

- **라벨 검정 외곽선 두께** — H 는 «ref 4 vs 우리 5~6 (+25~50%)», G 는 «양쪽 동일(4~5)» 로 **갈렸다.**

  평평한 띠로는 못 만든다 → 측정표 §10 «아트 필요» 에 등재.
- **레퍼런스 아이콘의 «하단» 은 구조적으로 신뢰할 수 없다** — 레퍼런스에서 아이콘과 라벨은 **겹친다**
  (측정표 §4 «아이콘–라벨 gap 은 음수»). 그래서 합성 이미지를 재는 비평가마다 하단이 갈린다:
  상점 칸 세로를 G 115 · J 124 · I 131 로, 측정표는 115 로 읽었다. **상단은 라벨이 안 덮어 안전하다** —
  8회차부터 앵커를 «칸별 ref top» 으로 옮긴 이유다. 하단이 필요한 판정은 라벨을 배제한 마스크로만 하고,
  못 하면 «상단 + 폭» 으로 대신할 것. (8회차 비평 프롬프트에 이 지시를 넣었다.)
- **상점 칸 세로** — 위 이유로 4갈래(115/115/124/131)라 8회차에 손대지 않았다. K·L 의 근거 있는
  실측을 받아 2인 일치가 나오면 그때 움직인다.

### 6회차에 겪은 게이트 사고 1건 (다음 세션이 반드시 볼 것)

`node tools/smoke.js | tail -2 && git push ...` 로 묶었더니 **파이프가 smoke 의 종료 코드를 가려**
`SMOKE FAIL` 인 채로 push 가 나갔다(커밋 `3730eac`, 다음 커밋에서 복구). **게이트는 출력이 아니라
종료 코드로 확인한다** — `node tools/smoke.js > 파일; echo $?` 형태로 돌릴 것.

실패 내용 자체도 남길 만하다: CSS 주석 안에 «210/211/211/211/» 뒤에 마크다운 강조 별표 두 개를
붙였더니 **슬래시+별표가 여는 주석 기호로 세어져** smoke [0] 의 주석 균형 검사가
«여는 1695 vs 닫는 1694» 로 FAIL 했다. 렌더링은 멀쩡하지만(주석은 첫 닫는 기호에서 끝난다)
게이트가 «규칙이 조용히 사라지는» 사고를 잡으려고 세는 값이라 실제 결함으로 취급하는 게 맞다.
**주석 안에서 슬래시 바로 뒤에 별표 두 개를 쓰지 마라.**
