## 1. 무엇이 어긋나 있었나 — 액자 하나뿐이었다

행의 나머지는 **이미 6행 전부 동일**했다(실측, 카드 로컬 좌표):

| 부품 | 6행 실측 |
|---|---|
| 카드 | 980×350 (동일) |
| 이름 `.nm` | @(39,40) h56 (동일) |
| 보상 알약 `.pill` | 288×46 @(92,121) (동일) |
| 라벨 `레벨`/`남은 횟수` | @(134,243)/(316,243) (동일) |
| 값 `.sp` | 156×47 @(84,277) · 171×47 @(279,277) (동일) |
| 레드닷 | 27×27 @(956,0) (동일) |
| **썸네일 액자 `.th`** | **330×330@(643,11) / 311×305@(662,36) / 296×289@(677,52) ← 셋으로 갈림** |

즉 «행 레이아웃이 제각각» 의 실체는 **썸네일 액자 하나**다. 6행을 세로로 훑으면
액자 왼쪽 선이 **x643 → 662 → 677 → 643 → 643 → 643** 으로 튄다.

## 2. 원인 — «크롭 차이» 가 «틀 어긋남» 이 됐다

카드별 값(311/36 · 296/52)은 **틀린 측정이 아니다.** 레퍼런스에서 그 자리는 «카드 우·하단으로
흘러넘쳐 잘리는 일러스트» 였고(측정표 §3-8), 잘려 나가는 그림은 카드마다 크롭이 달라도 자연스럽다.

그런데 **72 가 주인 재지시로 그 자리를 «액자» 로 바꿨다** — 네 변이 다 보이는 틀이다.
틀이 되는 순간 같은 차이가 «크롭» 이 아니라 **«틀이 안 맞는다»** 로 읽힌다.
§3-8 자신이 이미 «레퍼런스에는 액자가 없다 — 의도적 이탈» 이라고 적어 뒀는데,
**그 이탈의 귀결(= 틀은 한 벌이어야 한다)까지는 안 따라간 상태**였다.

## 3. 수정 ① — 슬롯을 6행 공용 상수 한 벌로

```js
const DUN_TH_W = 330, DUN_TH_T = 11;
Object.keys(DUN_UI).forEach(k => { const u = DUN_UI[k];
  u.thw = DUN_TH_W + 'px'; u.tht = DUN_TH_T + 'px'; });
```

값은 **6행 중 4행(유물조각 1~4단)이 이미 쓰던 것**을 그대로 승격했다 — 새 값을 발명하지 않았다.
카드(980×350) 안에서 우단 7(`.dnc>.th` CSS 상수) · 하단 9 · 상단 11 · 좌변 x643 으로 떨어진다.

| | 149 이전 | 149 이후 |
|---|---|---|
| 슬롯 | 311×305 / 296×289 / 330×330 ×4 | **330×330 ×6** |
| 상단 인셋 | 36 / 52 / 11 ×4 | **11 ×6** |
| 액자 좌변 | x662 / 677 / 643 ×4 | **x643 ×6** |
| 캔버스 픽셀 | 289×283 / 274×267 / 308×308 ×4 | **308×308 ×6** |

⚠ **레이드·아레나 카드(`.dnc.rd`)는 안 건드렸다** — 97 이 «슬롯을 꽉 채운다» 규칙으로 통과시킨 화면이고,
주인 지시는 «던전 행» 이다. `verify72` 의 레이드 절(REXP)·`verify121` 의 `RAID_TH` 도 그대로다.

## 4. 수정 ② — 프레임 rect 트림 (`TH_TRIM`)

슬롯을 통일하고 다시 재니 **황금 동굴(용)만** 액자 안에서 아래로 치우쳐 있었다.

| 카드 | 잉크 중심 오프셋 | 세로 채움 |
|---|---|---|
| 황금(용) | cx +6 · **cy +31.5** | **39.3%** |
| 수정(새) | 0 · 0 | 87.7% |
| 유물 1~4 | 0 · 0 | 87.7~89.0% |

원인은 슬롯이 아니라 **아틀라스 프레임 rect** 였다. 아이들 창 전 프레임의 알파 bbox 를 재 보면:

| 아틀라스/애니 | rect | 잉크 | rect 대비 |
|---|---|---|---|
| **dragon/fly f2·f3·f4** | 96×64 | **x2..95 · y22..63** (세 프레임 y 동일) | **60~64%** |
| bird/frame0 | 82×95 | x1..80 y1..93 | 95.5% |
| robo/Running_007 | 126×217 | x1..124 y1..215 | 97.4% |
| zombie/walk_006~008 | 174~178×225~235 | 여백 1~2px | 97.4~98.0% |
| elves/green·blue_idle | 106~117×130~135 | 여백 1px | 96.6~96.8% |

**dragon 만 위 22행(34%)이 완전 투명**이라 `contain` 이 빈 공간까지 담았다.
세 프레임의 잉크 y 가 **완전히 같고**(22..63) x 좌단만 2·4·8 로 날갯짓하므로,
**합집합 rect `[2, 22, 94, 42]`** 를 상수로 쓰면 창 안에서 배율 `k` 가 하나로 유지된다
→ 121 6회차가 확보한 «창 안 top p2p 0 · step 0» 이 그대로 산다(VERIFY121 122/122 로 확인).

결과: 용 **cy +31.5 → +0.5** (나머지 5행과 같은 0). `TH_TRIM` 은 던전 카드(`fit` 경로)에만 걸고
레이드·아레나(`fit 0`, 꽉 채우기)에는 안 건다.

### 남는 것 — 세로 채움 39.9% 는 «아트 대기» 다

용은 잉크 자체가 94×42(**종횡 2.24**)라 종횡 1.0 액자에 담으면 세로가 남는 것이 정상이다.
트림이 고친 것은 «작다» 가 아니라 **«치우쳤다»** 다. 크기는 종횡 1 에 가까운 용 아트가 들어와야 풀린다
(발주 규격: 액자 안쪽 **308×308**, 투명 PNG, 사방 16px 여백 — 측정표 §3-8 개정에 적었다).

## 5. 게이트 — 상수를 «베끼지 않고 읽게» 바꿨다

`verify72` 의 `EXP` 와 `verify121` 의 `DUN_TH` 는 값을 **하드코딩**하고 있었다. 그대로 새 값으로
갈아 끼우면 다음에 또 낡는다(LESSONS 147-③). 둘 다 **페이지에서 `DUN_TH_W/DUN_TH_T` 를 읽어**
기대치를 만들도록 고쳤다. `verify72` 의 «종횡 왜곡 0» 단언도 `TH_TRIM` 을 페이지에서 읽어
**그리기 계약과 같은 원본 rect** 로 재게 했다 — 안 그러면 트림을 넣는 순간 게이트가 거짓 빨강을 낸다.

신설 단언 2개: «공용 슬롯 상수 = 330/11» · «기대 슬롯이 6행 전부 같은 한 벌».

## 6. 곁가지 — verify121 의 성능 2항목은 내 것이 아니다

`verify121` 에 «배경 켠 채 스크롤 fps 기준 대비 ≥90%» · «중앙 프레임 ≤ 33.3ms × 1.15» 가 있는데
**수정 전 HEAD 에서도 72.5% / 76.6% 로 빨갛다**(2회 확인). 이 컨테이너의 rAF 간격이 32~42ms 라
33.3ms 기준선 자체가 도달 불가다(index.html 주석이 여러 곳에서 같은 사실을 적어 뒀다).
내 구간이 아니고 122 가 lock 을 들고 있어 **손대지 않았다.** 재실행하면 통과할 때도 있는 **간헐**이다
(LESSONS 145-② «한 시점으로 찍는 게이트는 뜨고 진다» 와 같은 계열) — 최종 확인 실행은 122/122 PASS.
