### 유령 셋의 뿌리는 하나 — **이 화면에는 앵커가 둘이다**

ROUTINE [2] 의 «프레임 y = 레퍼런스 y − 84» 는 **상단 앵커 요소**의 변환이다.
03 은 상단 HUD 와 하단 탭바 사이를 꽉 채우는 페이지라 아래에 붙는 요소는 자가 다르다:

| 앵커 | 요소 | 변환 |
|---|---|---|
| 상단 | 카드 리스트(카드 5장) · 팝업 내장 재화 바 | `cap_y = ref_y − 84` |
| **하단** | **서브탭 바** · 앱 하단 탭바 | **`cap_y = ref_y − 60`** (ref 2340 ↔ cap 2280) |

두 자의 차 **24px** 이 프레임이 레퍼런스 콘텐츠(2256)보다 긴 몫이다.
비평가에게는 ROUTINE 이 «−84» 만 알려 주므로 **하단 앵커 요소는 자동으로 +24 어긋나 보인다.**
①②③ 이 정확히 그것이다 — ①은 +24 를 «+34» 로 읽은 것이고, ②③ 은 그렇게 밀린 그림에서
«바가 짧고 알약이 눌렸다» 로 이어 읽은 것이다.

독립 검증 두 가지가 이 해석을 못박는다:
- **탭바**(같은 하단 앵커)는 ref 2160 → `−60` 으로 **cap 2100** 이고 우리도 **정확히 2100** 이다.
  `−84` 를 쓰면 2076 이 되어 «탭바도 24px 낮다» 가 되는데, 탭바는 아무도 지적한 적이 없다.
- **카드**(상단 앵커)는 ref 241 → `−84` 로 **157** 이고 우리도 **157**, 카드5 하변 1946 ↔ 1947.

### 실재 둘의 뿌리도 하나 — **96 2회차 비평가의 두 처방**

둘 다 레퍼런스 대조가 아니라 «다른 화면과의 통일감» 논거였고, 코드에 그대로 주석까지 남아 있었다.

| 자리 | 96 2회차가 넣은 것 | 레퍼런스 |
|---|---|---|
| `.dns-list{bottom}` | «상점과 같은 14px 여백» → 153 | 이음매 바탕 **0px** (카드 검정 하변 8px 과 바 검정 상변 6px 이 **겹친다**) |
| `.dns-sub{left}` | «다른 공용 바는 전부 대칭» → 143/143 | 좌 **151** / 우 **135** = 축 **+8 비대칭** |

레퍼런스가 기울어 찍힌 것이 아니다 — **같은 화면의 카드는 x50~1029 로 좌우 여백 50/50 대칭**이다.
이 바만 오른쪽으로 8px 밀린 것이 원본 디자인이고, 그래서 뒤이은 비평가 넷이 전원 반대로 지적했다.

### 고친 것 (제품 2줄)

```
.dns-list{ … bottom:153px → 139px }      /* = 40(바 하단 여백) + 99(바 높이) */
.dns-sub { left:143px → 151px }          /* 폭 794 불변 → 우 135 */
```

**카드1 상변 157 · 바 하변 «탭바 위 40» 은 한 픽셀도 안 건드렸다.** 24px 잉여를 어디에 둘지는
ROUTINE [2] 가 이미 답을 갖고 있다 — «고정 요소는 절대값 그대로, 남는 높이는 흐르는 콘텐츠가 흡수».
이 화면에서 흐르는 콘텐츠는 스크롤 리스트라, 리스트의 **클립선**을 바 상변까지 늘려 잉여를
스크롤 여유로 먹였다. 바를 14px 올려 이음매를 닫는 대안은 «바 하변 ↔ 탭바 41» 을 54 로 깨므로 안 받았다.
