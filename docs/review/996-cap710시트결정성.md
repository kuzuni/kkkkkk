## §2 진짜 뿌리 — 손잡이는 셋이고 셋이 서로 다른 것을 잡는다

갈래를 «찍힌 화소» 가 아니라 **시전 규격(`spec`)** 에서 갈랐다. 같은 트리 3판의 `spec` 을 견주니
`whirl`·`gale`·`spiral`·`meteor` 넷만 갈렸고, 갈린 필드는 **각(`a`)** 하나였다:

```
whirl  a = 0.8759337600 / 0.9119347200 / 0.9719102400   (gale 도 같은 값 — 같은 누산기)
spiral a = sa = 2.0438454400 / 2.1278476800 / 2.2677905600
```

- `whirl`·`gale` 은 `orbitAng*0.3`(index.html **26314**·**26592**), `spiral` 은 `orbitAng*0.7`(**26341**)
  으로 **시전각을 전역 누산기에서 읽는다.**
- `orbitAng` 는 `step()` 이 `dt*2.4` 씩 밀어 올린다(**26941**·**26964**).
- 이 자는 `await page.waitForTimeout(1200)` 뒤에 rAF 를 끄는데, **그 1.2초 동안 제품의 rAF 가
  몇 프레임 도는지가 판마다 다르다** ⇒ 각이 판마다 다른 값으로 굳는다.

⚑ **15회차의 «각이 안 변한 종만 그 각을 싣는다»(aFixed) 는 이 드리프트를 구조적으로 못 본다** —
두 표적 자리에서 두 번 시전해 견주는 것은 **한 판 안**이라, 판을 가로지르는 드리프트에 대해서는
`aFixed: true` 가 «상수각» 이 아니라 **«이 판에서의 상수각»** 을 뜻한다.

`arrow`·`curve`·`rico` 칸은 뿌리가 다르다 — 흔들린 화소의 자리가 **칸 상자의 위·왼 띠**였고
(전 화면 차분의 띠 y 877~931 · 1840~1925), 이는 **배경 소품**이다. 부팅 뒤 `Math.random` 이
안 씨앗돼 있어 `spawnStage()` 가 판마다 다른 자리에 세운다.

### 처방 — 형제 자와 같은 세 줄

```js
let _rs = 0x2f6e2b1 >>> 0;
Math.random = () => { _rs = (Math.imul(_rs, 1664525) + 1013904223) >>> 0; return _rs / 4294967296; };
performance.now = () => 1e6;
orbitAng = ORB;                    /* ORB 기본값 0 */
```

앞 두 줄은 `verify792`·`probe792r13`·`probe792r15` 가 이미 쓰는 것 그대로다(사본이 아니라 같은 상수).
세 번째가 이 작업이 새로 세운 것이다.

### 손잡이별 기여 — 하나씩 빼서 쟀다(`probe996 --off`)

| 뺀 손잡이 | 되살아난 칸 | 판정 |
|---|---|---|
| `seed`(`Math.random`) | `whirl` `gale` `curve` `arrow` `rico` `spiral` (6) | **본체** — 소품 자리 + 스폰 타이밍이 `orbitAng` 까지 흔든다 |
| `orbit`(`orbitAng` 핀) | `whirl` `gale` `spiral` (3) | **본체** — 시전각을 읽는 세 칸 |
| `clock`(`performance.now`) | 없음 (3판 0) | **이 17종에서는 효과 없음** |

⚠ **시계 얼림은 «재 본 만큼» 효과가 없었다.** 그래도 세워 둔 이유는 두 가지이고 둘 다 기록해 둔다:
① 형제 자가 전부 `1e6` 이라 **채점한 그림과 자가 잰 그림이 같은 위상**이어야 한다,
② 접촉형(`aura` 반경 = `sin(performance.now()/220)` · index.html **28624**)이 시트에 들어오는 날
곧바로 필요해진다. **«고쳤다» 고 적지 않고 «파리티» 로 적는다.**

⚠ `auraTick` 도 핀에 넣어 봤지만 **아무것도 안 바꿔서** 안 넣었다.

## §3 위상 — 고른 자리가 «최악» 인가 (등재문 경고)

등재문은 «ⓐ 시계를 얼린다 — 단 «어느 위상에서 얼릴 것인가» 를 정해야 하고 잘못 고르면 회전 종이
최악 위상에서 굳는다» 고 경고했다. 그래서 `CAP710_ORBIT` 손잡이(기본값 0 · 눈금 불변)를 두고
여덟 위상을 쟀다(`node tools/probe996.js --sweep` · 칸 중심 ±70px · 휘도 90 위 잉크):

천장 대비 **−1.9%** 뿐이고, `gale`(−1.3%)·`spiral`(−3.1%)은 중간이다. ⇒ 잉크로 보면 이 셋은 회전에
거의 대칭이라 **«최악 위상» 이라는 걱정 자체가 얕다.** 그래도 수치를 `verify996` [3] 의 밴드로 박아,
누가 위상을 옮기면 그 자리가 스윕 밖인지 바로 보이게 했다.

## §4 처방 ⓐ vs ⓑ — ⓐ 를 골랐다 (위임 규약 채택)

등재문은 처방 후보 둘을 세우고 «고르는 것이 이 행의 본체다» 라고 적었다.
2026-09-01 위임 규약대로 **주인 상신 없이 그 회차에서 골라 진행했다.**

| | 대가 | 얻는 것 |
|---|---|---|
| **ⓐ 위상 고정 (채택)** | 연출 종의 «움직임» 은 여전히 한 장으로만 채점된다 | 시트가 **결정적** — 792 가 «처방이 먹혔나 / 위상이 달랐나» 를 가를 수 있다. 형제 자와 같은 위상. 시트 크기 불변 |
| ⓑ 여러 위상 나란히 | 시트가 커진다(17종 × N) · 채점 축과 회차 예산이 같이 늘어난다 · **792 는 2차 라운드 15/20 이라 남은 회차가 5뿐** | 움직임을 채점할 수 있다 |

**ⓐ 를 고른 결정적 이유**: 996 이 아픈 이유는 «움직임을 못 본다» 가 아니라 **«회차 간 점수를 못 견준다»**
이고(등재문 «그 세 칸에서는 못 가른다»), 그건 ⓐ 로 정확히 닫힌다. ⓑ 는 다른 결손(움직임 채점)을 푸는
다른 작업이고, 남은 5회차를 시트 개편에 쓰는 것은 792 라운드를 통째로 태우는 길이다.
**되돌리는 법**: `CAP710_ORBIT` 를 여러 값으로 돌려 여러 장을 찍으면 ⓑ 가 곧바로 된다 —
손잡이를 이미 심어 뒀으므로 ⓑ 로 가는 데 이 수리를 되돌릴 필요가 없다.
