## 2. 왜 «실행마다» 갈리나 — 창의 폭이 실측으로 나왔다

`jzClose()`(index.html 41189)는 `.jz-c` 를 **애니메이션이 끝날 때** 뗀다(`jzDoneThen` 훅, 폴백 타이머).
그런데 게이트의 [D][E][F] 블록은 **동기** `page.evaluate` 라 그 안에서는 프레임이 한 장도 안 흐른다 —
`closeModal(); showItem(); readParts()` 사이에 브라우저가 끼어들 자리가 없다.
그래서 값을 정하는 것은 **[D] 가 시작된 시각 하나뿐**이다. `probe764` [2] 의 창 스윕:

| 직전 닫기로부터 | `.sk-db` 폭 | 무엇이 걸렸나 |
|---|---|---|
| 0 · 20 · 40 · 60ms | **750** | `jzBoxOut` 0% (scale 1) — 아직 안 깎였다 |
| 80ms | 739.98 | 채우는 중 |
| 100ms | 747.14 | 채우는 중 |
| 120 · 140ms | 721.2 | 채우는 중 |
| **160ms** | **705.07** | 종점 부근 = `scale .94` ← **등재문의 값** |
| 200 · 300ms | 750 | 연출이 끝나 `.jz-c` 가 걷혔다 |

즉 **빨간 창은 «직전 닫기 뒤 50~170ms»** 한 토막이다. [C] 절의 마지막 닫기와 [D] 의
`page.evaluate` 왕복이 그 창 안에 떨어질 때만 빨개진다 — 한가하면 왕복이 창보다 짧고(초록),
아주 느리면 창을 지나간다(초록). **부하가 딱 그 사이일 때만** 빨갛다 = 등재문의 «플레이키».
빨간 표본은 **예외 없이** `#modal` 에 `.jz-c` 가 붙어 있었다(`probe764` 2-b).

## 3. 처방 — «몇 ms 기다린다» 는 오답이다

⚠ **고정 대기로는 이 창을 못 닫는다.** `jzBoxIn` 이 62% 에서 **1.02 로 넘겼다** 돌아오기 때문에,
고정 대기는 축소(690)든 **확대(765)** 든 어느 한쪽을 잡는다. `probe764` [1] 위상 스윕의 꼬리가
`t+200ms 764.96` · `t+240ms 764.96` 인 것이 그 증거다 — «넉넉히 기다리면 되겠지» 가 **반대 방향으로**
같은 결함을 만든다.

⇒ 재기 전에 **연출이 정착했는지 묻는다**(291·353 이 세운 축). `verify429` 안에 `settleBox()` 를 두고
`out.parts` · `out.petParts` 두 측정 지점 앞에서만 부른다.

```js
const settleBox = async () => {
  const pend = () => (document.getAnimations ? document.getAnimations() : [])
    .filter((a) => /^jzBox/.test(a.animationName || '') && a.playState !== 'finished');
  const t0 = performance.now();
  for (let quiet = 0; quiet < 2 && performance.now() - t0 < 1500;) {
    const P = pend();
    if (P.length) { await Promise.all(P.map((a) => a.finished.catch(() => 0))); quiet = 0; }
    else quiet++;
    await new Promise((r) => requestAnimationFrame(() => requestAnimationFrame(r)));
  }
};
```

### 3-1. 공용 `settle291()` 을 안 쓴 이유 (두 가지 — 둘 다 실측)

공용 부품이 이미 있는데 새로 적었으므로 근거를 남긴다. 처음엔 **`settle291` 에 «무엇을 기다릴지»
인자를 더해** 쓰려고 했고, 실제로 그렇게 짜서 돌려 봤다. **되돌렸다.**

- **ⓐ 기본 필터를 넓히면 게이트 44개가 같이 움직인다.** 그 자의 훅은 `page.waitForTimeout` 을
  전부 감싸고, 64·262(«300ms 눌러 1회 · 350ms 전엔 반복 없음»)·107(«멎은 뒤 몇 프레임») 처럼
  **시간 자체를 재는** 자는 rAF 두 프레임이 얹히면 문턱을 넘는다(그 파일 `PENDING_SRC` 주석이
  이미 그렇게 빨개진 적을 적어 두고 있다). 인자를 옵션으로 두면 그 위험은 없지만 —
- **ⓑ 그 사다리에는 이 자리의 창을 못 닫는 구멍이 있다.** `step()` 은 «부를 때 pending 이 0 이면
  곧바로 끝낸다». 그런데 이 자리는 **연출이 다음 프레임에 붙는다** — 부르는 순간엔 0 이다.
  실측으로 확인했다: 사다리를 그대로 빌려 쓰면 g200·g300 에서 **정착 후 690**(= `jzBoxIn` 0%)을 잡아,
  **고치기 전엔 초록이던 자리를 새로 빨갛게** 만들었다.
  ⇒ 조건을 «**두 프레임 연속으로 돌 것이 없을 때만** 끝낸다» 로 바꿔야 닫힌다.

상한 1500ms 는 291 과 **같은 값**을 쓴다 — 어떤 이유로든 `finished` 가 안 오면 자를 멈추지 않고 지나간다.
**되돌림**: `settleBox` 선언과 두 호출을 지우면 종전 동작 그대로(제품·다른 게이트 0줄).

## 6. 곁다리 등재 1건 — **771**

부하 재현(6코어 태우기 × 게이트 4개 병렬) 중 **다른 항**이 1회 빨개졌다:

```
FAIL A9 2280 ↔ 1600 프레임 좌표 Δ0 — (24,16) ↔ (31.74,27.19)
```

**이번 작업의 몫이 아니다**(다른 절·다른 연출·다른 기계). 다만 뿌리는 계산으로 이미 잡힌다 —
`s = (31.74 − 540) / (24 − 540) = **0.9850**` · 세로도 `(27.19 − 1140)/(16 − 1140) = 0.9900`.
**0.985 는 `jzPgIn` 의 0% 프레임**(`@keyframes jzPgIn{0%{scale:.985}}`, index.html 13951)이고,
이는 **291 이 이름 붙인 바로 그 병**이다. 291 의 훅이 이 자리를 못 막는 이유도 §3-1 ⓑ 와 같다 —
`openRel()` 의 `waitForTimeout(300)` 이 끝나는 순간엔 pending 이 0 이고 연출은 **다음 프레임에** 붙는다.
⇒ 771 로 등재했다(처방 후보까지 그 행에 적어 뒀다).

## 7. 교훈

1. **«등방으로 눌렸다» 는 배율원을 이름으로 찍을 수 있다는 뜻이다.** 관측값을 기대값으로 나눈
   0.94009 를 `@keyframes` 표와 맞대면 후보가 한 개로 좁혀진다. 이번엔 그 나눗셈 하나가
   «여는 연출» 이라는 등재문의 지목을 «닫는 연출» 로 바로잡았다.
2. **동기 `page.evaluate` 안에서는 프레임이 안 흐른다 — 그래서 «블록이 시작된 시각» 이 값을 정한다.**
   블록 안을 아무리 들여다봐도 원인이 안 보이는 플레이키는 **블록 밖**(직전 절의 꼬리)을 봐야 한다.
3. **고정 대기는 이런 창을 못 닫는다.** 오버슈트(`1.02`)가 있는 연출에서는 «넉넉히 기다리기» 가
   반대 방향의 같은 결함을 만든다. 물어야 할 것은 시각이 아니라 **정착 여부**다.
4. **공용 부품을 빌릴 때도 «그 부품이 내 창을 닫는가» 를 실측한다.** `settle291` 사다리를 그대로
   빌렸다면 g200·g300 을 **새로 빨갛게** 만들고도 «공용 부품을 재사용했다» 고 적을 뻔했다.
