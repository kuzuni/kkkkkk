## 1. 증상 — 등재문보다 심했다

등재문(297 이 곁가지로 관측)은 «4회 중 1회 빨갛다» 였다. 이 세션에서 **고치기 전 4회를 돌렸더니 4회 다 빨갰다**:

| 회 | 결과 | 빨간 자리 |
|---|---|---|
| 1 | `VERIFY262 41/42` | `equip` |
| 2 | `VERIFY262 40/42` | `skill` · `cos` |
| 3 | `VERIFY262 41/42` | `cos` |
| 4 | `VERIFY262 40/42` | `skill` · `pet` |

즉 **`skill` 전용이 아니다**(등재문의 «§7 의 skill 만 잡힌다» 는 관측 표본이 작았던 것이다) — 네 계열
(`skill`·`equip`·`pet`·`cos`)에 **아무거나 걸린다**. 그리고 어긋남은 언제나 **정확히 한 칸**이었다:

```
lv: «Lv. 6» vs «Lv. 7» / pb: «99967/10» vs «99957/11» / own: «공격력 +4.2%» vs «공격력 +4.5%»
```

`live` 쪽이 **항상 한 칸 뒤**다. 한 번도 반대 방향이 없었다 — 표기가 «틀린» 것이라면 방향이 섞여야 한다.

## 2. 원인 — 값이 아니라 **두 읽기 사이에 낀 틱** (계측 부패)

고치기 전 §8 은 왕복을 **세 번** 했다.

```js
await page.mouse.down();
await page.waitForTimeout(800);
const live = await face(page);   // ← 왕복 ①
await page.mouse.up();           // ← 왕복 ②  (이 사이에 upHoldTick 이 한 번 더 돈다)
await page.waitForTimeout(200);
const full = await face(page);   // ← 왕복 ③
```

홀드 반복(`upHoldTick`)은 `TR_HOLD_IV0` 에서 시작해 `×TR_HOLD_ACCEL` 로 가속돼 **최소 60ms** 까지 빨라진다
(§4 가 재는 값 그대로다). 800ms 를 누른 뒤라면 이미 최소 간격이다. 그런데 `face()` 읽기와 `mouse.up()` 은
각각 CDP 왕복이라 **60ms 보다 오래 걸릴 수 있다**. 그 틈에 틱이 한 번 더 돌면 `mdLive()` 가 DOM 숫자를
한 칸 올리고, 뗀 뒤의 통짜 재렌더(`o.full`)는 그 «한 칸 더 오른» 상태를 그린다 →
**두 읽기가 서로 다른 상태를 본다.** 표기층은 멀쩡한데 자를 대는 시점이 어긋난 것 —
303·305 와 같은 «간헐 FAIL» 계열(부하에서만 드러나는 계측 부패)이다.

증거 두 가지:
1. 어긋남이 **언제나 정확히 1레벨, 언제나 live 가 뒤** — 틱 한 번이 낀 모양과 정확히 같다.
2. 계열을 안 가린다 — `skill` 만의 표기 코드 문제라면 `equip`·`pet`·`cos` 가 같이 빨갈 이유가 없다.

## 3. 고친 것 — 읽기·정지·읽기를 **한 번의 evaluate 안**으로

등재문의 «처방 방향» 둘 중 **후자**(297 이 `verify203` [10]·`verify210` [I] 에서 쓴 방식)를 골랐다.
전자(«`upHold === null` 을 상태 전이로 기다린 뒤 잰다»)는 이 자리에선 못 쓴다 — 여기서 재야 하는 `live` 는
**멎기 «전» 의 홀드 중 표기**라서, 멎기를 기다리면 재야 할 상태 자체가 사라진다.

```js
const faceBoth = page => page.evaluate(() => {
  const read = () => { /* .sk-gr b · .sk-lv b · .sk-pb i(width) · .sk-pb b · .sk-ct .vl .nt b · .sk-db p · .sk-ow .v b */ };
  const held = typeof upHold !== 'undefined' && upHold !== null;
  const live = read();
  upHoldStop(false);        // 제품의 «뗌» 과 같은 경로 → h.end(h.n,false) → o.full(n) = 통짜 재렌더
  const full = read();
  return { held, live, full };
});
```

세 단계가 **한 콜스택 안에서 동기로** 끝나므로 `setTimeout` 틱이 낄 자리가 없다(JS 단일 스레드).

지킨 것 두 가지:
* **게이트용 샛길을 새로 파지 않았다.** 정지는 제품이 `pointerup` 에서 타는 바로 그 함수
  (`upHoldStop(false)` → `h.end(h.n, false)` → `o.full(n)`)다. 뒤이은 `mouse.up()` 은 `upHold` 가 이미
  `null` 이라 no-op 으로 지나간다(§5 의 «뗌» 판정과 충돌하지 않는다).
* **판정을 무디게 만들지 않았다.** «홀드가 이미 멎은 뒤에 재서 대조가 헛도는» 조용한 통과를 막으려고
  `held`(읽는 순간 `upHold !== null`)를 같이 돌려받아 계열마다 **따로 채점**한다. 그래서 판정 수가 42 → **46** 으로 늘었다.

«그냥 통과하는 게이트» 가 된 게 아님을 본다. 제품의 `mdLive`(홀드 중 «숫자만» 갱신하는 공용 라이터)를
**페이지 안에서만** 일부러 갈라놓고(`lv` 에 `✱` 를 덧붙인다) 같은 대조를 돌린다. `index.html` 은 안 건드린다.


[B] 가 이번 수정의 핵심 증거다: **두 읽기가 같은 레벨(6)을 본다** — 예전이라면 여기서 `6 vs 7` 이 났다.
숫자는 같고 «일부러 넣은 오염» 만 갈렸다 = 틱은 사라졌고 판정은 살아 있다.
