«상시 FAIL» 로 등재됐지만 실제로는 **뜨고 지는 FAIL** 이다. 수정 전 4회 연속 실행 결과 **3 FAIL / 1 PASS**,
그리고 FAIL 할 때마다 어긋난 값이 매번 달랐다(212.2 / 210.1 / 208.6 / 210). 이 «값이 매번 다르다» 가
등재 당시 «애니메이션 위상» 을 의심하게 만든 근거였고, 그 방향 자체는 맞았다.

## 2. 등재된 원인은 틀렸다

PROGRESS 136 은 이렇게 적혀 있었다:

> 122 가 붙인 링 펄스가 `:not(.lack)` 이라 **충분 상태에만** 걸려서, 충분 쪽 rect 가 애니메이션 위상만큼 흔들린다.

그 펄스는 이것이다:

```css
.shp-card .cbtn.b1:not(.lack){animation:jz122Ring calc(.9s * var(--jz-per)) ease-out infinite}
@keyframes jz122Ring{
  0%{box-shadow:0 0 0 0 rgba(83,230,250,…)}
  70%{box-shadow:0 0 0 calc(22px * var(--jz-amp)) rgba(83,230,250,0)}
  100%{box-shadow:0 0 0 0 rgba(83,230,250,0)}}
```

**`box-shadow` 는 `getBoundingClientRect` 를 1px 도 바꾸지 못한다.** 레이아웃에도 페인트 상자에도
안 들어간다. 즉 이 처방(«링을 정지시킨다» / «transform 을 box-shadow 로 옮긴다»)은 **둘 다 무효**였다 —
②는 이미 box-shadow 였고, ①을 해도 rect 는 그대로 흔들렸을 것이다.

결정적 반증이 하나 더 있다: **`.b1` 에만 걸린 펄스인데 `.b2`·`.b3` 도 같이 어긋났다.**

## 3. 진짜 원인 — 60 `jzStagger` 의 카드 등장 연출

세 버튼의 어긋남에서 배율과 원점을 되짚으면 셋이 **같은 배율·같은 원점**을 공유한다:

| 버튼 | 정지값 | 흔들린 값 | 배율 | 역산 원점 |
|---|---|---|---|---|
| `.b1` 무료 | `770,309,200,98` | `772.3,308.2,202,99` | 1.0100 | x≈540 · y≈387 |
| `.b2` 10회 | `526,425,208,127` | `525.9,425.4,210,128.2` | 1.0097 | x≈537 · y≈383 |
| `.b3` 30회 | `767,425,206,127` | `769.2,425.4,208,128.2` | 1.0097 | x≈540 · y≈383 |

원점 (540, 385) 는 **첫 `.shp-card` 의 중심**이다(앱 폭 1080 → 가운데 정렬 카드의 중심 x = 540).
버튼이 아니라 **카드가 통째로 배율을 먹고 있었다.**

진단기(`getAnimations()` 를 조상 사슬로 훑는 일회용 스크립트)로 현행범을 잡았다:

```
rich  t=400 525.99,425.01,208.07,127.05 | running=41
         DIV.shp-card jz-st | none | jzSt@249/running      ← 이것
lack  t=400 526,425,208,127             | running=32
         (jz-st 없음)
```

범인은 60 쥬시 모듈의 카드 스태거다:

```css
.jz-st{animation:jzSt .2s linear both;animation-delay:var(--jzd,0ms)}
@keyframes jzSt{0%{scale:.94;opacity:0;…} 62%{scale:1.02;…} 100%{scale:1;opacity:1}}
```

`jzOpen()` → `jzStagger()` → `jzStagGo()` 가 카드마다 `--jzd = 60 + i×25ms` 를 주고 `.jz-st` 를 붙인다.
**`scale:.94 → 1.02 → 1`** 이라 도는 동안 카드 안의 모든 rect 가 카드 중심을 원점으로 배율을 먹는다.

### 왜 «충분» 쪽만 흔들렸나 — `.lack` 과는 아무 상관이 없다

게이트의 두 패스가 팝업을 여는 방식이 다르다:

| 패스 | 호출 | 팝업 상태 | `jzOpen` | 스태거 |
|---|---|---|---|---|
| 충분 `rich10` | `open10(99999,2)` | **닫혀 있다가 열림** | 실행 | **돈다** |
| 부족 `lack10` | `open10(0,0)` | 이미 열려 있음 | 건너뜀 | 안 돈다 |

`openShopPage()` 는 닫힌 상태에서만 `jzOpen()` 을 태운다. 그래서 첫 패스만 연출 위상을 탄 채로
측정됐고, 두 번째 패스는 정지 상태였다. **두 패스의 `.lack` 차이가 아니라 «연출 위상» 차이**다.

### 그러면 왜 «상시» 가 아니었나

`.b2` 가 든 첫 카드(i=0)의 스태거는 `60 + 200 = 260ms` 에 끝난다. 게이트의 고정 대기는 400ms 라
**원래는 여유가 140ms 있었다.** 그런데 바로 앞에서 `#app` 스크린샷 4장을 찍기 때문에, 부하에 따라
연출 시작이 150ms 넘게 밀린다(진단에서 t=400 인데 `jzSt@249`, 즉 시작이 151ms 밀렸다). 밀린 정도가
회차마다 달라서 **어떤 실행은 통과하고 어떤 실행은 실패**했다.

> 126 이 «서체 교체 뒤 편차가 0.4px → 2.7px 로 커졌다» 고 본 것도 서체와 무관하다 —
> 편차 크기는 «측정 순간의 연출 진행률» 이 정하고, 그건 실행마다 무작위다.

## 4. 고친 자리 — 제품이 아니라 게이트

카드가 등장하며 배율을 먹는 것은 **60·122 가 의도한 연출**이고 정지하면 정확히 `scale:1` 로 수렴한다.
102 가 재려는 «재화가 부족하든 충분하든 버튼 기하가 같다» 는 **레이아웃 불변식**이므로,
연출이 도는 중에 재는 것 자체가 틀렸다. 그래서 `tools/verify102.js` 안에서만 고쳤다.

**고정 대기를 늘리는 처방은 쓰지 않았다.** 시작 시각이 부하를 따라 밀리므로 어떤 상수를 골라도
언젠가 다시 깨진다. LESSONS 120 의 처방(«고정 대기 대신 기하 정지 폴링»)을 그대로 따랐다.

```js
const settle = (p, sels) => p.evaluate(async ss => {
  const rd = () => ss.map(s => { … b.left/top/width/height 를 소수 3자리로 … }).join('|');
  let prev = rd(), same = 0;
  while (performance.now() - t0 < 4000) {
    await raf();
    const cur = rd();
    if (cur === prev) { if (++same >= 4) return { ok:true, … }; }
    else { same = 0; prev = cur; }
  }
  return { ok:false, … };
}, sels);
```

- **재려는 rect 자체가 4프레임(≈64ms) 연속 동일**해질 때까지만 기다린다. «어떤 애니메이션이 도는가» 를
  세지 않으므로 무한 루프 연출(`jz122Ring`·`jz122Breathe`·`.cart` 부유 등)에 걸려 영영 못 빠져나오는 일이 없다 —
  그것들은 rect 를 안 움직이니까 폴링이 그대로 수렴한다.
- 반대로 **앞으로 rect 를 움직이는 무한 연출이 붙으면 4초 뒤 «수렴 실패» 로 드러난다.** 그래서 수렴 여부를
  `12/10 기하 정지 폴링 수렴` 항목으로 채점표에 남겼다(수렴에 걸린 ms 도 같이 찍는다).
- 10·12 **네 패스 전부**(충분·부족)에 붙였다. 12 는 지금 통과하지만 같은 함정 위에 있다.

실제 수렴 시간: 12 충분 59ms · 12 부족 60ms · **10 충분 226ms** · 10 부족 131ms.
10 충분만 유독 긴 것이 바로 «400ms 고정 대기 뒤에도 스태거가 남아 있었다» 는 증거다.

## 5. 음성 테스트 — 폴링이 게이트를 무력화하지 않는다는 증명

기하 정지 폴링은 자칫 «항상 통과하는 게이트» 를 만든다. 그래서 같은 경로가 **진짜 어긋남은
그대로 잡는지** 를 양방향으로 확인하는 항목 3개를 신설했다.

| 항목 | 방법 | 결과 |
|---|---|---|
| 136 음성 · 3px 어긋남을 잡는다 | `.cbtn.b2` 에 `margin-left:3px` → settle → 재측정 | `529,425,208,127` ≠ `526,…` ✔ |
| 136 음성 · 어긋남이 정확히 3px(반올림 아님) | 위 값의 left 차 | `3` (±0.01) ✔ |
| 136 음성 · 되돌리면 원래 기하 | 인라인 스타일 제거 → settle → 재측정 | `526,425,208,127` ✔ |

즉 폴링은 «값을 굳히는» 것이 아니라 «연출이 끝난 뒤의 레이아웃» 을 읽을 뿐이고, 소수점도 안 죽인다.
