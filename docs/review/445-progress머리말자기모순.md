## 1. ⚑ 본체 — 이건 이론이 아니라 **관측된 피해**다

이 세션은 지시서 [-1] 의 티어 스캔으로 미선점 작업을 골랐다. 383 행이 이렇게 읽혔다:

```

```

그래서 `node tools/claim.js 383` 로 **선점했다.** 착수 직후 `docs/review/383-*.md` 를 읽고
1회차(2026-08-29, sess-0500-24433 워커 D)가 이미 끝냈음을 알았고,
`node tools/verify383.js` **42/42 PASS**(§R 되돌림 4항 포함)로 그 완료문이 사실임을 확인했다.

**표의 구현 칸은 처음부터 `✅ **완료(2026-08-29 …)`** 였다. 빠진 것은 비고 머리말 한 칸이고,
티어 스캔이 읽는 칸이 하필 그 칸이다.

388 이 세운 규칙은 «구현 칸 · 루프 횟수 · 비고 머리말 **셋을 같이** 고쳐라» 였고,
388 이 심은 자(`verifyProgress` §2)는 그중 **①이 비어 있는 행만** 본다:

```js
const NOT_YET = /\|\s*(?:–|—|-|미착수\.?|)\s*\|\s*(?:–|—|-|)\s*\|[^|]*\|\s*…(미착수|등재만|착수 전)/;
                  ^^^^^^^^^^^^^^^^^^^^^^^^ 구현 칸이 «–» 이어야 한다
```

⇒ **③ 만 안 고친 행은 자가 한 건도 안 센다.** 388 이 닫은 것은 사고의 절반이었다.

### 2-1. 곁가지로 드러난 것 — 337·382 는 등재문이 **화면에서 사라져 있었다**

두 행은 비고 안에 **escape 안 한 `|`** 가 있어 비고가 두 칸으로 쪼개져 있었다:

- **382**: 8칸(`… | 완료문 | 등재문 |`) — 표 머리가 7칸이라 GitHub 은 **8번째 칸을 렌더에서 버린다.**
- **337**: 7칸이지만 **측정표 칸이 통째로 빠져** 한 칸씩 밀려 있었다
  (측정표 칸에 구현문 · 구현 칸에 점수 · 점수 칸에 «3/5» · 횟수 칸에 완료문 · 비고에 등재문).

즉 두 행은 **사람이 보는 표에서도 틀려 있었고**, 티어 스캔은 그 밀린 마지막 칸을 비고로 읽었다.
⇒ 등재문 본문은 **한 줄도 안 지우고** 비고 한 칸으로 합쳤다(`<br>**↓ 아래는 등재문(보존).**`),

## 3. 처방 — 머리말 축을 **단독 축**으로 세웠다

등재문의 후보 ⓐ 를 택했다. ⓑ(«`done(<ID>)` 이력이 있으면 머리말만으로 빨갛게»)는
**얕은 클론에서 창이 10건뿐**이라 ⓐ 보다 약하다 — §1 머리말이 그 한계를 이미 적어 뒀다.

```js
const HEAD_NOT_YET = /^\s*(?:\*\*)?\s*(?:←\s*)?(?:\(등재문[^)|]*\)\s*)?(미착수|등재만|착수 전)/;
function tailHead(line) { /* 마지막 비어 있지 않은 칸의 머리말 */ }
```

판정은 **축 둘**이 됐고 순서가 중요하다:

```js
const y = NOT_YET.exec(line);          /* ⓐ 구현 칸까지 등재 상태 (388) */
if (y) { …kind:'impl'; continue; }
const t = tailHead(line);              /* ⓑ 구현 칸은 채웠는데 머리말만 (445) */
if (t) …kind:'tail';
```

**옛 관행 행은 두 축에 다 걸린다.** 겹치면 **구체적인 쪽(`impl`)이 먼저 대야** 한다 —
순서가 바뀌면 tail 축이 impl 축을 가려 «구현 칸이 비었다» 는 진단을 영영 못 낸다.
(§1 의 두 자가 «정확 되돌림 → 표지 회귀» 순서를 지키는 것과 같은 이유이고,
그 자리는 388 머리말이 «앞의 자가 뒤의 자를 가리면 뒤의 자가 한 번도 안 돈다» 로 적어 뒀다.)

진단문도 갈랐다 — tail 축은 «구현 칸은 채웠는데 **비고 머리말**이 … (세 칸 중 ③ 만 안 고친 꼴)»
로 말하고, 처방 안내에 «escape 안 한 `|` 가 있으면 뒤 칸이 렌더에서 사라진다» 한 줄을 붙였다.

## 4. 무르게 풀지 않았음을 세 겹으로 못박았다

### §R3 — 되돌림 시험 (신설)

**구현·점수·횟수는 완료 그대로 두고 비고 머리말만** 등재 상태로 되돌린 사본을 자에게 물린다.
표본은 리터럴로 안 박고 **표에게 묻는다**(«완료 표지가 있고 머리말은 정상인» 행 407건 중 앞 3건 —
379 가 리터럴 표본으로 한 번 물린 선례).

각 표본마다 셋을 묻는다:
1. 사본이 **옛 축으로는 안 걸린다**(`!NOT_YET_SHAPE`) — 이게 445 의 사각이었음을 사본 자신이 증명한다
2. 자가 빨갛다(종료 코드 1)
3. **머리말 축으로** 그 ID 를 지목한다(진단이 구체적이다)

### §R 보강 — «어느 축으로 잡았나» 까지 묻는다

기존 §R(옛 관행 되돌림)에 «`구현 칸이 «–»` 로 지목하는가» 항을 더했다.
이게 없으면 두 축이 겹치는 자리에서 tail 축이 impl 축을 가려도 초록이다.

### §N3 — 음성항 (신설)

**완료 표지가 없는 진짜 미착수 행**(418·419·425·435~445 등 13건)은 머리말이 «미착수» 여도
안 잡혀야 한다. 이 축은 머리말만 보므로 «완료 표지 없음» 한 조건이 그 행들을 지킨다 —
그 조건이 무너지면 **표의 미착수 행 전부가 빨개지는 항등식**이 된다.
표본은 여기서도 표에게 묻고 하한(≥3)을 건다.

⚠ 기존 §N 의 ««미착수» 를 **인용**만 하는 완료행 23건은 조용하다» 도 그대로 초록이다 —
넓힌 것은 «머리말» 이지 «본문 어딘가» 가 아니다.

## 6. 교훈 (LESSONS 445)

1. **규칙이 셋을 요구하면 자도 셋을 봐야 한다.** 388 은 «세 칸을 같이 고쳐라» 를 세우고
   자에는 ①의 상태만 넣었다. 규칙과 자가 어긋나면 **지키는 쪽이 더 번거로운 규칙은 진다**
   (290 이 선점에서 같은 결론을 냈고, 그래서 claim.js 는 «덮어쓸 방법 자체를 없앴다»).
2. **자의 사각은 «빨강 0건» 으로 보인다.** 수리 전 트리에서 §2 는 초록이었고 표에는 5건이 있었다.
   초록을 «없다» 로 읽지 말고 **그 자가 무엇을 못 보는지** 를 같이 적어라
   (§1 이 얕은 클론 창을 ⚠ 로 찍는 것과 같은 정직성).
3. **워커의 스캔이 읽는 칸을 자도 읽어야 한다.** 티어 스캔은 `$(NF-1)` 을 본다 —
   그래서 자도 «마지막 비어 있지 않은 칸» 을 봐야 하고, 그 덕에 표를 넘쳐
   **렌더에서 사라지던 칸**(337·382)까지 같이 걸렸다.
4. **축을 더할 때는 «어느 축으로 잡았나» 를 게이트가 물어야 한다.** 두 축이 겹치는 자리에서
   순서가 뒤집히면 옛 축의 진단이 조용히 죽는다 — 그것도 초록으로 보인다.
