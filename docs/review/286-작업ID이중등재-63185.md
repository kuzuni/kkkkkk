## 3. 재발 방지 — 281 의 규칙이 «마지막 행» 이면 이번 정리가 곧바로 규칙을 깬다

281 이 명문화한 문장은 «표의 **마지막 번호** + 1» 이었다. 그런데 이번에 옮긴 287·288 은
원래 표 **한가운데**(63 자리 · 185 자리) 있던 행이다. 그대로 두면 다음 워커가 표 끝 행 «286» 을 읽고
**287 을 새 번호로 골라 충돌**한다 — 정리가 새 중복을 만드는 자기모순이다. 두 갈래로 막았다:

1. **행을 표 끝(286 뒤)으로 이동**시켜 «마지막 행» 과 «가장 큰 번호» 가 같은 답을 내게 했다.
2. 규칙 문장을 **«이미 쓰인 번호 중 가장 큰 것 + 1»** 로 고치고(`docs/PROGRESS.md` 병렬 세션 규칙 1 ·
   `docs/claims/README.md`), 판정을 눈이 아니라 한 줄 명령으로 못박았다:

```
awk '/^\| [0-9A-Z]/{split($0,a,"|");gsub(/^ +| +$/,"",a[2]);print a[2]}' docs/PROGRESS.md | sort -n | tail -1   # 최댓값
awk '/^\| [0-9A-Z]/{split($0,a,"|");gsub(/^ +| +$/,"",a[2]);print a[2]}' docs/PROGRESS.md | sort | uniq -d      # 중복(비어야 한다)
```

## 6. 교훈

1. **번호를 옮기면 «번호를 고르는 규칙» 도 같이 검산하라.** 281 의 «마지막 행 + 1» 은 그 시점엔 참이었지만
   (옮긴 행이 마침 표 끝에 있었다) 이번 정리로 **거짓이 됐다**. 정리 작업은 자기가 만든 새 상태에서
   규칙이 여전히 성립하는지를 마지막에 한 번 더 봐야 한다.
2. **«둘 중 뭘 옮기나» 는 등재 순서가 아니라 «굳은 넓이» 로도 검산된다.** 63 은 둘이 일치했지만
   (뒤 등재분 = 자산 적은 쪽), 일치하지 않았다면 순서만 보고 옮겼을 때 참조 수십 곳이 깨진다.
   옮기기 전에 양쪽의 파일·주석·인용을 **세어 보는 것**이 5분이다.
3. **앞 세션이 «임시 규약» 으로 버티고 있으면 그것도 이 작업의 범위다.** LESSONS 의 `185넉백-①` 은
   번호를 못 옮기는 워커가 만든 우회로였다. 번호가 갈린 뒤에도 우회로를 남기면 «185넉백» 이라는
   세 번째 이름이 영구히 남는다.
