### 반증까지 갔다가 **비평가가 맞았던 것** — 카드 radius

측정표는 원호 피팅으로 `radius ≈ 34` 라고 적었는데 **틀렸다.** 두 가지로 교차 검증했다:
- 카드 **상단 행(dy=0)에서 직선이 시작하는 x = 60** → `60 − 36 = 24`
- 검정이 **최좌단 x=36 에 도달하는 행 dy = 24**
둘 다 `r = 24` 로 자기일관적이다. → **곡선은 «상단행 직선 시작점» 으로 재라. 원호 피팅은 AA 에 약하다.**

### 채택 — 카드 radius 정오표 (**네 번 만에 확정**)

| 출처 | 값 | 방법 |
|---|---|---|
| 측정표 | 34 | 원호 피팅 (dy 8~25) |
| 1회차 B | 24 | 최좌단 도달 dy |
| 2회차 C | 32 | 코너 잘림 «면적» 역산 |
| **자가 최소자승** | **30** | 좌상단 28행 inset 을 원 모델로 최소자승 (**rms 0.46**) |

`inset(dy) = r − √(r²−(r−dy)²)` 로 맞추면 r=30 이 rms 0.46, r=24 는 **3.01**, r=34 는 1.77 이다.
**dy=0 행은 JPEG 부분행이라 반드시 제외**해야 한다(이걸 넣으면 r 이 24 로 읽힌다 — 1회차 B 의 오류).
CSS 는 5px 테두리·AA 때문에 30 을 주면 28 로 렌더돼 **32** 로 줬고, 실측 r=30 으로 ref 와 Δ0.

> **교훈: 곡선은 «한 점» 이 아니라 «전 구간 최소자승» 으로 재라.** 이 화면에서만 세 가지 단일점
> 방법(원호 피팅·최좌단 도달·면적 역산)이 전부 다른 답을 냈다.

## 이번에 잡은 함정 3개 (다른 화면에서도 재발한다)

   `padding-bottom = (본문아래여백 91 − 배지돌출 8) + 하단크롬 15 = 98` 이 맞다.

2. **카드 «면색» 마스크로 아이콘 잉크를 재면 안쪽 밝은 림이 통째로 섞인다.**
   면색만 빼고 스캔하니 잉크가 87×105 로 나왔는데, **림색까지 함께 제외**하니 실제로는 63×64 였다.
   림이 6px 짜리 별도 색이라 «면과 Δ>55» 조건에 전부 걸린 것이다.
   더해서 **개수 배지의 검정 외곽선(9px)이 카드 안쪽까지 올라와** 잉크 높이를 88 로 부풀렸다 —
   `max(RGB)<40` 을 같이 제외해야 정상값(70)이 나온다.

3. **`border-radius` 가 큰 요소는 모서리 근처 열에서 세로 스캔하면 안 된다.**
   카드(radius 34)를 좌단에서 24px 떨어진 x=60 열로 세로 스캔했더니 테두리가 5px 이 아니라
   4px 로, 카드 높이도 157 이 아니라 154 로 읽혔다. **아직 원호 구간**이기 때문이다.
   DOM `getBoundingClientRect` 로 재니 정확히 157 이었다. 원호 밖(중앙 근처) 열을 골라야 한다.

## 구현 메모 (다음 담당자용)

- 버튼 3개는 **10 상점 소환 탭이 만든 `freeLeft()` / `SHOP_FREE` / `doSummonFree()` / `summonCost()` 를
  그대로 재사용**한다. 저장 구조를 건드리지 않았다(KEY 유지).
- 레퍼런스 카드 등급색은 **초록 7 / 갈색 2 / 파랑 1** 3종뿐이다. 실측 3종을 `SUM_CARD[0..2]` 에 그대로 넣고
  상위 3등급(영웅·전설·신화)은 같은 «면 + 밝은 림» 명암 구조로 확장했다 — **레퍼런스에 표본이 없다.**
  기존 `GRADE.bg/.c` 는 어두운 남색 계열이라 이 화면에는 못 쓴다(다른 화면 것은 건드리지 않았다).
- **같은 아이템이 여러 번 나오면 칸을 늘리지 않고 개수로 합친다.** 레퍼런스에 개수 배지가 있는 이유가
  이것이다. 그래서 10연을 해도 카드가 10칸이 아닐 수 있다.
- **30연은 5행(837px)이라 우리 프레임의 패널↔버튼 100px 안에 못 들어간다.**
  09 처럼 «앞 N칸만 표시» 로 자르지 않고 **레퍼런스 케이스(2행 335px)를 픽셀 그대로 두고
  초과분만 스크롤**하도록 했다. 스크롤바는 숨겼다.
