## 3. 처방 — 세 가지 (등재문 권장 순 그대로)

### ① 자: `tools/verifyProgress.js` **§5 추적 파일 급감** 신설
- **무엇을 보나**: `merge-base(origin/main, HEAD)` → **작업 트리**의 diff 한 벌.
  커밋했지만 아직 push 안 한 것 + staged + unstaged 가 한꺼번에 들어온다(사고의 모양 그대로 · [B5] 가 커밋 전에도 걸림을 못박는다).
- ⚑ **기준이 `origin/main` 이 아니라 merge-base 인 것이 이 절의 핵심**이다. 워커 넷이 상시 push 하는 저장소라
  `origin/main` 을 기준으로 잡으면 **남이 방금 올린 5,000줄**이 내 쪽 「−5,000」 으로 읽혀 매번 헛빨강이 난다.
  헛빨강을 내는 자는 한 번 꺼지면 끝이라 이것은 편의가 아니라 **생존 조건**이다(`verify733` [C2]).
- **대상은 전 추적 파일**(공용 파일 목록이 아니다). 사고는 자리를 옮겨 가며 난다 —
  571 = PROGRESS·LESSONS · 363 = UI-REFERENCE · 733 = LESSONS. 목록으로 막으면 목록 밖 다음 파일에서 그대로 재발한다.
- **빠져나가는 문은 «말하는 문»**: `--allow-shrink <path>`(여러 번 가능). 밝힌 경로는 «관찰» 로만 찍힌다.
  ⚠ 사고의 본질은 «지웠다» 가 아니라 **«아무도 모르게 지웠다»** 이므로 막는 것이 아니라 소리 없이 지나가지 못하게 하는 것이 이 절의 일이다.
- **종료 코드에 반영**했다([A3]) — 경고만 찍고 코드 0 이면 push 게이트가 아니다(604 가 축 ⓓ 에서 겪은 그대로).

### ② 지시서 [4]·[6] 에 add 규약 명문화
지금까지 «`git add -A` 금지» 는 **§4 가 빨개진 한 경우에만** 적혀 있었다. 그것을 상시 규약으로 올렸다 —
회차 커밋은 `git add -- <경로들>` 로 **이름을 적어** 담고, `git status` 에 내 작업과 무관한 파일이 보이면 **담지 말고 그대로 둔다**.

### ③ 복구 절차 한 줄 ([4])
`git log --oneline -- <파일>` → `git checkout <그 앞 sha> -- <파일>` → `git add -- <파일>`,
그리고 그 사이 그 파일을 건드린 커밋이 없었는지 `git log -- <파일>` 로 확인(새 내용을 묻지 않기 위해).
