## §0 등재문 대조 — «2곳» 이 아니라 **3곳** 이었다

등재문은 «피해 경로 9개 중 kx/ky 를 실제로 넘기는 곳 2곳(폭발 · 회전검), 나머지는 이미 `0,0`» 이라고 적었다.
실측하니 **투사체(shots) 경로가 하나 더** 있었다 — 등재문이 «나머지» 로 묶은 쪽에 섞여 있었다.

| # | 경로 | 옛 넉백 인자 | 크기(초기 속도) |
|---|---|---|---|
| ① | 폭발 `areaDamage()` | `ex*0.4, ey*0.4` | 반경 190 기준 최대 **76px/s** (중심에서 멀수록 큼) |
| ② | 회전검(지속 orb) | `Math.cos(a)*70, Math.sin(a)*70` | **70px/s** 고정, 칼날 진행 방향 |
| ③ | 투사체 `shots` 명중 | `b.vx*0.05, b.vy*0.05` | 투사체 속도의 5% (표창 772px/s → **39px/s**) |

나머지 6곳(즉발·연쇄 번개·장판·검기 등)은 등재문대로 이미 `0, 0` 이었다.

**172 의 실측과도 맞물린다** — 172 는 «넉백 평균 |k| 9.5px/s = 추격 속도의 8%, 10프레임 반감» 을 재고
«172 의 원인은 아니다» 라고 결론냈다. 그 9.5px/s 가 이 세 문에서 나오던 값이다.

## §1 고친 것 — 인자를 «0 으로» 가 아니라 **문 자체를 없앴다**

등재문이 준 두 갈래 중 **후자**(«`hitEnemy` 에서 kx/ky 인자 자체 폐기 + `e.kx/ky` 필드·감쇠 코드 정리»)를 골랐다.
다른 사용처가 없었기 때문이다(`grep '\.kx\b|\.ky\b'` = 이동 적분·감쇠·`hitEnemy` 4줄이 전부).
값만 0 으로 넘기면 «다음에 누군가 다시 채워 넣을 수 있는 문» 이 남는다.

| 자리 | before | after |
|---|---|---|
| `hitEnemy()` 시그니처 (~15668) | `function hitEnemy(e, dmg, crit, kx, ky)` · `e.kx += kx\|\|0; e.ky += ky\|\|0;` | `function hitEnemy(e, dmg, crit)` — 넉백 줄 삭제 |
| 폭발 호출부 (~15776) | `hitEnemy(e, d, crit, ex*0.4, ey*0.4)` | `hitEnemy(e, d, crit)` |
| 회전검 호출부 (~16251) | `hitEnemy(e, …, crit, Math.cos(a)*70, Math.sin(a)*70)` | `hitEnemy(e, …, crit)` |
| 투사체 호출부 (~16516) | `hitEnemy(e, dmg, crit, b.vx*0.05, b.vy*0.05)` | `hitEnemy(e, dmg, crit)` |
| 나머지 5곳 | `hitEnemy(…, 0, 0)` | 잉여 인자 `, 0, 0` 제거 (문이 없어졌으므로 표기도 맞춘다) |
| 이동 적분 (~16353) | `e.x += ((ax/al)*spd + e.kx)*dt` · `e.kx *= Math.pow(0.02, dt)` (2줄) | `e.x += (ax/al)*spd*dt` — 넉백 항·감쇠 삭제 |
| 적 생성 (~15122 `makeEnemy` · ~18964 승급 수호자) | `kx:0, ky:0` | 필드 삭제 |

**지운 것은 «이동» 뿐이다.** 피격 반응(`e.fx = 0.12` 피격 플래시 · `hitRing()` 피격 링 · `impactFx()` 스파크)은
한 줄도 안 건드렸다 — 게이트 [2] 가 «피격 플래시 n회» 로 이것을 매 경로마다 못박는다.

**밸런스 불변**: 피해 계산(`e.hp -= dmg`)·판정 반경·쿨다운은 전부 그대로다. 바뀐 것은 적의 **위치**뿐이고,
그마저도 «추격이 되돌려 놓던 것» 이라 DPS 축에는 영향이 없다(V86 46/46 회귀로 확인).

## §2 게이트 `tools/verify185.js` 신설 — 문턱 없는 자

적의 위치를 쓰는 코드는 **한 줄뿐**이다(`e.x += (ax/al)*spd*dt`). 즉 이동 = «추격» + «넉백» 이고,
**추격 항을 0 으로 만들면 남는 이동은 넉백뿐**이다. 하니스가 매 틱 `e.sp = 0` 을 박는다(일반 몹은
`spd = e.sp * (slow?0.55:1)` 이라 그대로 0) — 그러면 **«변위 0.00px = 넉백 없음» 이 산술적으로 동치**가 된다.
눈대중 문턱도, before/after 사이에서 고르는 튜닝도 필요 없다.

상태는 제품이 실제로 쓰는 문(`step(1/60)` · `S.own`/`S.eqSkill` · `makeEnemy`)으로만 만든다(223-③).

## §5 172 재확인 (등재문 «같은 세션 처리 권장»)

등재문은 «185 가 172(보스가 반대편으로 밀림)의 유력 원인 후보» 라 적었지만, **172 는 이미 2026-08-27
sess-0339-16324 이 다른 원인으로 닫았다** — `SOLO_CHASER` 누락(승급 수호자·아레나 도전자에 직진 추격
예외가 안 걸림)이 원인이었고, 그 세션의 별도 실측이 «넉백은 원인이 아니다(평균 9.5px/s = 추격의 8%)» 를
이미 배제해 두었다. 그래서 이번 세션은 **재현이 아니라 회귀**로 처리했다: `verify172` 를 그대로 돌려
세 개체의 정렬·속도가 그대로인지만 봤다. 넉백이 사라지면서 정렬은 오히려 **1.000 으로 붙었다**
(172 당시 after 0.999/1.000/1.000 → 이번 1.000/1.000/1.000 — 남아 있던 8% 성분이 빠진 것).

> ⚠ `verify172` 의 문턱 주석은 «직진 추격이면 **넉백(실측 평균 9.5px/s)만큼만** 깎인다» 라고 적혀 있다.
> 185 이후 그 항이 0 이 되었으므로 주석의 전제가 한 겹 낡았다. **문턱(0.98)은 안 건드렸다** —
> 남의 구간(172)이고, 넉백이 빠진 방향은 정렬을 **올리는** 쪽이라 게이트가 무뎌지지 않는다.
