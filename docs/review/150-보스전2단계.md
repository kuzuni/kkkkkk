## 1. 150 — 보스는 «안 뜨는» 게 아니라 **다른 스테이지에 있었다**

28 의 설계는 «10의 배수 스테이지 = 보스 **단독** 스폰(일반 몹 0마리)» 였다. 그래서 실제 진행은:

| 스테이지 | 28 설계의 실제 동작 | 주인이 기대한 것 |
|---|---|---|
| 1~9 | 몹 50 → **보스 없이** 다음 스테이지 | 몹 50 → 보스 → 다음 |
| 10 | 몹 **0마리** + 보스만 | 몹 50 → 보스 → 다음 |

둘 다 «몹 50 → 보스 → 다음» 이 아니다. 주인이 본 «보스가 안 뜬다» 는 1~9 구간이고,
10에서는 반대로 **몹이 안 뜬다.**

### 수정 — 한 스테이지를 2단계로

```js
const BOSS_EVERY = 1;                  /* 몇 스테이지마다 보스인가 (지시 = 매 스테이지) */
let bossPend = false;                  /* 이 스테이지의 보스가 아직 안 나왔다 */
const inBossFight = () => bossT > 0;   /* 구: isBossStage() && !S.bossFarm — 파도까지 «보스전» 으로 셌다 */
```

* `spawnStage()` — **언제나 파도부터**. `bossPend = isBossStage() && !S.bossFarm`
* `step()` 클리어 분기에 단계 하나 추가 — 파도가 비고 `bossPend` 면 **`spawnBoss()`**(스테이지는 안 오른다)
* `spawnBoss()` — `killed` 를 0 으로 되돌리고(`stageTotal()` 이 1 이 되므로 진행바가 0/1 → 1/1) `bossT = BOSS_SEC`
* 보스를 잡으면 기존 경로 그대로 `S.stage++`
* `retryBoss()` — 구 코드는 `spawnStage()` 라 **몹 50마리를 다시 돌렸다.** 이제 `spawnBoss()` 로 직행한다

## 2. 그대로 넣으면 **게임이 스테이지 1 에서 막힌다** — 배수를 역산했다

보스가 1/10 에서 매 스테이지가 됐는데 `ETYPE.boss` 는 28 이 «10스테이지에 한 번» 을 전제로 잡은
HP ×22 · 공격 ×22 다. 헤드리스로 신규 세이브를 돌리면:

```
BOSS 1 등장 t=124s → ✗ stage 1 보스 실패 t=142s → 1 스테이지에서 정지(30분 돌려도 stage 1)
```

**18초 만에 죽는다.** 배수를 발명하지 않고 **게임 자신의 정의로 역산**했다(LESSONS 106-1) —
`tools/sim131.js` 의 `BOSS_TGT = BOSS_SEC/2` 「보스가 제한의 절반을 쓰면 빠듯하되 이긴다」.

자동 구매 ON 신규 세이브가 **스테이지 1~10 의 파도를 갓 깬 시점**의 실측:

| HP 배수 H | 처치 시간 (stage 1 → 10) | 판정 |
|---|---|---|
| 22 (군주) | 41 → 88초 | 제한 30초를 처음부터 초과 |
| 8 | 15 → 32초 | 후반이 제한 초과 |
| **5** | **9 → 20초** | **목표 15초를 가운데 둔다 ← 채택** |
| 3 | 5.6 → 12초 | 너무 쉽다 |

| 공격 배수 D | 몇 대 맞으면 죽나 | 판정 |
|---|---|---|
| 22 (군주) | 1.6 ~ 1.9 | **2대에 죽는다** ← 스테이지 1 정지의 원인 |
| 8 | 4.4 ~ 5.2 | 여전히 빠듯 |
| **4** | **8.9 ~ 10.4** | **채택** |
| 3 | 11.8 ~ 13.8 | 여유 |

```js
const BOSS_MILESTONE = 10;                          /* 10의 배수 = 28 의 «군주» 원본 배수 그대로 */
const SBOSS_MUL = { hp:5/22, dmg:4/22, gold:5/20 }; /* 그 사이 = «스테이지 보스» */
```

* 골드도 같은 비율로 낮췄다(×20 → ×5) — «보상 = 위험» 을 깨지 않으려고.
* **다이아**(`250 + stage*25`)는 **군주만** 준다(`!e.sb`). 매 스테이지로 풀면 다이아 수입이 10배가 된다.
* `tk` 는 `'boss'` 그대로 두고 배수만 실어 보낸다 — `e.tk === 'boss'` 판정이 HP 바·처치 연출·BGM 등
  열 곳 넘게 흩어져 있어 새 종류를 만들면 그 전부가 조용히 빠진다.

## 4. 151 — 클리어 문구에 **HTML 태그가 그대로 찍히고 있었다**

```js
let msg = 'STAGE CLEAR!';
if(first) msg += ' ' + curIc('dia') + '+' + d;   // ← 여기
showMsg(msg);
```

**125 이후 `curIc()` 는 이모지가 아니라 HTML 문자열**이다:
`<img class="cic" data-cur-ic="dia" src="assets/ui/cur-dia.svg" alt="">`.
그런데 `showMsg()` 가 그리는 곳은 DOM 이 아니라 **캔버스(`fillText`)** 다. 그래서 최고 기록을 갱신하는
스테이지마다 화면 한복판에

```
STAGE CLEAR! <img class="cic" data-cur-i…
```

가 태그째 찍혔다(`msgFit` 이 폰트를 18까지 줄이고 «…» 로 자르니 더 이상해 보인다).

**바로 위 골드 줄이 이미 답을 적어 뒀다** — 「골드는 58 코인 비행이 보여 주므로 문구에서 뺐다」.
다이아도 같은 규칙으로 문구에서 뺐다(**지급 자체는 그대로**, `fxWatch` 가 `S.dia` 증가를 보고 비행 연출을 쏜다).

### 곁가지 — CLEAR 문구가 0.0초 만에 덮여 있었다

```js
spawnStage();      // ← 내부에서 showMsg('STAGE n')
showMsg(msg);      // ← 'STAGE CLEAR!' 가 그 위를 덮는다
```

순서가 뒤집혀 있어 «STAGE n» 배너는 보이지도 않고 CLEAR 만 남았다. `spawnStage(quiet)` 를 추가해
**스테이지 상승 직후에는 배너를 생략**한다 — 그 자리의 문구는 CLEAR 다. 첫 로드·승급 복귀 등
다른 호출부는 배너를 그대로 띄운다.

검증: 문구 순서 `STAGE 1 → BOSS 1 → STAGE CLEAR! → BOSS 2 → …`, HTML 섞인 문구 **0건**.
