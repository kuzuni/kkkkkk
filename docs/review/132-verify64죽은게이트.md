## 3. 고친 것 3곳

### ① §8 «스탯 훈련 서브탭» → «3종 카드 공통»

폐기된 서브탭 대신, 지금 존재하는 **체력·체력 회복 카드**로 같은 취지를 검사한다.
64 의 반복 강화가 `atk` 카드에만 붙어 있으면 안 된다는 것이 원래 §8 의 뜻이었다.

|---|---|---|
| 1 | 체력 카드 420ms → `S.lv.hp` +2 (단발 1 + 반복 1) | Δhp 2 |
| 2 | 체력 카드를 눌러도 공격력·체력 회복은 안 오른다 | Δatk 0 / Δregen 0 |

| 5 | 체력 카드도 골드 0 → 60 shake(`.jz-sh`) + 강화 없음 | shake true / hp 0 |

### ② 헬퍼에서 폐기 키 제거

- `snap()` : `sp`/`spAtk` → **훈련 3종(`TRAIN_STATS`) 레벨** `atk`/`hp`/`regen` 을 다 본다.
- `reset()` : `S.statStage`·`S.sp*`·`trSub` 대입 삭제, 대신 `hp`/`regen` 초기 레벨을 옵션으로 받는다
  (기본값 `{atk:0, hp:0, regen:0, gold:1e12, qty:1}`).

### ③ §4 가속 검사 — «창 두 개의 개수» → «구매 시각 직접 측정»

옛 검사 `ok('가속: 뒤 600ms 구매수 > 앞 600ms', n2 > n1 - 1)` 는 **구현 문제가 아니라 측정 문제**로
이 컨테이너에서 흔들렸다. 수정 전 원본으로 재현한 실측:

```
앞 6 / 뒤 6      앞 5 / 뒤 5      앞 6 / 뒤 6        ← 항상 «똑같은 수». 여유가 0 이다
앞 6 / 뒤 5      앞 7 / 뒤 6                         ← ±1 지터마다 FAIL (3회 중 1회)
```

원인: 틱마다 `save()` + `renderTrainLive()` 비용 `w` 가 붙어 실측 간격이 `iv + w` 가 된다.
`iv` 가 160→60 으로 줄어도 `w` 가 상수로 얹히니 **«창당 구매 개수» 로는 가속분이 `w` 에 묻힌다.**

그래서 `trainBuy` 를 래핑해 **성공한 구매의 `performance.now()` 를 직접 기록**하고, 간격 자체를 본다
(래퍼는 §4 가 끝나면 원복 — 뒤 절에 영향 없다). 한 번의 실행 «안에서» 비교하므로 기계 속도에 무관하다.

| 검사 | 실측 예 |
|---|---|
| 1.0초 꾹 → 5회 이상 강화 | 6회 |
| 반복 시작 지연 ≈ 350ms (300~560) | 374ms |
| **가속: 마지막 반복 간격(끝 3개 중앙값) ≤ 첫 반복 간격 × 0.85** | 첫 140ms → 끝 77ms |
| 가속 상한: 반복 간격이 55ms 밑으로 안 내려감(최소 60ms) | 최소 73ms |

간격 로그도 같이 찍는다 — `간격(ms): 374 140 130 140 162 111 114 82 73 77 107`.

## 8. 다음 세션에 남기는 것

- 64 의 게이트는 이제 **실제 회귀를 문다**. 훈련 카드 꾹 누르기를 건드리면 `node tools/verify64.js` 로 확인할 것.
- §4 처럼 **«개수 두 창 비교»** 로 타이밍을 검사하는 게이트는 부하가 붙는 순간 여유가 0 이 된다.
  타이밍은 **개수가 아니라 시각**을 재라 — 한 실행 «안에서» 비교되면 기계 속도가 변수에서 빠진다.
- 게이트를 고쳤으면 **회귀를 일부러 주입해 FAIL 이 나는지** 한 번 보라. 안 그러면 «PASS 하는 죽은 게이트» 가
  «FAIL 하는 죽은 게이트» 로 바뀐 것뿐이다(130·132 가 둘 다 이 함정이었다).
