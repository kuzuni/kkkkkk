# 224 — 유물 소환 가격 «고정 100»

> 저장소 주인 지시(2026-08-27): «유물소환 가격 고정값으로 100으로 하자»

## 1. 무엇이 있었나

유물 소환 비용은 그동안 **두 번** 다른 곡선을 탔다.

| 시기 | 식 | 오르는 축 |
|---|---|---|
| 89 (최초) | `800 + 22 × ΣLv` | 유물 레벨 합 |
| 119 (2026-08-26 주인 지시) | `100 + 1 × 누적 소환 횟수`(`S.cnt.sumRelic`) | 소환 횟수 |
| **224 (이번 지시)** | **`100`** | **없음** |

```js
const RELIC_COST = 100;
const relicCost = () => RELIC_COST;
```

- `S.cnt.sumRelic` 카운터는 **계속 센다** — 61 미션·154 가이드가 그 값을 쓰기 때문이다.
  다만 **가격은 그 값을 읽지 않는다**: 수천 번 소환한 구 세이브를 열어도 100 이다.
- 등재 **198**(«유물 소환 시작 가격 — 1 부터»)은 «오르는 곡선» 을 전제한 항목이라 이 지시가 **대체**한다 → PROGRESS 에서 폐기 처리했다.

## 2. 게이트 — 새 파일을 만들지 않고 119 를 옮겼다

`tools/verify119.js` 는 «유물 소환 비용» 이라는 **같은 성질**을 지키는 게이트다. 규칙이 바뀌었다고 게이트를
새로 만들면 같은 성질을 두 파일이 서로 다르게 단언하게 된다 — 162·94 에서 쓴 처리를 그대로 따라
**기대값만 새 규칙으로 옮기고 옛 곡선 2개는 여전히 «부재» 로 잡는다.**

| 항목 | 옛 기대(119) | 새 기대(224) | 실측 |
|---|---|---|---|
| A3 상수 | `RELIC_COST_BASE=100, RELIC_COST_PER=1` | **`RELIC_COST = 100` 하나 · `RELIC_COST_PER` 부재** | ✅ |
| A4 식 | `sumRelic` 기반 | **어느 축도 안 읽는다(상수 반환)** | ✅ |
| A4b (신설) | — | `S.cnt.sumRelic++` 카운터 자체는 살아 있다 | ✅ |
| C 1회 소환 뒤 | 101 | **100** (차감은 정확히 100) | ✅ |
| D 50회 소환 뒤 | 150 · 누적 6,225 | **100 · 누적 5,000** | ✅ |
| E ΣLv 300 + 7회 | 107 | **100** (89 곡선이면 7,400 · 119 곡선이면 107) | ✅ |
| F 홀드 | 예산 353 → 3회 · 끝 103 | **예산 350 → 3회 · 끝 100** | ✅ |
| H 구 세이브 sumRelic 37 | 137 | **100** | ✅ |
| I 누적 12,345회 | 12,445 | **100** | ✅ |

`node tools/verify119.js` → **38/38 PASS**.
`node tools/verify154.js`(가이드 미션 — sumRelic 카운터 사용처) → 42/42 PASS.

## 3. 밸런스 메모

119 가 «던전 1회(유물조각 150~400) = 소환 1~3회» 로 이미 크게 풀어 둔 상태였고, 224 는 거기서
**후반 상승분을 없앤다**. 소환을 오래 돌릴수록 차이가 커지므로(1,000회째 = 구 1,100 → 신 100)
유물 파워가 도달하는 상한이 사실상 «유물조각 수급량» 하나로 정해진다 — 밸런스 패스(199) 때
유물 기여도를 잴 때 이 점을 전제로 재야 한다.
