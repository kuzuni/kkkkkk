## 1. 실측 — 진행바 기하 (#stinfo 프레임 좌표)

CSS 에서 직접 잰 값이다(눈대중 아님. `verify161 §1` 이 매 실행마다 같은 값을 역산해 상수와 대조한다).

| 요소 | CSS | #stinfo 좌표 |
|---|---|---|
| 트랙 `.kbar` | `left:15 top:34 w:410 h:24 r:12` | x **15..425** |
| 채움 `.kbar>i#prF` | `left:6 top:6 h:12 max-width:398` | x **21** 에서 시작, 최대 **398** 뻗어 x **419** |
| 시작 노드 `.n1` | `left:17 w:48 h:48` (노랑 40 + 검정 테 4) | 중심 x **41** |
| 중간 노드 `.n2` | `left:200 top:26 w:40 h:40` | 중심 x **220** |
| 보스 해골 `.kboss` | `left:379 top:5 w:82 h:82` | 중심 x **420** |

→ 선단이 중간 노드 **중심**에 닿는 진행률 = `(220 − 21) / 398` = **정확히 0.5**.
소스에는 `const KBAR_W = 398, KNODE2_AT = (220 − 21) / KBAR_W` 로 **역산식 그대로** 적었다 —
`0.5` 를 손으로 적어 두면 CSS 만 옮겼을 때 조용히 어긋난다.

## 2. 고친 것 3곳

### ① 점등 — `.n2.on` (CSS)

```css
#stinfo .n2{ … background:#000;border:0;z-index:3}
#stinfo .n2{transition:background-color .18s ease-out,border-color .18s ease-out}
#stinfo .n2.on{background:#FFBF17;border:4px solid #000}
```

- 색·테 두께는 **n1 관례 그대로**(노랑 `#FFBF17` + 검정 테 4).
- `.knode` 가 이미 `box-sizing:border-box` 라 테두리가 붙어도 **외경 Ø40 이 그대로**다 —
  레퍼런스 bbox 를 넘지 않는다(`verify161 §3` 이 점등 전후 폭·높이 불변을 잰다).
- 켜질 때 뚝 바뀌지 않게 색만 .18s transition. 폭·위치는 전이 대상이 아니다(채움은 매 프레임 갱신).

### ② 판정 — `drawHud()` (JS)

```js
let prR;                       /* 진행바 채움 비율(0~1) */
if(promo){ prR = clamp(promo.t/promo.max, 0, 1); … }
else     { const total = stageTotal();
           prR = total > 0 ? clamp(killed/total, 0, 1) : 0; … }
$('prF').style.width = (prR*KBAR_W) + 'px';
$('kn2').classList.toggle('on', prR >= KNODE2_AT);
```

- 승급전(`promo`)·일반 스테이지 **두 갈래가 같은 `prR` 하나**를 쓰게 묶었다. 점등 규칙이 갈래마다 갈리지 않는다.
- `total > 0` 가드 — 예전엔 `killed/total` 이 `NaN` 이면 `width:'NaN%'` 가 나갔다(무효 CSS 라 조용히 무시됐다).

### ③ **덤으로 잡은 실제 버그** — 채움 폭이 3% 앞서 갔다

`#prF` 폭을 `%` 로 주고 있었는데, **절대배치 자식의 `%` 는 부모의 padding box(410)** 를 기준으로 풀린다.
채움이 실제로 이동하는 거리는 **398**(트랙 안쪽 6px inset 양쪽)이라, 진행률이 늘 **410/398 = 1.030 배 앞서** 갔다:

| 진행률 | 예전 선단 x | 바른 선단 x | 오차 |
|---|---|---|---|
| 50% | 226 | **220** | **+6px** (중간 노드 중심을 이미 지나쳐 있었다) |
| 97.1% | 419 (max-width 로 잘림) | 407 | +12px — **97% 에서 이미 꽉 참** |
| 100% | 419 (잘림) | 419 | 0 |

`max-width:398` 이 100% 에서만 오버런을 잘라 주고 있어서 **끝 두 값만 맞고 중간이 전부 틀린** 상태였다.
`161` 이 «선단이 노드에 도달하면» 을 요건으로 걸면서 드러났다 — 노드를 50% 에 두면 **선단은 이미 6px 지나쳐 있다**.
→ 폭을 **px 로** 준다(`prR*398`). `max-width` 는 상한·안전망으로만 남긴다.

**하네스 함정 하나 — 게임 루프를 얼리지 않으면 오탐이 난다.**
`killed`·`promo` 를 박고 다음 `evaluate` 로 읽으면 그 사이에 RAF 한 프레임이 돌아 값을 되돌린다
(웨이브가 비어 있으면 `killed = 0; queueMobs()`, `promo` 는 `step()` 이 소진시킨다).
실제로 «50%부터 전부 소등» 이라는 가짜 실패가 나왔다. → `window.requestAnimationFrame = () => 0` 으로
루프를 끊고 `drawHud()` 를 손으로 부른다. 색 `transition(.18s)` 때문에 **읽기 전 260ms** 도 필요하다
(안 기다리면 전이 중간값 — 배경은 아직 검정, 테 색은 아직 `currentColor` 로 읽힌다).
