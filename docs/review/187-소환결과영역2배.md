# 187 — 12 소환 결과 팝업: 결과 영역 «2배» (보이는 행 2 → 4)

> 티어 **T2**(저장소 주인 지시) · 지시서 [3]-**(가) 기계적** — 레퍼런스 대조가 아니라

> 대신 «커진 만큼 12·84 의 자리가 그대로인가» 를 게이트로 재고, 되돌림 시험으로 그 자를 검증했다.

## 1. 주인 지시와 증상

> «소환 결과 30개 뽑으면 가려짐 — 결과 부분이 작아서, 2배 정도로 훨씬 커야 함»

실측(수정 전, 1080×2280 · 고유 30칸):

| 항목 | 값 |
|---|---|
| `.sm-grid` 높이 | **335px 고정** |
| 한 행 pitch | 170 (카드 158 + gap 12) |
| 완전히 보이는 행 | **2** (칸 12) |
| 30연 실제 행수 | **5** (칸 30) |
| 가려지는 칸 | **18 / 30 (60%)** |

## 2. 왜 335 로 굳어 있었나 — 그 근거가 이미 만료돼 있었다

`.sm-grid` 위 주석은 이렇게 적고 있었다:

> 30연 소환은 5행이 되는데 우리 프레임에는 **패널↔버튼 사이가 100px 뿐**이라 들어가지 않는다

이 «100px» 은 **1920(9:16) 프레임 시절 값**이다. 작업 63 이 기준을 9:19(2280) 으로 바꾸고
작업 84 가 버튼을 하단 앵커로 옮기면서 그 사이는 이렇게 벌어져 있었다:

```
패널 하변 1248        (top 709 + h 539)
버튼 상변 1706        (bottom 앵커 426 + 버튼 높이 148 → 2280 − 574)
────────────────────
여유          458px   ← 주석이 말하는 100px 이 아니다
```

즉 **자리는 이미 있었고, 아무도 주석을 다시 재지 않았을 뿐**이다.
(LESSONS 계열 «옛 프레임 값이 주석에 화석으로 남는다» 의 또 한 건 — §5 에 등재.)

## 3. 고친 것 — 3곳, 한 벌

### ① `.sm-panel` 에 «행수를 따르는» 높이

```css
height:max(539px, min(calc(204px + var(--sm-gh,335px)), calc(100% - 1303px)))
```

* `204` = border-box 패딩분(상 106 + 하 98). 즉 패널 = 204 + 그리드.
* 상한 `100% − 1303` = «패널 하변 + 20 ≤ 버튼 상변» 을 푼 값
  (버튼 상변 = 프레임H − 426 − 148 → 패널 최대 = 프레임H − 574 − 20 − 709).
* 바닥 `539` = **레퍼런스 패널 높이**. 짧은 프레임에서 상한이 539 아래로 내려가도
  ref 케이스는 픽셀 그대로 두고, 그 아래는 `.sm-btns` 의 기존 보호항이 받는다.

### ② `.sm-grid` 는 높이를 패널에서 받는다

```css
height:100%        /* 옛 335px 고정 */
```

패널 높이가 확정값이므로 `100%` 는 «패널 높이 − 204» 로 정확히 떨어진다.

### ③ `showSummonResult()` 가 행수를 준다

```js
const smRows = Math.ceil(agg.length / 6);
const smGh   = smRows <= 2 ? 335 : Math.min(170 * smRows - 4, 676);
$('sumGrid').parentElement.style.setProperty('--sm-gh', smGh + 'px');
```

n행 높이 = `170n − 12(마지막 gap 없음) + 8(배지 돌출)` = **170n − 4**.

| 결과 행수 | `--sm-gh` | 패널 h | 패널 하변 | 보이는 행 |
|---|---|---|---|---|
| 1~2 | **335** (= ref, Δ0) | 539 | 1248 | 2 |
| 3 | 506 | 710 | 1419 | 3 |
| 4 이상 | **676** (상한) | 880 | 1589 | **4** |

## 4. 설계 판단 — «항상 2배» 가 아니라 «필요할 때 2배»

지시서 처방은 «335 → ~670 고정» 이었지만 **고정으로 넣지 않았다.**
레퍼런스 케이스(10연 = 2행)에서 패널만 880 으로 늘어나면 카드 아래로 **340px 짜리 빈 검은 면**이
남아 12 화면(2차 폴리시 라운드 ①~④ 8 통과)을 그대로 깎는다.

행수를 따라가게 하면 **두 요구가 동시에 산다**:

* 10연(= ref 캡처 케이스) → 패널 539 · **픽셀 Δ0** → `verify12` 14/14 · `verify84` 30/30 무회귀
* 30연(= 주인이 본 케이스) → 보이는 행 2 → **4 (정확히 2배)**

`verify84` 가 원래 갖고 있던 «패널 h(회귀) = 539» 단언이 **손대지 않고 그대로 통과**한 것이
이 판단이 맞았다는 가장 싼 증거다.

## 5. 84 앵커를 왜 안 건드렸나 (안 건드려도 되는지 계산으로 확인)

`.sm-btns{bottom:min(426px, calc(100% - 1416px))}` 는 **그대로 두는 것이 정답**이다.
패널 하변 = `709 + max(539, min(880, H−1303))` 이므로 프레임 높이 H 에 따라:

| 구간 | 패널 하변 | 필요 조건 `bottom ≤ H − 하변 − 168` | `min(426, H−1416)` |
|---|---|---|---|
| H ≥ 2183 | 1589 (상한) | H − 1757 (≥ 426) | 426 ✔ |
| 1842 ≤ H ≤ 2183 | H − 594 | **정확히 426** | 426 ✔ (여유 20 딱 맞음) |
| H < 1842 | 1248 (바닥) | H − 1416 | H − 1416 ✔ |

세 구간 모두 기존 식이 필요 조건과 **같거나 더 엄하다.**
`verify187` D 절이 화면비 4종(2280 · 1920 · 1600(하한) · 2600(상한))에서 실제로 겹침 0 을 확인한다.

### ⚑ 이 회차에서 게이트가 스스로 잡힌 것 — «화면 px 과 프레임 px»

D 절 첫 실행이 **1920×1080 에서만** «패널 h 364 < 539» 로 헛FAIL 했다.
`fit()` 이 그 화면비에서 `#app` 을 `scale(0.675)` 로 줄이므로
`getBoundingClientRect()` 가 **화면 px** 을 준 것이다(1600 × 0.675 = 1080).

→ GEO 가 배율 `k = rect.height / app.offsetHeight` 로 나눠 전부 **프레임 px** 로 되돌린다.
`scrollHeight`·`scrollTop` 은 레이아웃 값이라 **나누면 안 된다**(둘을 섞으면 C9·C14 가 뒤집힌다).
`verify84` 가 같은 화면비에서 **불리언(겹침 여부)만** 재는 이유가 이것이었다 — 절대값을 재려면
배율을 먼저 나눠야 한다.

두 번째로 A12 «2행이면 스크롤 없음» 이 헛FAIL 했다. `scrollHeight` 는 개수 배지 **상자**
(`bottom:-23.7px`)까지 세므로 2행에서도 0 이 아니다 — **187 이 만든 것이 아니라 원래 그렇다**
(잉크 돌출 8 은 `.sm-grid-in{padding-bottom:8px}` 이 이미 받고 있다). 단언을 «여유 ≤ 40» 으로 정정.
