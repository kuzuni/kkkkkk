## 1회차 — ⓐ 게이트가 자기 실패를 말하게 하기

등재문의 착수 순서 ⓐ 「먼저 **실패 항목을 이름으로 찍게** 고친다」.

**진단**: 실패는 원래도 `  ✗ …` 로 찍히고 있었다. 안 보였던 이유는 **출력 순서**다 —
`[A]` 20줄 + 표 20줄이 뒤에 붙어서, `tail` 로 잘라 보면 마지막 줄
(`VERIFY95 FAIL — 1건`)만 남는다. 292 가 «`grep '✗'` 로도 안 잡힌다» 고 적은 것은
`✗` 가 없어서가 아니라 **저장한 출력이 이미 잘려 있었기 때문**으로 보인다.

**수정**(`tools/verify95.js`)

- `fail()` 이 메시지와 함께 **그 시점의 절 이름**(`[A]`~`[I]`)을 같이 담는다 (`section()` 도입).
- 표를 찍은 **뒤에** 실패 목록을 다시 찍는다 — `tail` 로 잘라도 «무엇이» 가 남는다.

```
실패 항목 (절 · 내용)
  1. [E] 관성(fling)
     ✗ 관성 없음 — 뗀 직후 360 → 360
```

## 2회차 — ⓑ 어느 항목이 흔들리는가

첫 실행에서 바로 재현됐다: **`[E] 관성(fling)`** — 등재문이 «1순위 용의자» 로 지목한 그 축이다.

전수 확인용으로 `tools/probe305.js` 를 신설했다. verify95 `[E]` 와 **완전히 같은 제스처**
(6 × 60px · 사이 8ms → up)를 N 회 돌리면서, 게이트 눈에는 안 보이던 값을 같이 찍는다.

| 값 | 뜻 |
|---|---|
| `gap` | pointerup 시각 − 마지막 pointermove 시각 — index.html 의 `< 90` 창 |
| `fling` | `dsFling` 이 실제로 불렸는가 (함수를 감싸서 기록) |
| `v` | 그때 잡힌 속도(프레임px/ms) — `DS_VMIN` 0.02 미만이면 관성 없음 |
| `t0→t1` | 게이트가 재는 값(뗀 직후 · 450ms 뒤) |

## 3회차 — ⓒ 제품 결함인가 계측 결함인가

**계측 결함이다.** 제품(index.html «95» 절)은 의도대로 동작한다:

```js
if(performance.now() - r.t < 90) dsFling(r);   /* 멈춘 채로 뗐으면 관성 없음 */
```

«손을 떼기 직전까지 움직이고 있었을 때만 관성» 이라는 규칙이고, 90ms(≈5프레임)는
사람 손 기준으로 맞다. 틀린 것은 **게이트의 제스처**였다 — playwright 의 `page.mouse.move`·
`page.mouse.up` 은 호출마다 CDP 왕복을 기다리므로, «마지막 move» 와 «up» 사이에
클라우드 컨테이너 기준 **84~134ms** 가 끼어 버린다. 즉 게이트가 **창의 앞턱에 서 있었다**
(226 «게이트가 잰 시점이 흔들렸다» 와 같은 형태 — 제품이 아니라 대기 시각이 원인).

**처방: 고정 대기 → 창 안에 확실히 드는 제스처 + 전제 검사.**

1. `[E]` 의 제스처를 **같은 CDP 세션에 마지막 move 와 up 을 연달아**(왕복을 안 기다리고) 보내는
   방식으로 바꿨다. 세션이 같으면 순서는 보장되고, 간격은 **0.7~1.0ms** 로 떨어진다.
   입력 경로 자체는 `page.mouse` 와 같다(`Input.dispatchMouseEvent`) — 검사가 약해지지 않는다.
   `[F]` 터치 절이 이미 같은 방식으로 CDP 를 쓰고 있어 선례도 있다.
2. 그래도 언젠가 창 밖으로 나갈 수 있으니, **간격을 페이지 안에서 직접 재서** 90ms 이상이면
   «관성이 없다» 가 아니라 **«게이트 계측 — 이 표본으로는 판정할 수 없다»** 로 실패시킨다.
   제품에 없는 죄를 씌우지 않는다.

**결정 대조 실험**(같은 컨테이너 · 각 6회)

| 제스처 | gap(ms) | PASS |
|---|---|---|
| `page.mouse` (수정 전) | 83.7 / 84.4 / 86.7 / 92.1 / 107.0 / 133.1 | **3/6** |
| CDP 연달아 (수정 후) | 0.7 / 0.8 / 0.8 / 0.9 / 0.9 / 0.9 | **6/6** |

**수정 후 프로브 10회 (`node tools/probe305.js 10`)** — gap 0.8~1.0ms · **PROBE305 PASS 10/10**.
`v` 도 0.89~1.12 로 안정(수정 전 PASS 표본의 0.44~0.47 보다 큰 것은, 왕복 지연 없이
마지막 60px 이 온전히 속도로 잡히기 때문이다).

## 교훈 (LESSONS 등재분)

1. **«실패 건수만 보인다» 는 대개 «출력이 잘렸다» 다.** 게이트가 실패를 찍고 있어도
   뒤에 표를 붙이면 `tail` 에서 사라진다 — **판정에 필요한 것은 마지막에 다시 찍어라.**
2. **드라이버 왕복 지연이 제품의 시간 창을 삼킬 수 있다.** playwright 의 `page.mouse` 는
   호출당 왕복이라 «마지막 move → up» 이 84~134ms 다. 제품이 90ms 창을 쓰면
   **게이트는 제품을 재는 게 아니라 컨테이너 부하를 잰다.** 시간 창을 건드리는 제스처는
   같은 CDP 세션에 연달아 쏴서 간격을 1ms 미만으로 만든다.
3. **게이트는 «판정 불가» 와 «제품 실패» 를 구분해서 말해야 한다.** 전제(창 안에서 뗐는가)를
   같이 재고, 전제가 깨졌으면 그 사실을 이름으로 찍는다 — 그래야 다음 세션이
   «flake 니까 재실행» 으로 닫지 않는다.
