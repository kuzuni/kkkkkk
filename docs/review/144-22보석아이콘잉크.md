## 1. 등재된 가설은 틀렸다 (반증)

PROGRESS 144 등재문은 이렇게 적혀 있었다:

> 126 의 서체 교체(이모지 폴백 메트릭이 같이 움직였는지 확인할 것) … **126 서체 교체가 유력 —
> 이모지 폴백이 바뀌면 같은 fs 에서 잉크가 달라진다.**

**이 자리에는 이모지가 없다.** 작업 **125**(화폐 아이콘 단일 출처, 저장소 주인 지시)가 22 보상 칸을
이미 이미지로 갈아 끼웠다:

```js
'<div class="qs-r"><span class="qs-i ifr">' + curIc('dia') + '<i class="ifq">' + fmt(dia) + '</i></span>'
//                                            ↑ <img class="cic" src="assets/ui/cur-dia.svg">
```

`<img>` 는 `font-family` 가 안 건드린다. 따라서 126 은 이 감소분의 원인이 될 수 없다.
게이트 ①(«아이콘은 `<img class="cic">` · src = cur-dia.svg · 이모지 문자 0건»)이 이 사실을 못으로 박아 둔다 —
누가 이 자리를 다시 이모지로 되돌리면 그 항목이 먼저 깨진다.

> **교훈**: «언제부터 줄었는지» 를 묻기 전에 **«지금 무엇이 그려지고 있는지»** 를 먼저 봐야 한다.
> 등재 시점의 코드 주석(«ref 젬 잉크 55×55 에 세로를 맞췄다»)은 **이모지 시절 주석**이었고,
> 그 주석을 근거로 세운 가설이라 통째로 옛 전제 위에 서 있었다. 126 §9-6 «측정표의 환산 상수가
> 옛 서체 것이다» 와 **완전히 같은 함정**이고, 이번엔 그게 주석에서 재발했다.

## 2. 진짜 원인 — 아트 파일 자신의 여백

`assets/ui/cur-dia.svg` 의 젬은 **viewBox 를 꽉 채우지 않는다**:

| 경로 | x | y | stroke | 실루엣(외곽선 포함) |
|---|---|---|---|---|
| 바깥 젬 `M20 4h24l16 18-28 38L4 22z` | 4..60 | 4..60 | 4 (바깥 2) | **2..62 = 60 / 64 = .9375** |

같은 폴더의 `cur-gold.svg` 는 `rx 30 + stroke 4` 라 **0..64 = 1.000** 으로 꽉 찬다.
즉 채움비는 «화폐 아이콘 공통» 이 아니라 **파일마다 다르다**.

`.cic` 는 `width:1.08em;height:1.08em` 이므로 프레임 한 칸의 잉크는

```
잉크 = --if-ic × 1.08 × 0.9375 = --if-ic × 1.0125
```

`--if-ic:50px` → **50.6px** 이 나온다. 차분 실측 **50.67** 과 소수점까지 일치한다.

### 2-1. 비평가 Y 의 «40×46» 은 왜 안 맞나

Y 는 «우리 40×46 vs ref 54×55» 로 적었다. 우리 쪽 실측(50.67×50.67)과 폭이 10px 넘게 갈린다.
젬의 **검정 외곽선을 뺀 색면**만 재면 x 6..58 · y 6..58 = 52/64 → 43.9×43.9 로 Y 값에 가까워진다.
ref 55×55 는 **외곽선 포함 실루엣**이므로(측정표 §5-1 «아이콘 … 검정 외곽선» 항목), 둘을 맞대면
기준이 어긋난 비교가 된다. 이 문서·게이트는 전부 **외곽선 포함 실루엣**으로 통일했다.
방향(«작다»)은 Y 가 맞았고 크기만 과대평가된 것이라, 등재 자체는 유효한 지적이었다.

## 3. 처방

```css
/* index.html .qs-i */
--if-ic: 54.3px;      /* = 55 / 1.0125 */
```

`--if-ic` 는 104 가 «화면별 입력» 으로 남겨 둔 예외 손잡이다(공용 `.ifr` 주석 ⚠ 예외 하나).
아트 여백은 파일마다 다르므로 **공용 토큰으로 흡수할 성질이 아니다** — 화면별 입력이 정확히 맞는 자리다.

`cur-dia.svg` 를 고쳐 여백을 없애는 길도 있었지만 **버렸다**: 같은 파일을 33 재화정보 팝업 · 상단 HUD 알약 ·
53 가방 · 70 출석이 함께 쓰고, 그 화면들은 이미 ①~④ 8 로 통과했다. 아트를 건드리면 통과분 네 화면이
한꺼번에 움직인다(게이트 ④ 가 이 세 칸의 불변을 지킨다).

### 6-1. 잉크는 «면색 마스크» 가 아니라 «차분» 으로 재라

처음엔 «프레임 면색(`--if-face`)과 다른 픽셀 = 잉크» 로 짰다가 버렸다. 프레임은 코너가 둥글고
(r = 폭×.233) 안쪽에 등급 림 6px 이 있어서, 면색 표본을 어느 모서리에서 뜨든 검정선·림이 섞인다.
그러면 임계가 무너져 마스크가 **안쪽 전체**를 잉크로 삼킨다 — 106 프레임에서 «잉크 82×82»
(= 106 − 패딩 24) 가 나온 것이 그 증상이었다. 표본 위치를 모서리→변으로 옮겨도 소용없었다.
아이콘 노드만 `visibility:hidden` 으로 껐다 켠 두 장을 빼면 프레임·림·그라디언트·배지가 통째로
상쇄돼 잉크만 남는다(ink141.js 와 같은 이유).

### 6-2. 캡처를 evaluate 로 넘길 때 두 가지

두 번 죽고 나서 알았다. 다음 게이트를 짤 사람을 위해 남긴다.

1. **`page.screenshot({encoding:'base64'})` 는 이 버전에서 Buffer 를 돌려준다.** 그대로
   `page.evaluate` 로 넘기면 직렬화돼 `data:image/png;base64,[object Object]` 가 되고
   `Image.onerror` 로 떨어진다 — 원인 표시가 «decode» 뿐이라 아트 문제로 오해하기 쉽다.
   `(await page.screenshot({clip})).toString('base64')` 로 간다.
2. **전체 화면을 3× 로 찍으면(3240×6840) data: URI 디코드가 실패한다.** 반드시 `clip` 으로
   필요한 박스만 자른다. 덤으로 빨라진다.
3. `page.evaluate(fn, a, b)` 는 **인자를 하나만 넘긴다** — 두 개 이상은 객체로 묶어라.
