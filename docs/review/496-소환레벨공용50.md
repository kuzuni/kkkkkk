## 2. ★ 이 작업의 본체 — «×2» 를 곧이곧대로 하면 **뽑을 등급이 없는 레벨**이 생긴다

등재문 처방 ③ 은 «불멸 24 → 49, **나머지 ×2 반올림**» 이다. 사다리 여덟 칸 중 앞 두 칸은
`unlock:1` 인데, 그것까지 ×2 하면 **2** 가 된다. probe496 ⓔ 가 `gradeProbs` 와 같은 식으로
그 «만약» 을 찍었다:

```
전부 ×2  (2,2,10,16,24,32,40,48) → Lv1 에서 Σw = 0 · Σp = 0     ← 뽑을 등급이 없다
바닥 유지 (1,1,10,16,24,32,40,49) → Lv1 에서 Σp = 1 · 일반 0.800
```

`gradeProbs` 의 `const tot = w.reduce(...) || 1` 폴백은 **분모만** 1 로 만든다 — 분자가 전부 0 이면
확률도 전부 0 이다. 즉 «÷0 크래시» 로도 안 드러나고 **조용히 아무것도 안 나오는 Lv1** 이 됐을 것이다.

⇒ **바닥 두 행(`unlock:1`)은 «해금 레벨» 이 아니라 «항상 열려 있다» 는 바닥**이므로 ×2 하지 않는다.
`verify496` [C5] 가 그 자리를 지키고, 근거는 추측이 아니라 probe 의 두 줄이다.

같은 이유로 **불멸은 숫자 49 를 손으로 안 적었다** — `unlock: SUM_MAXLV - 1` 이다.
196 이 정한 «불멸만 만렙 직전 1 레벨 램프» 는 값이 아니라 **규칙**이라 만렙에서 역산해야
만렙이 또 움직여도 따라간다(LESSONS 106-1). `verify115`·`verify85`·`verify106` 의 이관도
`maxlv − 1` 로 적어 같은 성질을 갖게 했다.

## 3. 구조 — 왜 옛 이름 `S.sum` 을 안 지웠나

저장 자리는 **스칼라 둘**로 내려왔다: `S.sumLv` · `S.sumExp`.
그런데 `S.sum[b].lv = 25` 로 상태를 만드는 자리가 제품 밖(게이트·재현기)에 **열 곳이 넘는다**.
등재문 ① 이 «호출부 변경을 최소화» 하라고 한 것도 그 뜻이다.

⇒ `S.sum` 은 사라지지 않고 **별칭 뷰**로 남는다(`sumAliasView`, `Object.defineProperty`):

- `enumerable:false` — `JSON.stringify(S)` 가 안 담는다. **새 세이브에는 스칼라 둘만** 들어간다
  (다섯 벌 사본이 다시 저장되면 «어느 쪽이 진실인가» 가 되살아난다). `verify496` [A6] 이 지킨다.
- setter 는 **일부러 no-op** — `load()` 의 `Object.assign(b, d)` 가 구 세이브의 `d.sum` 을
  여기로 밀어 넣는데, 그대로 받으면 별칭이 평범한 객체로 덮인다. 구 세이브는 이관 블록이
  `d.sum` 에서 **직접** 읽는다. 같은 이유로 `['lv','eqSlot',…,'sum','dun']` 목록에서 `sum` 을 뺐다.
- getter 가 `this` 를 쓴다 — `load()` 안에서 상태 객체는 `S` 가 아니라 `b` 다. 바깥 `S` 를 잡아 두면
  로드 도중 엉뚱한 객체를 가리킨다.

이 구조의 값은 «편의» 가 아니다 — **«두 배너가 서로 다른 레벨» 이라는 상태를 만들 방법 자체가
없어진다.** `verify496` [A4] 가 옛 이름으로 써 놓고 다섯이 한 값인지를 묻는다.

접근자 둘은 인자를 **일부러 무시**한다(`const sumLv = _b => S.sumLv`). 인자를 지우면 같은 뜻의
편집이 `gradeProbs`·카드·확률 팝업·20 프로필·게이트 수십 자리로 번진다.

## 4. 곡선 — 표를 식으로 되돌렸다

```
need(n) = SUM_EXP_A + SUM_EXP_B·n = 200 + 210·n      (n = 지금 레벨 1..49)
  Lv1→2 410 · Lv10 2,300 · Lv25 5,450 · Lv49 10,490
  누적 Σ = 200×49 + 210×(49×50/2) = 267,050 뽑
```

주인 확정문의 «약 268,000 뽑» 대비 **−0.35%**(확정 ±1% 안). 확정문의 «Lv49 10,500» 은
식으로는 **10,490** 이다(200 + 210×49) — 확정문이 210×50 을 적은 자리로, 식이 정의이므로 식을 따랐다.
**정오표**: 496 등재문 ② 의 «Lv49 10,500 · 누적 268,000» → 실제 **10,490 · 267,050**.

구 표는 이름을 바꿔 **이관 전용**으로만 남겼다(`SUM_EXP_TABLE_V196` · `sumNeedExpV196` · `SUM_MAXLV_V196`).
`verify496` [B8]·[B9] 가 «살아 있는 표는 없고 `_V196` 만 있다» 를 지킨다 — 그래야 밸런스를 고치려는
다음 세션이 **표가 아니라 A·B 두 상수**를 잡는다.

## 5. 세이브 이관 — «손해 0 = 총 뽑기 수 보존»

KEY 는 안 올렸다(44 교훈 2). `sumLv` 이 없는 세이브를 구 세이브로 보고 한 번만 옮긴다.

1. 배너별로 **구 곡선으로 되돌려 센다** — `Σ 구need(1..lv−1) + exp`.
2. 다섯을 더한다(경험치 1 = 소환 1 회라 합이 곧 **총 뽑기 수**).
3. 그 합을 새 곡선에 그대로 얹는다(`sumAddExp` 와 같은 셈).

측정 — 등재문이 지정한 표본 **배너별 12/8/3/20/5**:

| | 구 누적 | 새 자리 | 되돌려 센 값 |
|---|---|---|---|
| 12/8/3/20/5 (exp 0) | **75,350 뽑** | Lv **26** · exp **2,100** | **75,350** ✔ |
| 잔여 exp 포함 표본 | 80,496 뽑 | Lv 27 · exp 1,586 | 80,496 ✔ |
| 구 5 배너 만렙 | 382,250 뽑 | Lv **50 MAX** (상한) | — |

`verify496` [D2] 가 «새 곡선에서 되돌려 세도 같은 수» 를 단언한다 — 레벨 숫자를 기대하는 대신
**보존량**을 묻기 때문에 이관이 사라지면 반드시 빨개진다.

⚠ **상한은 상한이다** — 구 5 배너 만렙(382,250 뽑)은 새 만렙까지의 267,050 뽑보다 크므로
그런 세이브는 Lv50 MAX 에서 멈춘다. 레벨을 잃지는 않는다(어차피 만렙).

⚠ **손댄 세이브 방어를 «더하기 전에» 걸었다**(1 회차에 놓칠 뻔한 구멍) — `exp: 999999` 를 그대로
더하면 «다음 레벨에 못 미치는 잔여» 였던 값이 999,999 뽑으로 둔갑해 **Lv14 짜리 세이브가 공짜로**
생긴다. 배너마다 `구need(lv) − 1` 로 접고서 더한다. 정상 세이브의 exp 는 구조상 늘 그 아래라
**깎이는 진짜 진행도는 0**. `verify496` [D6] 이 그 자리를 지킨다(50 + 199 = 249 뽑).
