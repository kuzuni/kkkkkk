## 2. 뿌리 — 「겹쳐 서지 않는다」가 **서 있는 동안만** 지켜지고 있었다

257 이 넣은 두 겹(조향 `BOSS_SEP` + 위치 해소)은 **이동 루프 안**에 있다. 그 루프의 맨 앞이

```js
if(e.born < 0.3) continue;      /* 등장 창 18프레임 — 이동도 분리도 안 돈다 */
```

이고, **스폰 좌표는 이웃을 안 본다**:

```js
const a = Math.random()*6.283, r = rnd(SPAWN_RMIN, BOSS_RMAX);   /* 300~340 링의 난수 한 점 */
```

보스 반지름은 `dunBossType` 이 24~90 으로 잡으므로 반지름 합은 최대 180px, 링 둘레는 ~2000px 다.
세 마리를 **같은 프레임에** 링 위 난수로 뽑으면 한 쌍이 겹칠 확률이 낮지 않다 — 실측 **24회 중 12회**.
겹쳐 태어난 판은 0.3초를 **한 마리처럼 겹친 채 서 있다가**(등장 애니 중이라 아무도 안 움직인다)
분리가 시작되면 반씩 미는 해소가 몇 프레임에 걸쳐 푼다(그래서 이동 후에도 최악 79%).

게이트가 4회에 1번만 빨갰던 이유도 여기서 나온다 — **게이트는 `k < 12` 만 건너뛰는데 제품은
`k < 17` 을 건너뛴다.** 그 어긋난 5프레임이 «겹쳐 태어난 판» 을 잡아내던 유일한 창이었다.
스폰이 안 겹친 판(12회)은 그 창도 초록이라 전체가 초록으로 끝났다.

> ⚑ 즉, 이 항은 **플레이키한 게이트가 아니라 «절반만 보는 게이트»** 였다. 난수를 고정했으면(ⓐ)
> 주인이 화면에서 보는 «보스 셋이 한 마리로 겹쳐 등장하는 판» 을 **초록으로 굳혔을 것**이다
> (LESSONS 338-① 의 재발 — 등재문의 처방 방향은 가설이지 사양이 아니다).

## 3. 처방 — 스폰이 이웃을 본다 (`index.html`, 1곳)

```js
const soloClash = (tk, r, x, y) => {          /* 단독 개체(SOLO_CHASER)끼리만 본다 */
  if(!SOLO_CHASER[tk]) return null;
  for(const o of enemies){ if(SOLO_CHASER[o.tk] && Math.hypot(x-o.x, y-o.y) < r + o.r) return o; }
  return null;
};
...
while((x < 60 || … || soloClash(tk, T2.r, x, y)) && tries < 40);   /* ← 새 항은 맨 뒤 */
```

세 가지를 지켰다:

1. **새 항은 `while` 의 맨 뒤**다. 필드에 단독 개체가 하나뿐이면 `soloClash` 는 언제나 `null` 이라
   **뽑는 횟수도 `Math.random()` 소비도 한 번도 안 달라진다** — 스테이지 보스 · 승급 수호자 ·
   아레나 도전자 · 46 레이드 샌드백 · 보스 1마리 던전의 좌표는 한 px 도 안 움직인다.
   (전수 확인: 2마리 이상의 단독 개체가 같은 필드에 서는 경로는 **동시 등장 던전 3종뿐**이다 —
   `startRaid` 는 `enemies.length = 0` 뒤에 한 마리, `startPromo`·`startArena` 도 단독.)
2. **미는 것은 새로 태어나는 쪽뿐**이다. 40번을 다 써도 자리가 없는 극단(좁은 월드 · 반경 90
   보스 여럿)에서만 도는 마지막 4패스가 **신참만** 민다 — 이미 서 있는 개체의 좌표는 여기서도 불변.
3. **밸런스 0줄.** 링 반지름(300~340)의 분포를 안 건드렸다 — 다시 뽑는 것은 **각도**뿐이고
   체력·공격력·수·보상은 한 줄도 안 지났다.

## 4. 게이트 — [6] 을 한 항에서 «전제 1 + 4항 × 3던전 × 3뽑기» 로 가르고, [6-R] 되돌림 시험을 신설

| | 무엇을 묻나 | 기대 | 실측 |
|---|---|---|---|
| 전제 | 동시 등장 던전이 몇 종인가 | ≥ 2 | 3 (relic3:2 · stone:2 · rstone:3) |
| 전제 | 보스가 **실제로** 그 수만큼 섰다 | ≥ bn | 2·2·3 |
| ① | 스폰 프레임 겹침 0 | ≥ 100% | 249.5 · 126.2 · 327.3% |
| ② | 등장 창(k<17, 아무도 안 움직임) | ≥ 100% | 같은 값(움직이지 않으므로) |
| ③ | 런 전체 최소 간격 | ≥ 90% | 97.4 · 98.9 · 98.3% |
| ④ | 97% 아래가 **이어진** 최대 프레임 | ≤ 2 | 0 · 0 · 0 |

세 가지를 바꿨다:

- **`if (k < 12) continue;` 를 지웠다.** 건너뛰던 그 창이 결손이 살던 자리였다.
- **표본을 «1던전 1뽑기» 에서 «3던전 × 3뽑기» 로.** 한 번의 뽑기 운으로 초록이 될 수 없다.
- **「최소 간격 ≥ 97%」 한 항을 넷으로 갈랐다**(LESSONS 326 «칸을 갈라 써라»). 이동 중에는
  위치 해소가 **반씩** 미느라 한 프레임짜리 잔차가 남고 그 바닥이 실측 **97.4%** 다 —
  0.4%p 위에 임계를 두면 «겹쳐 서 있다» 와 «한 프레임 수렴 잔차» 를 같은 자로 재게 되어
  **또 흔들린다**. 그래서 정지 창(①②)은 **100% 로 조이고**, 이동 창은 **깊이(③ ≥90%)** 와
  **지속(④ 연속 ≤2프레임)** 으로 나눠 물었다. 이것은 무르게 푼 것이 아니다:
  수리 전 결손(12~53% 가 **17프레임 이상**)은 ①②③④ 가 **전부** 빨갛고, 257 의 위치 해소를
  되돌리면(공격 모션 중 얼어붙어 겹침 17%가 수백 프레임 지속) ③④ 가 빨갛다.

### [6-R] 되돌림 시험 — 옛 스폰을 손으로 만들어 본다 (334-③ 처방)

```
ok  R1 옛 스폰을 심으면 간격이 12.0% — ③(≥90%) 이 실제로 빨개진다
ok  R1 등장 창 18프레임 내내 12.0% — ②(≥100%) 도 빨개진다 (제품은 이 창에서 아무것도 안 한다)
ok  R2 그대로 40프레임 굴리면 99.5% 로 복구 — 257 의 위치 해소는 살아 있다
```

R1 은 **새 단언에 이빨이 있음**을, R2 는 **257 이 만든 것을 한 줄도 안 깨뜨렸음**을 못박는다.
