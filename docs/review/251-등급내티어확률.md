## 1. 무엇이 요구였나

주인 지시 원문: **«같은 등급 안에서도 티어가 낮은 것은 뜰 확률을 더 적게»**

작업 전 상태는 **등급 내 완전 균등**이었다 — `gradeProbs()` 로 등급을 뽑고 그 등급 풀에서
`pool[Math.floor(Math.random()*pool.length)]` 로 1/N. 11 확률 팝업도 같은 전제로
`gp[g] / items.length` 를 찍고 있었다(그래서 한 등급 안의 행이 **전부 같은 값**이었다).

### «티어» 의 정의 — 지어내지 않았다

작업 **260**(2026-08-27)이 바로 앞에서 정의를 확정해 두었다: 등급 안 배열은 **앞이 약하고 뒤가 세다**
(장비 `v` 오름차순 · 펫 `m/cd` 오름차순). 260 의 인계 메모 7-③ 이 그대로 적어 두었다 —
«251 의 «티어» 정의는 이제 배열 순서와 같다».

**단, 스킬은 예외다.** 260 은 주인 완화 지시(«같은 등급이면 효과 비슷해도 될 듯»)로 스킬의
오름차순을 **면제**했고 «등급 안 편차 ≤ 3.0» 만 조였다. 그래서 스킬은 배열 자리가 세기 순서가 아니다
(게이트 [E3] 로 «6개 등급 전부 그렇다» 를 실측해 못 박았다). → **티어는 자리가 아니라 «세기» 로 잡는다.**
척도는 260 이 쓴 것을 그대로 재사용했다:

| 계열 | 티어 척도 | 근거 |
|---|---|---|
| 장비(무기·방패·목걸이) | `v` | 85 의 개체차 배율. 260 이 등급 안 오름차순으로 정렬해 둔 값 |
| 펫 | `m / cd` | 106 의 파생식. 260 [B2] 가 쓰는 «세기» 와 같은 자 |
| 스킬 | `m × hits / cd` (cd 0 = 지속형은 `m × 3`) | `stat.dps` 가 실제로 쓰는 식(260 [C] 와 동일) |

## 2. ★ 방향이 이 작업의 유일한 쟁점이었다 — 그리고 그것을 «상수 하나» 로 만들었다

등재문 자신이 걸어 둔 물음: **«확인 필요(주인)»** — 지시문 그대로면 «약한(= v 낮은) 개체가 더 드물게»
인데, 흔한 방치형 관례(강한 것일수록 희귀)와 **반대 방향**이다.

**주인은 지금 자리에 없고(루틴 워커), 물어볼 길이 없다.** 그래서 이렇게 갈랐다:

- **지시문 원문을 그대로 구현했다.** «티어가 낮은 것 = 그 등급 안에서 약한 것» 이고, 그것이 «더 적게»
  나온다. 260 이 확정한 «1번째가 제일 약하다» 와 붙여 읽으면 «티어가 낮다 = 앞자리 = 약하다» 로
  두 문장이 정확히 맞물린다. 앞 세션(260 인계 메모)이 «뒤로 갈수록 확률을 낮게» 라고 적어 둔 것은
  **주인의 말이 아니라 그 세션의 관례 추정**이라, 원문을 이겼다고 볼 근거가 없다.
- **대신 방향을 되돌리는 비용을 «상수 한 글자» 로 낮췄다.** `TIER_W_DIR` 을 `1` → `−1` 로 바꾸면
  가중치·추첨·11 확률 팝업·게이트가 전부 따라 뒤집힌다. 게이트 [A5] 가 지금 값이 «지시문 쪽» 임을
  명시로 찍어 주므로, 주인이 반대를 의도했다면 그 한 줄만 고치고 [A5] 의 기대를 −1 로 바꾸면 끝이다.
- 폭도 상수 하나(`TIER_W_RATIO = 2.0`)다. `1.0` 으로 두면 정확히 종전 균등이 된다.

**남은 것(주인 확인)**: 방향이 반대였다면 `TIER_W_DIR = −1`. 그 외에는 아무것도 바꿀 필요가 없다.

## 3. 고른 처방 — 등비 가중, 등급 확률은 한 톨도 안 건드린다

```js
const TIER_W_RATIO = 2.0;   /* 등급 안 «최상위 티어 / 최하위 티어» 가중 비 */
const TIER_W_DIR   = 1;     /* +1 = 지시문 그대로(약한 것이 드물다) */
/* 세기 오름차순 순위 r(0 = 최약)에 대해  w ∝ RATIO^(DIR · r/(n−1)),  Σw = 1 */
```

등비를 고른 이유는 **«한 계단당 같은 배수»** 라서 종 수가 4개든 5개든 1개든 같은 규칙이 통하고,
양 끝의 비가 정확히 `TIER_W_RATIO` 로 떨어지기 때문이다(게이트 [A3] 이 그 값을 잰다).
5종이면 계단마다 ×1.189, 4종이면 ×1.260 이다.

| 종 수 | 티어별 확률(약 → 강) |
|---|---|
| 5종(등급 대부분) | 13.726% · 16.324% · 19.412% · 23.085% · **27.453%** |
| 4종(스킬 일반·고급·신화) | 17.102% · 21.547% · 27.147% · **34.204%** |
| 1종(불멸) | 100% (그대로) |

### 못 3개

1. **등급 확률(`gradeProbs`)은 1도 안 바뀐다.** `tierWeights` 합이 정확히 1 이라 한 등급의 항목 확률
   합은 여전히 `gp[g]` 다 — 게이트 [B1] 이 **전 배너 × 전 이정표**(250 이 «레벨 1..25 연속» 으로
   넓힌 뒤라 배너당 25단계)에서 오차 ≤1e-12 로 확인한다. 즉 **197(등급 점프 파워 커브)·199(최종
   밸런스)의 등급 분포는 흔들리지 않는다.** 움직이는 것은 개체차 `v` 의 기댓값 하나뿐이고,
   5종 등급에서 균등 1.012 → 가중 1.030 = **+1.8%** 다(등급 배수 최소 비 1.500 대비 무시할 폭).
2. **추첨과 표시가 같은 함수를 쓴다** — 등재문이 못 박은 조건(«표기만 바꾸고 추첨을 안 바꾸면 그게 곧
   버그»). `summonOne()` 과 `renderProbInfo()` 가 **둘 다** `tierWeights()` 를 부른다. 게이트 [D1] 이
   11 확률 팝업 DOM 의 행별 % 문자열을 그대로 읽어 계산값과 대조한다(무기 36행 · 스킬 27행 · 펫 36행).
3. **세이브·id·표에 손대지 않았다.** 251 은 «어느 종이 나오느냐» 의 확률만 바꾼다 —
   `S` 키 집합·`KEY`·`EQUIPS/PETS/SKILLS` 의 id·v·m·cd 전부 불변([E1]·[E2]·[F1]·[F2]).

### 손댄 자리 (index.html 3곳)

| 자리 | 전 | 후 |
|---|---|---|
| `summonOne()` | `pool[Math.floor(Math.random()*pool.length)]` | `tierWeights(pool, b)` 누적 추첨 |
| `renderProbInfo()` | `each = gp[g] / items.length * 100` | `each = gp[g] * tw[ti] * 100` |
| 11 팝업 머리 주석 | «등급 내 균등 추첨» | «251 등급 내 티어 가중 추첨 `tierWeights`» |

`tierScore()`·`tierWeights()` 는 `gradeProbs()` 바로 뒤에 신설했다.

## 4. ★ 게이트가 처음에 «제품이 맞는데» 빨갛게 나왔다 — 자가 틀린 경우

첫 판에서 [C1]·[C2]·[C3] 이 전부 FAIL 이었다. 원인은 제품이 아니라 **게이트가 쓴 난수**였다.

표본 추출을 재현 가능하게 하려고 흔한 LCG 를 그대로 옮겨 적었다:

```js
s = (1103515245 * s + 12345) % 2147483648        // ← JS 에서 이러면 안 된다
```

`s` 가 2³¹ 근처면 곱이 **2.4×10¹⁸ = 2⁵³ 초과**라 배정밀도 가수가 잘려 나간다. 게다가 LCG 는
하위 비트 주기가 짧아, `summonOne` 이 **한 번에 두 번**(등급 뽑기 → 티어 뽑기) 부르는 구조와
강하게 상관됐다. 그 결과 «무기 20만 표본» 과 «펫 20만 표본» 의 등급별 카운트가 소수점까지
쌍둥이(1526 vs 1528 …)로 나왔고, 일반 등급의 관측 순서가 뒤집혀 보였다.

**mulberry32**(32비트 정수 연산 `Math.imul`·`>>>` 만 쓴다 — 정밀도 손실이 구조적으로 없다)로 갈고
표본을 40만으로 올리자 20개 풀 전부 초록이 됐다. 판정도 «상대오차 3%» 같은 고정 문턱에서
**`4·√기대값 + 1%`**(= 4σ + 여유)로 바꿨다 — 얇은 칸(기대 2,600)과 두꺼운 칸(기대 33,000)에
같은 상대 문턱을 걸면 얇은 쪽이 원래 뜨고 진다.

## 7. 범위 밖으로 둔 것 (근거 포함)

### ⓐ 유물 소환(`summonRelic`, `#relw`) — **손대지 않았다**

등재문이 «유물은 `RELICS[Math.floor(Math.random()*RELICS.length)]`» 이라고 같이 짚었지만,
이 경로에는 **«등급을 뽑는 단계가 아예 없다»**. 10종 전체에서 균등 1종을 골라 Lv+1 하는 것이
89 가 확정한 설계(«유물조각으로 소환 = 균등 1종 Lv+1 자동 강화»)다. 지시문의 «같은 등급 안에서도»
가 성립하려면 등급 단계가 먼저 있어야 한다.

게다가 **유물에는 티어 축이 없다.** 같은 등급 안의 두 유물이 서로 다른 효과라 `v` 가 비교 불가다:

| 등급 | 구성원 | `v` |
|---|---|---|
| 고급 | 전사의 문장(**hp**) · 심판의 저울(**cdmg**) | 0.08 · 0.06 |
| 희귀 | 광전사의 뿔(**atk**) · 현자의 눈(**crit**) | 0.12 · 0.02 |
| 영웅 | 용의 심장(**hp**) · 폭풍의 인장(**rate**) | 0.20 · 0.10 |
| 전설 | 황금 왕관(**gold**) · 세계수의 씨앗(**regen**) | 0.35 · 0.40 |

«hp +8% 와 치명타 피해 +6% 중 어느 쪽이 센가» 는 **밸런스 판단**이지 측정이 아니다.
지어내면 260 이 경고한 «닫히는 검산으로 틀린 수를 굳히는» 짓이 된다.
→ **주인 확인 사항으로 남긴다**: 유물에도 티어 차등을 넣으려면 ① 유물 소환을 등급 뽑기로 바꿀지
② 티어 축을 무엇으로 잡을지(효과별 환산 계수) 두 가지를 먼저 정해야 한다.

### ⓑ 장비 합성 결과(`nextGradeItem`, 85 ⑤) — **균등 유지**

«합성 결과는 다음 등급 5종 중 랜덤» 은 85 의 **주인 지시 원문**이다. 251 은 «뜰 확률»(소환)에 대한
지시이고 합성은 소환 경로가 아니라, 다른 작업 단위의 확정 사양을 251 이 덮지 않았다.
넣기로 한다면 `nextGradeItem` 에 `tierWeights` 를 물리는 **한 줄**이면 된다(함수가 이미 범용이다).

### ⓒ `verify193` 1건 FAIL — **내 작업 전 트리에서도 똑같이 재현된다**

`node tools/verify193.js` → **72/73**, 「기존 19종 id·등급·cd·m 불변」 4건 어긋남.
`git stash push -- index.html` 로 작업 전 트리에서 돌려도 **똑같이 72/73** 이다.
내용은 **260 이 조인 스킬 m 4~5건**(drain·frost·bounce·gale·lance)이고, 260 은 같은 성격의 표를
`verify86` 에서는 갱신했는데 `verify193` 쪽은 남겨 두었다. 251 구간이 아니라 **손대지 않았다** —
게이트 정리 라운드(211~215·219·223·227 계열)의 몫으로 PROGRESS 에 등재한다.
