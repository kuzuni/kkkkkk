## 1. 재현 (338 규칙 — 처방 전에 «찍힌 픽셀» 부터)

등재문은 한 자리의 수치만 들고 있었다 — 69 우편 목록에서 다이아 **49.33** vs 골드 **52.00** = **1.054 배**로
411·356 이 쓰는 «덩치 최대÷최소 ≤ 1.05» 눈금을 넘는다. `tools/probe644.js` 를 신설해 그것이
**한 자리의 사고가 아니라 아트 15장의 규격 결손**임을 세 갈래로 물었다.

**등재문 그대로 확인됐다.** 아트 15장이 캔버스를 채우는 «긴 축» 비율:

| 아트 | 긴 축 채움비 | | 아트 | 긴 축 채움비 |
|---|---|---|---|---|
| `cur-gold` | **1.0000** | | `cur-stone` | 0.8164 |
| `cur-rstone` | 1.0000 | | `cur-tstone` | **0.7500** |
| `cur-relic` | 0.9727 | | `cur-mile` | 0.9063 |
| `cur-dia` | 0.9375 | | `cur-ticket-*` (8장) | 0.9375 |

⇒ **최대 1.0000 ÷ 최소 0.7500 = 1.3333** — 눈금을 크게 넘는다. `.cic` 상자는 **정사각**이라
같은 상자에 담아도 골드는 단련석보다 **33% 크게** 그려진다. 69·53 처럼 **한 상자를 여러 아트가 공유하는
자리**는 예외 없이 이 편차를 그대로 화면에 낸다(53 가방도 같은 1.054 를 냈다).

## 2. 눈금을 먼저 정했다 (394 규약)

**눈금 = «외접 정사각형의 변» = max(잉크w, 잉크h) ÷ 캔버스.**
`.cic` 상자는 정사각이고 `object-fit:contain` 이므로 상자를 정하는 것은 **긴 축 하나**다.
짧은 축은 **아트 자신의 종횡비**이고 356 규약(원본 비율 · 비균등 스케일 금지)이 그것을 못 건드리게 한다
— 그래서 «세로» 나 «면적» 을 눈금으로 삼는 길은 정사각 상자 안에서 **기하적으로 막혀 있다**
(입장권은 종횡 1.765 라 세로를 코인에 맞추면 폭이 상자를 76% 넘는다).

### 목표 채움비 F — 근거는 취향이 아니라 레퍼런스 실측이다

후보는 둘이었다. **ⓐ 1.0000**(골드가 쓰는 값) · **ⓑ 0.9375**(다이아 + 입장권 8장 = **15장 중 9장**의 최빈값).
표만 보면 ⓑ 가 «다수결» 이고 바꿀 파일도 6장뿐이라 싸 보인다. **그런데 저장소 안에 레퍼런스 실측이 있다.**

`tools/verify340.js` 의 `REF` 상수가 ref 코인·젬의 **실루엣을 똑같이 64×65** 로 적어 두었다
(`gold: {sil:[64,65]}` · `dia: {sil:[64,65]}`). **레퍼런스는 두 아트를 같은 덩치로 그린다** — 즉 채움비는
아트마다 다를 수 없다는 것이 레퍼런스의 선언이다. 그리고 340 [2] 는 골드의 **색 잉크를 ref 57 ±3** 으로
못박고 있다.

⇒ **ⓑ 를 고르면 골드가 ref 에서 멀어진다**(57 → 53.4 = 340 [2] 가 즉시 빨개진다).
ⓐ 를 고르면 골드는 **한 픽셀도 안 움직이고**(원래 1.0000 — 644 가 손대지 않은 유일한 아트다)
340 이 «−12.5%» 로 적어 둔 다이아의 결손이 ref 쪽으로 줄어든다.
**레퍼런스 실측이 박혀 있는 축을 «멀어지는 쪽» 으로 미는 것은 재기준이다** ⇒ **F = 1.0000**.

125 컴포넌트 주석·측정표(A3 «63×63» · 41 «57×57»)가 `.cic` 상자를 **«아트 자리 bbox»** 로 적어 둔 것도
같은 방향이다 — **F=1.0 은 새 규격이 아니라 그 선언이 처음으로 참이 되는 것**이다.

## 3. 처방 — 자른 것은 **캔버스뿐**이다

각 파일의 `viewBox` 를 **그 아트의 잉크 bbox** 로 바꿨다. path·stroke·색은 **한 자도 안 건드렸다**.
`width="64" height="64"` 를 그대로 두면 캔버스는 정사각으로 남고, 기본 `preserveAspectRatio`(xMidYMid meet)가
잘린 viewBox 를 그 안에 **등방으로** 맞춰 가운데 놓는다.

| 파일 | viewBox | | 파일 | viewBox |
|---|---|---|---|---|
| `cur-gold` | `0 0 64 64` (**무변경**) | | `cur-stone` | `8 1 48 52` |
| `cur-dia` | `2 2 60 60` | | `cur-tstone` | `8 8 48 48` |
| `cur-relic` | `5 1 54 62` | | `cur-mile` | `3 13 58 42` |
| `cur-rstone` | `12 0 40 64` | | `cur-ticket-*` ×8 | `2 15 60 34` |

수리 뒤 **15장 전부 긴 축 채움비 1.0000 · 최대÷최소 1.0000** · 잉크 중심 전부 (32, 32).
`cur-rstone` 은 자르기 전후로 **렌더가 비트 동일**하다(세로가 원래 꽉 차 있어 스케일 1) — 그런데도 잘라 둔 것은
「viewBox == 잉크 bbox」 를 **15장 공통 불변식**으로 만들어 자 하나가 파일만 보고 검산할 수 있게 하기 위해서다.

⚠ **`cur-stone`·`cur-mile` 은 자르면서 가운데로 옮겨졌다**(stone 중심 y 27 → 32 · mile 34 → 32).
그림이 캔버스 안에서 원래 치우쳐 그려져 있던 것이고, «상자 = 아트 자리» 선언에서는 가운데가 맞다.

### 왜 `<g transform>` 이 아니라 viewBox 인가

둘은 **렌더가 같다**(스트로크까지 같은 배율로 커진다). viewBox 는 **속성 한 줄**이라 path 를 손대지 않는다는
것이 파일 자체로 보이고, 자가 「viewBox == 잉크 bbox」 를 **파일만 읽고** 검산할 수 있다.

## 4. ⚑ 본체는 «아트를 고치는 것» 이 아니라 **보정 손잡이를 되감는 것**이었다

아트만 고치고 끝냈으면 **9종의 자가 빨개졌고 그중 넷은 제품이 레퍼런스에서 멀어졌다는 뜻이었다.**
저장소가 이 결손을 **자리마다 상자·배율로 이미 보정하고 있었기** 때문이다 — 585 의 주석이
«아트가 viewBox 를 덜 채워서 같은 배율에 그려진 잉크가 제각각 작아진다» 고 **이 결손을 그대로 적어 두고**
자리마다 되민 값을 박아 뒀다.

⇒ 규칙을 하나 정해 그대로 적용했다:

아무도 안 못박은 자리는 선언(상자)이 참이 되게 둔다.**

## 5. 게이트 이관 — 셋은 «잘못된 근거로 초록이던» 자리다

- **`verify584` [2-g] 는 헛초록이었다.** 세 파일의 `viewBox` **문자열**이 같은지만 보고
  «상자가 같다 = 잉크가 같다» 를 주장했는데, 그 결론은 세 아트가 캔버스를 같은 비율로 채울 때만 성립한다.
  실제로는 `cur-rstone` 이 **가로를 .625 밖에** 안 채워 같은 상자에서 폭이 37% 작았고 **옛 술어는 그것을
  한 번도 못 봤다.** ⇒ 문자열이 아니라 **실제로 그려진 채움비**를 재게 갈아 끼우고, «rstone 은 가로가 .625 다»
  를 별도 항([2-g2])으로 세워 그 사실이 이제 표에 남게 했다.
- **`verify125` C1** 의 `viewBox="0 0 64 64"` 문자열 술어 → «네 수짜리 유효한 viewBox + `width/height` 64».
  C1 이 지키려던 것(파일·`<svg>`·viewBox 유효성)은 그대로이고, 자르기 값 자체는 `verify644` 가 **더 세게** 지킨다.
- **`verify433`·`verify444`** 는 아트의 **속** 기하(문양 ↔ 속띠 ↔ 검은 테)를 `N = 64×SC` 로 래스터해서 잰다
  — «1단위 = SC px» 이 `viewBox="0 0 64 64"` 전제다. path 가 안 바뀌었으므로 **잴 때 좌표계를 되돌리면
  옛 래스터가 그대로 재현**되고 BAND·CY·MIN_W 상수는 한 자도 안 바뀐다(한 줄 `VB644()`).
- **`verify144`** 의 «`.cic` 박스 = `--if-ic` × 1.08 (58.64±0.6)» 도 실은 어긋나 있었다 — 그 자리는 418 이 박은
  **명시 override 59** 이고 자연값 58.64 와 다른 수인데 허용폭 안에 우연히 들어와 있었다.
  644 로 «상자 = 잉크» 가 되면서 그 override 가 **ref 잉크 55 와 같은 수**가 됐다.
- **`verify125` D1·D3 / `verify340` [3][4]** 는 **상자** 숫자만 63 → 59.06 으로 옮겼다.
  ⚑ **이 이관의 음성항은 `verify340` [2] 와 `verify585` §5** 다 — **잉크**를 재는 그 두 절이
  **수리 전과 똑같은 값으로** 초록인 한, 상자 숫자를 옮긴 것은 무르게 푼 것이 아니다.
  (340 은 D3 주석에 «자산이 고쳐지면 D1 과 함께 내린다» 고 **미리 적어 두었다**.)
- **`verify543`** 의 기준선 `BASE_DIA_INK` 36.09 → **38.50**(= 36.09 × 64/60). 그 값은 «543 이전 트리의
  비행 중 다이아 잉크» 이고 채움비가 곱해진 수라 같은 비율로 다시 잰다. §R 되돌림이 실제로 38.50 을 찍고
  [C] 와 **같은 상수**를 쓰므로 임의로 적을 수 없다.
- **`verify596` [R2 전제]** 의 비등방 사본 계수 1.12875 → 1.05820(× .9375). **비등방 축 `scaleY(1.379)` 는
  그대로 뒀다** — 그 항이 잡으려는 위반 자체가 그 축이라 거기를 건드리면 되돌림 시험이 무뎌진다.

### ⚑ 하나는 «픽셀 Δ0» 이 아니었다 — `verify93` (알약 펄스 비트)

전수 스윕에서 **`verify93` 만 새로 빨개졌다**(23/26 · 3회 재실행 전부 같은 값 = 플레이키가 아니다).
`FX3_GINK` 를 108.3 으로 되돌린 사본을 만들어 **원인을 한 상수로 좁혔다** — 그 사본은 **26/26 초록**이다.

뿌리는 되돌릴 수 없는 것이었다. `FX3_GINK` 는 알갱이의 **잉크 지름**이고 그 상수의 끝 계수가 바로
`cur-dia.svg` 의 채움비다(`55 × 2.10 × 0.938`). 644 로 채움비가 1.0 이 되었으므로 실제 잉크가
**108.3 → 115.5** 다 — 108.3 을 그대로 두면 상수가 잉크를 **속이고** 알갱이가 6.7% 겹치게 깔린다
(`verify543` [D] 가 즉시 잡는다). 543 의 설계가 «크기를 개수와 맞바꾼다» 이므로 밴드 피치·최소 중심거리
(`FX3_MIND` 123 → **132**)가 같이 커졌고 **UI 발 슬롯이 4 → 3** 이 됐다.

⇒ 3 은 이 화면의 **사양 하한**이다 — 93 자신의 «UI 발 3~6개» · `verify58` [2] ·
`verify543` [D](«개수가 3 밑으로 안 내려간다»)가 **같은 수**를 쓴다.
한쪽만 묻던 «≥4» 를 **양쪽을 묻는 «3..6»** 으로 옮겼다 — **위반 방향이 하나 늘었으므로 순 손실이 아니다**.
그리고 이 항은 여전히 기하에 물려 있다(알갱이를 다시 줄이면 개수가 저절로 4 로 돌아온다 — 위 되돌림 사본이 증거).
