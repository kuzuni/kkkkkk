## §1 등재문과 무엇이 달랐나 — 재현이 «조용함» 의 정체를 한 칸 정정했다

등재문은 «`--release` 를 부른 직후 stderr 에 Node 배너만 남고 **조용히 끝났다**» 고 적었다.
`tools/probe571.js`(신설)로 진짜 bare 원격 + 클론 2개를 세워 그 상황을 그대로 굴려 보니
**조용한 것은 claim.js 가 아니라 git 이었다.**

| 축 | 실측 |
|---|---|
| [1] `git -c rebase.autoStash=true pull --rebase` 가 stash pop 충돌 | **종료 코드 0** · 트리에 `UU docs/PROGRESS.md` · `stash@{0}: autostash` 보존 · stderr 에 «Applying autostash resulted in conflicts» |
| [2] 그 뒤 `git commit` | **코드 128** — «Committing is not possible because you have unmerged files» |
| [3] 지시서 [1] 이 시키는 `git add -A` + 커밋 | **코드 0 — 병합 표시가 그대로 커밋된다** |
| [4] 수리 전 `claim.js --release` | **코드 1 · lock 은 이미 지워진 뒤** = «반쯤 해제» |
| [5] 음성 대조(상류와 안 겹치는 더러운 트리) | 선점 0 · 해제 0 · 미커밋 파일 보존 |

⇒ **뿌리는 [1] 한 줄이다.** claim.js 116~122행의 방어는 `gitQ(...) === null`(= 종료 코드 ≠ 0) 뿐인데,
autostash pop 충돌은 **rebase 자신은 성공**이라 코드 0 으로 끝난다. 그래서 그 검사를 그대로 통과하고,
claim.js 는 병합 표시가 남은 트리 위에서 계속 굴러갔다.

그 다음이 등재문이 본 «Node 배너» 다 — release 경로는 `fs.unlinkSync(LOCK)` 로 **lock 을 먼저 지우고**
`git('commit', …)`(throw 판)을 부르는데 [2] 때문에 그 커밋이 128 로 거부되어 **uncaught 예외**가 됐다.
즉 사고 시점의 상태는 «조용히 성공» 이 아니라 **«lock 은 사라졌는데 커밋은 없는 반쯤 해제»** 였고,
워커가 그 뒤 지시서대로 `git add -A` 를 하자 [3] 이 그 삭제와 병합 표시를 **한 커밋에 같이** 담았다
(`618d000`: PROGRESS 569 행 두 벌 · LESSONS 에 표시 3줄).

## §2 처방 — 등재문 후보 ⓐ + ⓒ 를 골랐다 (ⓑ 는 기각)

- **ⓐ `claim.js` — 조용한 성공을 종료 코드로 바꾼다.** `pull` 직후(그리고 pull 전에도)
  `git diff --name-only --diff-filter=U` 로 unmerged 경로를 직접 센다. 하나라도 있으면
  `stopOnConflict()` 가 **아무것도 지우기 전에** die(1) 한다.
  자리를 «lock 을 지우는 곳보다 앞» 으로 잡은 것이 요점이다 — **반쯤 해제가 구조적으로 불가능**해진다
  (`verify571` A5 가 소스 위치로 그것을 못박는다). 종료 코드 체계는 안 늘렸다(0/1/2 그대로, 1 = 오류).
  메시지는 «무엇이 났나 · 네 변경은 어디에 살아 있나(양쪽 표시 + `stash@{0}`) · 어떻게 푸나»
  세 줄이다 — 지시서 [4] 의 «양쪽을 모두 살린다» 를 그 자리에서 읽게 한다.
- **ⓑ «pop 을 되돌리고 멈춘다» 는 기각.** 되돌리려면 작업 트리를 HEAD 로 되감아야 하는데,
  그것이 안전하다는 근거가 «stash 가 남아 있다» 하나뿐이다. 지금 상태로도 워커의 변경은
  **두 곳(트리의 양쪽 표시 · stash)** 에 다 있어 아무것도 안 잃는다 — 지우는 쪽이 순손해다.
- **ⓒ `verifyProgress.js` §4 — 모든 워커의 push 전 문에 세운 그물.** ⓐ 는 claim.js 를 지나는 사고만
  막는다. 병합 표시가 커밋된 전례는 이번이 **두 번째**이고(363 이 `UI-REFERENCE.md` 에서 걷어냈다)
  자리를 옮겨 가며 재발하므로, «그 파일» 이 아니라 «모두가 반드시 지나는 문» 에 건다.
  지시서 [4] 가 이미 `verifyProgress` 를 그 문으로 쓰고 있어 **새 게이트를 안 만들었다.**

### §2-1 §4 는 왜 표시 «한 줄» 이 아니라 «세 짝» 을 보는가

이 저장소의 기록(PROGRESS·LESSONS·ROUTINE)은 사고를 적을 때 표시 문자열을 **인용한다** —
571 등재문 자신이 그렇다. 줄 첫머리 한 종류만 세면 그 인용이 곧바로 헛빨강이 된다.
그래서 ⓐ 열림 `<<<<<<< ` ⓑ 가름 `=======`(줄 전체) ⓒ 닫힘 `>>>>>>> ` 이 **그 순서로** 다 있어야 빨강이다.
짝이 안 맞는 한 줄은 조용히 넘기지 않고 **«관찰»** 로 세어 찍는다. 인덱스의 unmerged 항목은
해석의 여지가 없으므로 그 자체로 빨강이다.

**정밀도를 재현율 앞에 둔 이유는 §3 머리말과 같은 저울이다** — 이 자가 빨개지면 저장소 전체의
push 가 막힌다. 헛빨강 하나가 놓친 자리 하나보다 비싸다.

⚠ 그 대가로 **자·도구 소스는 표시를 줄 첫머리에 적을 수 없다.** `probe571`·`verify571`·`verifyProgress`
셋 다 표시를 **런타임에 조립**한다(`'<'.repeat(7)`). `verify571` A7 이 그 규약을 소스로 단언한다.
