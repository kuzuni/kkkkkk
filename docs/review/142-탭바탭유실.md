## 1. 재현

```
$ TAP_N=40 node tools/verify74.js
  ✗ 탭바 탭: 30/40 (75.0%)
      #2  **대상이 최상위** · 최상위=span.ti · 착지=(click 없음)
      #6  **대상이 최상위** · 최상위=span.ti · 착지=(click 없음)
      #10 **대상이 최상위** · 최상위=span.ti · 착지=(click 없음)
      #14 …  #18 …
```

실패는 **정확히 `i ≡ 2 (mod 4)`** 에서만 났다. ⑤ 대상은 `adv`(짝수 i)·`box`(홀수 i) 를 번갈아
누르므로, 실패는 전부 **«`#relw`(89 유물 페이지)가 열려 있는 상태에서 던전 탭을 누른 것»** 이다.
`착지=(click 없음)` = click 이 **아예 나지 않았다**(컨테이너로 새어 나간 것도 아니다).

74 는 네이티브 click 을 window 캡처에서 삼키고 합성 click 으로 대체하는 구조라,
**합성기가 탭을 버리면 «아무 일도 일어나지 않는다»** — 74 가 원래 잡았던 증상 그대로다.
그래서 볼 것은 «합성기의 어느 `return` 에서 버렸나» 하나뿐이고, `tools/probe142.js` 를 그것만 보게 만들었다.

## 2. 진단 ① — 제품: 롱프레스 컷이 «정체 시간» 을 접촉 시간으로 센다

`probe142` 가 찍은 실패 탭 (HOLD=90ms):

```
{"ph":"down(win)","now":5420,"ts":5138, …}          ← 이벤트 발생 5138, 핸들러 5420 (282ms 밀림)
{"ph":"up",       "now":6828,"ts":5516, …,"dt":1408, "found":"span.ti","disabled":false,"ov":"(none)"}
```

- `tapFind()` 는 대상을 **찾았고**(`found: span.ti`), `disabled` 도 아니고, 딤 가드에도 안 걸렸다.
- 그런데 `dt`(= `performance.now() - rec.t`) 가 **1408ms** 라 `TAP_MS(700)` 컷에 걸려 버려졌다.
- 그러나 **이벤트 자체의 시각**은 `5516 − 5138 = 378ms` — 롱프레스가 아니다.

즉 `performance.now() - rec.t` 는 «손가락이 닿아 있던 시간» 이 아니라
**«pointerdown 핸들러가 돈 시각 ~ pointerup 핸들러가 돈 시각»** 이고, 그 사이의
**메인 스레드 정체가 통째로 섞인다.** 정체가 700ms 를 넘는 순간 보통 탭이 롱프레스로 오판된다.

### 수정 (`index.html`)

```js
function tapDur(rec, e){
  const a = rec.ts, b = e.timeStamp;
  if(a > 0 && b > 0 && b >= a) return b - a;      /* 두 timeStamp 는 같은 시계 → 차이는 항상 유효 */
  return performance.now() - rec.t;              /* 값이 없거나 뒤집힌 브라우저용 안전망 */
}
…
tapRec = { …, t: performance.now(), ts: e.timeStamp, type: e.pointerType };
…
if(rec.type === 'touch' && tapDur(rec, e) >= TAP_MS) return;
```

`e.timeStamp` 는 **이벤트가 난 시각**이라 렌더러가 몇 초를 밀려도 그대로다.
실제 손가락은 화면이 멈춰도 90ms 만 닿아 있다 — 재는 값이 그 사실을 따라가야 한다.

## 3. 진단 ② — 하네스: touchStart 의 ack 를 기다리면 «손가락» 이 길어진다

①만 고치면 30/40 → **33/40** 으로 나아지고 멈춘다. 남은 실패의 로그:

```
{"ph":"down(win)","ts":5882, "now":6630}    ← 이벤트 5882, 핸들러 6630
{"ph":"touchstart","ts":5882}
{"ph":"up",        "ts":6723, "now":7453, "dt":822}
```

`touchStart` 와 `touchEnd` 의 **이벤트 시각 차가 841ms** 다 — HOLD 는 90ms 인데.
원인은 하네스다: `Input.dispatchTouchEvent` 는 **렌더러가 그 이벤트를 처리할 때까지 resolve 되지 않는다.**
`await touchStart` → (정체 748ms) → `sleep(90)` → `touchEnd` 순이라, 정체가 그대로
«손가락이 닿아 있던 시간» 이 된다. 제품이 아니라 **하네스가 탭을 롱프레스로 만들어 놓고** 유실을 센 것이다.

정체의 정체는 제품 결함이 아니라 **헤드리스 소프트웨어 래스터**다. CPU 프로파일(4초, 샘플 200µs):

| 구간 | longtask |
|---|---|
| 아무것도 안 열림 | 0건 |
| `#dunw` 열림 | 3건 · 합 576ms |
| **`#relw` 열림** | **4건 · 합 2254ms · 최대 1032ms** |

그런데 그 시간의 **94.9% 가 `(program)`** = JS 가 아니라 스타일·레이아웃·페인트다
(JS 최상위는 `draw` 0.6% · `loop` 0.5%). GPU 가 있는 실기기의 문제가 아니라
`swiftshader` 로 1080×2280 을 칠하는 이 컨테이너의 문제라, **89 유물 페이지를 손대지 않았다**
(그건 이 작업 단위가 아니다).

### 수정 (`tools/verify74.js`)

```js
const started = cdp.send('Input.dispatchTouchEvent', { type: 'touchStart', touchPoints: [{ x, y }] });
await new Promise(r => setTimeout(r, HOLD));
await cdp.send('Input.dispatchTouchEvent', { type: 'touchEnd', touchPoints: [] });
await started.catch(() => {});
```

CDP 는 명령 순서를 보존하므로 순서는 그대로고, 접촉 시간만 실제 90ms 가 된다.
**게이트의 강도는 내려가지 않는다** — 74 가 잡으려는 «down↔up 사이에 노드가 죽는다» 는
여전히 그 90ms 안에서 일어나고, 오히려 «하네스가 만든 롱프레스» 라는 잡음만 걷힌다.

## 7. 교훈 (LESSONS 후보)

1. **«얼마나 오래 눌렀나» 를 `performance.now()` 차로 재지 마라 — 그건 «얼마나 오래 멈춰 있었나» 다.**
   입력 지속 시간·더블탭 간격·스와이프 속도처럼 **사람의 동작**을 재는 값은 전부 `e.timeStamp`
   (이벤트가 **난** 시각)로 재야 한다. 핸들러가 돈 시각으로 재면 메인 스레드가 밀리는 순간
   사람이 하지도 않은 동작으로 오판된다 — 그리고 74 처럼 네이티브 경로를 대체해 둔 구조에서는
   그 오판이 **아무 일도 안 일어남**으로 나타나 원인을 짚기가 가장 어렵다.
2. **입력 하네스는 «명령을 언제 보냈나» 가 아니라 «이벤트가 언제 났나» 로 검산한다.**
   `Input.dispatchTouchEvent` 는 렌더러 ack 까지 기다린다 — `await` 한 줄이 90ms 짜리 탭을
   841ms 짜리 롱프레스로 바꿔 놓는다. 재현율이 «화면이 무거운 대상에서만» 떨어지면
   제품보다 먼저 **하네스의 시간축**을 의심할 것.
3. **헤드리스의 «느림» 은 대부분 제품이 아니라 소프트웨어 래스터다.** 프로파일에서
   `(program)` 이 95% 면 JS 를 최적화할 곳이 없다 — 그 화면의 CSS 를 파기 전에
   먼저 그 사실을 확인하고, 아니면 손대지 말 것(이번에 `#relw` 를 그렇게 넘겼다).
