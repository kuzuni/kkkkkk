# 58 — UI 연출 공용 모듈 (fx) · 비평 기록

> 스펙: `docs/UI-REFERENCE.md` **58번**. 레퍼런스 스크린샷이 **없는** 신규 설계라
> 채점은 ROUTINE [3]-(다) 연출 축 4개(①타이밍 ②크기 비율 ③위치·경로 ④가독성·일관성, 최저 8 통과)로 한다.
> 도구: `node cap58.js <라운드>` (연속 프레임 캡처) · `node verify58.js` (기능 체크)

## 무엇을 만들었나

`#fxl` — 프레임 전체를 덮는 `pointer-events:none` 오버레이(z-index 60, 현재 최상위 `#ciw` 41 위).
**모든 연출 DOM 은 여기에만** 만든다. 대상 요소에 클래스를 붙이지 않는 이유는 25 교훈 5 —
훈련 카드·퀘스트 행처럼 `innerHTML` 로 통째로 재렌더되는 화면에서는 대상에 붙인 클래스가 그 프레임에 날아간다.

| 함수 | 하는 일 |
|---|---|
| `fxFly(from, cur, n)` | 재화 아이콘 **3~6개**가 `from` 에서 HUD 알약의 **코인/젬 아이콘 중심**으로 2차 베지에 호를 그리며 날아가 **꽂힌다**(마지막 프레임을 중심에 정확히 세우고 `.fx-land` 140ms 로 사라진다) |
| `fxPunch(el)` | 도착 순간 알약이 튄다 (`scale 1 → 1.15 → .975 → 1`, 300ms). **진행 중이면 재시작하지 않는다** |
| `fxPlus(cur, n)` | 알약 아래 `+n` 플로팅 텍스트 (750ms). **첫 도착**에 뜬다 |
| `fxPop(el)` | 팝 `0 → 1.2 → 1` (340ms) |
| `fxBurst(t, col, n)` | 방사형 버스트 파티클 (580ms) |
| `fxFlash(el)` | 대상 bbox 위 **금색 워시 + 흰 링 + 앰버 글로우** 1회 + `scale .97 → 1.14` (400ms) |
| `fxHitEl(el)` | 대상 **자체**의 스케일 펄스 `1 → 1.07 → 1` (260ms). 재렌더 화면에서는 재렌더 «뒤» 에 부른다 |
| `fxToast(txt)` | 상단 토스트 슬라이드다운 + 스프링, 1.2초 뒤 페이드아웃. **비행 아이콘보다 위**(z 2) |
| `fxCheck(el)` | 체크 스트로크 드로잉 (`stroke-dashoffset` 애니, 700ms — 18% 지점에서 완전히 뜬다) |
| `fxUpOk(t, at)` | «강화 성공» 한 세트 = `fxFlash` + `fxHitEl` + `fxBurst` |
| `fxReward(t)` | «보상 수령» 꼬리 = 수령 지점 버스트 (이어지는 재화 비행은 자동) |
| `fxAt(t)` | «다음 재화 증가» 의 출발점 힌트(600ms 유효) |

### 전역 부착 — 호출부를 고치지 않아도 걸린다

- **재화 획득**은 `fxWatch()` 가 매 프레임 `S.gold`/`S.dia` 의 **증가분**을 감시해 자동으로 쏜다.
  드랍·보상·판매·룰렛·우편 어느 경로로 늘어도 붙고, **앞으로 생길 경로도 자동 편입**된다
  (46 교훈 3 «모든 경로가 지나는 한 지점» 의 UI 판). 감소(소모)에는 걸지 않는다.
  잘게 들어오는 연속 킬은 **70ms 정지 또는 900ms 누적**으로 묶어 한 번에 쏜다 — 아이콘 폭탄 방지.
  «공중에 떠 있는 총합» 은 `FXFLY_MAX 12` 로 묶는다(골드·다이아가 같이 들어오면 묶음이 둘이라 두 배가 된다).
- **출발점**도 전역이다. `pointerdown` 캡처 리스너 하나가 마지막으로 누른 버튼·카드를 기억하고,
  명시 힌트(`fxAt`)와 «더 최근» 것을 쓴다. 그래서 새 화면이 아무것도 안 해도 «수령 버튼에서 재화가 날아가는» 그림이 된다.
  자동 전투는 `killEnemy()` 가 킬마다 `fxAt(fxWorld(e.x, e.y-e.r))` 를 불러 «적이 죽은 자리» 가 이긴다.
- **숫자 롤링**은 `fxDisp` 라는 «표시값» 을 두고 `drawHud()`·`renderPcb()`(41 팝업 내장 재화 바)가 둘 다 그 값을 읽는다.
  두 곳이 다른 숫자를 보이면 안 되므로 단일 소스로 묶었다. 롤링은 **고정 길이 트윈**(`FXROLL` 0.3초,
  easeOutCubic)이고, 증가를 감지하면 **코인이 첫 도착할 때까지 홀드**한다 — 그래야 «꽂히니까 오른다» 가 된다
  (홀드는 1.4초 뒤 스스로 만료돼, 비행이 안 뜨는 경로에서도 숫자가 굳지 않는다).

## 회차 기록

### 1·2회차 (2026-08-25, sess-0028-6966 워커 B) — 모듈 신설 + 타이밍 정합

모듈을 올리고 `verify58.js`(기능 체크)로 자체 검증. 이때 캡처는 `page.screenshot()` 기반이었다.

### ⚠ 1차 비평 (비평가 A·B) — **캡처 절차 오류로 무효 판정**

두 비평가가 **독립적으로 «연출 없음 · 0점»** 을 냈다. 지적 요지는 셋 다 같았다 —
«코인이 날아가는 프레임이 0장», «흰 플래시가 0프레임», «숫자가 트윈 없이 순간 점프».

그런데 같은 빌드에서 `verify58.js` 는 **비행 8개 · 알약 아이콘 중심에 0px 도착 · 연출 길이 691ms ·
플래시가 카드 bbox 와 Δ0 · 토스트/체크/버스트 생성**을 전부 통과했다. 둘 중 하나가 틀린 것이다.

원인은 **캡처였다.** 이 컨테이너에서 `page.screenshot()` 1080×2280 한 장이 **337~629ms** 걸린다.
스크립트에 «90ms 간격» 이라고 적어 놔도 실제 간격은 **430~720ms** 라,
0.3~0.8초짜리 연출이 8프레임 중 1~2장에만 걸린다. 비평가들이 본 «연출 없음» 은 사실이었지만
그건 구현이 아니라 **그 이미지들** 에 대한 사실이었다.
→ 04 교훈 1 «캡처 상태가 레퍼런스와 다르면 그 회차 비평은 통째로 무효» 의 **연출 판**.
1차 비평은 폐기하고 회차만 소모한 것으로 센다.

### 3회차 — 캡처를 CDP 스크린캐스트로 교체

`Page.startScreencast` 로 **렌더된 프레임을 타임스탬프째로** 받아 두고, 트리거 기준
0·90·…·630ms 에 가장 가까운 8장을 골라 저장하도록 `cap58.js` 를 다시 썼다.
결과: 목표 대비 **최대 ±63ms**, 원본 프레임 20~37장. 이제 8장이 실제로 0~0.65초를 덮는다.

같이 넣은 결정성 장치(앞 세션 교훈의 재적용):
- `window.step = () => {}` 로 **게임 로직만 정지**시킨다 — 캔버스의 스킬 이펙트·경험치·자동 진행이
  프레임마다 바뀌면 «연출 때문에 바뀐 것» 과 구분이 안 된다. `draw()`/`fxTick()` 은 계속 돈다.
  (1차 비평가 A 가 «정체불명의 회색 스우시가 HUD 반대 방향으로 표류한다» 로 잡은 것이 이 노이즈였다)
- 적은 **비우지 말고 멀리 주차** + `player.inv` (42 교훈 1·2).
- 씬1 의 `t0` 는 «S 증가 시각» 이 아니라 **«첫 비행 아이콘이 생긴 시각»** 으로 잡는다 —
  `fxWatch` 의 묶음 디바운스(180ms)만큼 앞이 비면 8프레임 중 앞 두 장이 정지 화면으로 낭비된다.

`+ 이번 회차에 같이 고친 것`: 비행의 **마지막 프레임을 알약 중심에 «정확히» 세우고** 짧게 사라지게 했다
(`.fx-land`, 140ms). 바로 `remove()` 하면 렌더된 마지막 위치가 `p<1` 이라 도착이 몇 px 모자란 채로 끝난다 —
`verify58` 의 «최근접» 이 8px → **0px** 이 됐다. 전체 길이는 `0.030*7 + 0.43 + 0.14 = 0.78초` 로 스펙(0.3~0.8초) 안.

### 3회차 비평 (비평가 C·D) — ①0/②0/③1/④0 · ②2/③2/④2

캡처가 정상이 되자 **둘이 독립적으로 같은 5가지**를 짚었다. 자체 픽셀·DOM 프로브로 전부 재현시켜 확인했고,
**5건 다 실제 결함이었다**(«비평가 수치는 확인 전엔 반영하지 마라» 로 반증을 시도했지만 이번엔 반증이 안 됐다):

| 지적 | 자체 프로브 재현 | 처방 |
|---|---|---|
| 코인이 화면 위쪽에서 **잘려 사라진다** | 비행 요소 y 최솟값 **−12px**, 프레임 밖 샘플 6건 | 제어점 y 를 `max(96, …)` 로 클램프 → **−12 → 0px, 밖 0건** |
| `+n` 이 **647ms 에야** 뜬다 | `fxPlus` 를 «마지막 아이콘 도착» 에 걸어 뒀다 | **«첫 도착»** 으로 옮김 |
| 숫자가 코인 도착 **전에** 다 올라간다(순서 역전) | 롤링이 `S` 변경 즉시 시작 | 비행이 뜨면 표시값을 **홀드**, 첫 도착에 해제(1.2초 안전 만료) |
| 강화 플래시가 **«회색 비활성»** 으로 읽힌다 | 흰 오버레이 opacity **90ms 0.76 → 186ms 0.36 → 278ms 0.03** — 30~40% 흰 워시가 오래 남는다 | 곡선을 세게 번쩍이게: **90ms 0.91 → 186ms 0.22 → 278ms 0.00** |
| 카드가 **커졌다 복귀하지 않는다** | 오버레이만 scale, **카드 bbox 는 전 프레임 동일** | `.fx-hit` 를 **대상 요소 자체**에 건다(`scale 1→1.07→1`, 260ms). 재렌더에 지워지므로 **재렌더 «뒤»** 에 붙인다 |
| 퀘스트 씬에서 아이콘 7~9개가 **617ms 까지 남아 헤더·HUD 를 가린다** | 골드·다이아 두 묶음이 겹쳐 최대 16개 | 개수 3~8 → **3~6**, «공중에 떠 있는 총합» `FXFLY_MAX 12` 상한, 묶음 디바운스 180 → **110ms** |

체크 스트로크도 같이 당겼다 — 페이드인이 완만해 «체크가 350ms 뒤에야 보인다» 였던 것을
`fxCheckIn` 18% 지점에서 완전히 뜨게 고쳤다(90ms **0.39 → 0.64**, 186ms **0.76 → 1.00**).

### 4회차 — 위 6건 반영 후 재캡처(r3)

### 4차 비평 (비평가 E·F) — 최저 2점 · 2점

또 둘이 독립적으로 같은 곳을 짚었다. 이번에도 **자체 계측으로 전부 재현**됐고, 그중 둘은
**내 앞선 계측이 틀렸다는 것**까지 드러났다.

| 지적 | 자체 계측 | 처방 |
|---|---|---|
| 숫자 롤링이 **645ms 에 목표의 26%** 만 진행 — 0.8초 안에 못 끝난다 | 지수 수렴(`d += d*dt*7`)은 남은 차이를 반씩만 줄여 «끝나는 시각» 이 없다. 실측 완료 **888ms** | **고정 길이 트윈**(easeOutCubic, `FXROLL`)으로 교체 → 완료 **738ms** |
| 알약이 **튀는 프레임이 한 장도 없다** | 아이콘 6개가 30ms 간격으로 도착하며 `fxPunch` 가 **매번 애니메이션을 재시작** → scale 1.02 를 못 넘는다 | 한 번 튀는 동안(300ms)은 재시작 금지 → 최대 확대 **×1.16** |
| 강화 플래시가 **8프레임 전부에 없다** | ⚠ **비평가가 맞았다.** 픽셀로 재니 흰 오버레이가 있긴 했는데 **훈련 카드 배경이 `#FFFDF2`(휘도 252)** 라 알파 .9 를 깔아도 **합성 채널 변화가 +2** 다 — 물리적으로 안 보인다 | 코어를 **금색 워시 + 흰 링 + 앰버 글로우**로 교체 → 채널 변화 **110**, 카드 영역 픽셀 Δ **55·60·44**(3프레임) |
| 카드가 **커졌다 복귀하지 않는다** | `.fx-hit` 를 대상에 걸었지만 `renderUI()` 가 0.35초 주기로 시트를 재렌더해 **90ms 안에 지워진다** | 스케일은 **오버레이가** 맡고(1→1.09→1.14), `.fx-hit` 는 재렌더 «뒤» 에 다시 건다 |
| 연출 시작이 늦다 | 오버레이를 `renderTrain()` **뒤에** 불러서 재렌더 비용만큼 밀렸다 — 클릭 후 **130ms** | 오버레이는 **재렌더 «전»** 에 부른다(#fxl 에 있어 재렌더에 안 지워진다) → **5ms** |
| 코인 경로가 **2단 꺾임** | 제어점 x·y 를 각각 랜덤으로 흔들어 아이콘마다 다른 방향으로 휘었다 | 제어점을 **«직선의 중점에서 수직 방향으로»** 밀어내고 휨 폭만 아이콘별로 다르게 |
| 재화가 **토스트 글자를 가린다** | 둘 다 `#fxl` 안이고 z 순서가 DOM 순서였다 | `.fx-toast{z-index:2}` / `.fx-fly{z-index:1}` — 코인이 토스트 **뒤로** 지나간다 |

> **여기서 얻은 계측 교훈 하나 더**: 앞 회차의 «플래시 opacity 0.91@90ms» 프로브는 **틀린 값**이었다.
> `await sleep(t - prev)` 로 시각을 누적하면 매 호출이 오버슈트해 «t=66ms» 라벨이 실제로는 150ms 다.
> 고정 간격(10ms) 폴링으로 `Date.now() - t0` 를 **매 샘플마다 다시 읽어야** 궤적이 맞다.

### 5회차 — 위 7건 반영 후 재캡처(r5)

`verify58.js` 에 «비평가 없이도 같은 결함을 잡는» 항목 6개를 추가했다 —
**클릭→가시 지연 ≤140ms · opacity≥0.7 유지 ≥150ms · 카드 위 최대 채널 변화 ≥45 ·
알약 확대 ≥×1.10 · 숫자가 코인 도착 «뒤» 에 시작 · 롤링 완료 ≤800ms.**

## 이 작업에서 나온 교훈 (LESSONS 로 옮길 것)

1. **연출 채점에 `page.screenshot()` 을 쓰면 회차가 통째로 날아간다.** 이 컨테이너에서 1080×2280
   한 장이 337~629ms 다. 스크립트에 «90ms 간격» 이라 적어도 실제는 430~720ms 라, 0.3~0.8초짜리
   연출이 8프레임 중 1~2장에만 걸린다. 비평가 2명이 독립적으로 «연출 없음 0점» 을 냈고 **틀린 것은
   구현이 아니라 캡처 절차**였다. → **CDP `Page.startScreencast`** 로 렌더 프레임을 타임스탬프째 받아
   원하는 시각에 가장 가까운 장을 고른다(±63ms 안에 들어온다). 04 교훈 1 의 연출 판.
2. **연출 캡처는 «게임을 멈추고» 찍어라.** `window.step = () => {}` 로 로직만 죽이면 `draw()`·`fxTick()`
   은 계속 돌아 연출은 그대로 보이면서 캔버스 노이즈(스킬 이펙트·자동 진행·경험치)가 사라진다.
   안 멈추면 비평가가 «정체불명의 회색 스우시가 HUD 반대 방향으로 표류한다» 같은 지적을 물고 온다
   (28 교훈 3 «캔버스가 스캔을 오염시킨다» 의 연출 판).
3. **«흰 플래시» 는 빠지는 곡선이 전부다.** opacity 를 완만히 빼면 30~40% 흰 워시 구간이 200ms 넘게
   남고, 사람은 그걸 «번쩍» 이 아니라 **«탈채도 = 비활성/잠김»** 으로 읽는다(비평가 2명이 독립적으로
   «회색이라 성공인데 실패처럼 보인다» 라고 했다). 세게 올리고 빨리 빼라.
4. **오버레이만 키우면 «커졌다» 로 안 읽힌다.** `#fxl` 오버레이에 `scale` 을 걸어도 **대상 카드의 bbox 는
   그대로**라 비평가가 «크기 변화 0%» 로 잡는다. 스케일 펄스는 **대상 요소 자체**에 걸어야 하고,
   `innerHTML` 재렌더 화면에서는 **재렌더 «뒤»** 에 붙여야 살아남는다(25 교훈 5 의 클래스 판).
5. **«도착하면 오른다» 는 순서를 코드로 못박아야 한다.** 재화가 늘어난 «즉시» 숫자를 굴리면 코인이
   도착하기 전에 카운터가 다 올라가 버려 인과가 뒤집힌다. 비행이 뜨는 순간 표시값을 **홀드**하고
   첫 도착에서 푼다(비행이 안 뜨는 경로를 위해 **만료 시각**을 같이 둘 것 — 안 두면 숫자가 영영 굳는다).
6. **동시 비행 상한은 «묶음당» 이 아니라 «공중에 떠 있는 총합» 으로 잡아라.** 골드·다이아가 같이
   들어오는 보상에서는 묶음이 둘이라 개수가 두 배가 되고, 그게 모달 헤더와 HUD 숫자를 가린다.
