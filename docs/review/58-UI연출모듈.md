# 58 — UI 연출 공용 모듈 (fx) · 비평 기록

> 스펙: `docs/UI-REFERENCE.md` **58번**. 레퍼런스 스크린샷이 **없는** 신규 설계라
> 채점은 ROUTINE [3]-(다) 연출 축 4개(①타이밍 ②크기 비율 ③위치·경로 ④가독성·일관성, 최저 8 통과)로 한다.
> 도구: `node cap58.js <라운드>` (연속 프레임 캡처) · `node verify58.js` (기능 체크)

## 무엇을 만들었나

`#fxl` — 프레임 전체를 덮는 `pointer-events:none` 오버레이(z-index 60, 현재 최상위 `#ciw` 41 위).
**모든 연출 DOM 은 여기에만** 만든다. 대상 요소에 클래스를 붙이지 않는 이유는 25 교훈 5 —
훈련 카드·퀘스트 행처럼 `innerHTML` 로 통째로 재렌더되는 화면에서는 대상에 붙인 클래스가 그 프레임에 날아간다.

| 함수 | 하는 일 |
|---|---|
| `fxFly(from, cur, n)` | 재화 아이콘 3~8개가 `from` 에서 HUD 알약의 **코인/젬 아이콘 중심**으로 2차 베지에 호를 그리며 날아가 꽂힌다 |
| `fxPunch(el)` | 도착 순간 알약이 튄다 (`scale 1 → 1.15 → .975 → 1`, 300ms) |
| `fxPlus(cur, n)` | 알약 아래 `+n` 플로팅 텍스트 (750ms) |
| `fxPop(el)` | 팝 `0 → 1.2 → 1` (340ms) |
| `fxBurst(t, col, n)` | 방사형 버스트 파티클 (580ms) |
| `fxFlash(el)` | 대상 bbox 위 흰 플래시 1회 + `scale 1.045` (340ms) |
| `fxToast(txt)` | 상단 토스트 슬라이드다운 + 스프링, 1.2초 뒤 페이드아웃 |
| `fxCheck(el)` | 체크 스트로크 드로잉 (`stroke-dashoffset` 애니, 800ms) |
| `fxUpOk(t, at)` | «강화 성공» 한 세트 = `fxFlash` + `fxBurst` |
| `fxReward(t)` | «보상 수령» 꼬리 = 수령 지점 버스트 (이어지는 재화 비행은 자동) |
| `fxAt(t)` | «다음 재화 증가» 의 출발점 힌트(600ms 유효) |

### 전역 부착 — 호출부를 고치지 않아도 걸린다

- **재화 획득**은 `fxWatch()` 가 매 프레임 `S.gold`/`S.dia` 의 **증가분**을 감시해 자동으로 쏜다.
  드랍·보상·판매·룰렛·우편 어느 경로로 늘어도 붙고, **앞으로 생길 경로도 자동 편입**된다
  (46 교훈 3 «모든 경로가 지나는 한 지점» 의 UI 판). 감소(소모)에는 걸지 않는다.
  잘게 들어오는 연속 킬은 **180ms 정지 또는 900ms 누적**으로 묶어 한 번에 쏜다 — 아이콘 폭탄 방지.
- **출발점**도 전역이다. `pointerdown` 캡처 리스너 하나가 마지막으로 누른 버튼·카드를 기억하고,
  명시 힌트(`fxAt`)와 «더 최근» 것을 쓴다. 그래서 새 화면이 아무것도 안 해도 «수령 버튼에서 재화가 날아가는» 그림이 된다.
  자동 전투는 `killEnemy()` 가 킬마다 `fxAt(fxWorld(e.x, e.y-e.r))` 를 불러 «적이 죽은 자리» 가 이긴다.
- **숫자 롤링**은 `fxDisp` 라는 «표시값» 을 두고 `drawHud()`·`renderPcb()`(41 팝업 내장 재화 바)가 둘 다 그 값을 읽는다.
  두 곳이 다른 숫자를 보이면 안 되므로 단일 소스로 묶었다.

## 회차 기록

### 1·2회차 (2026-08-25, sess-0028-6966 워커 B) — 모듈 신설 + 타이밍 정합

모듈을 올리고 `verify58.js`(기능 체크)로 자체 검증. 이때 캡처는 `page.screenshot()` 기반이었다.

### ⚠ 1차 비평 (비평가 A·B) — **캡처 절차 오류로 무효 판정**

두 비평가가 **독립적으로 «연출 없음 · 0점»** 을 냈다. 지적 요지는 셋 다 같았다 —
«코인이 날아가는 프레임이 0장», «흰 플래시가 0프레임», «숫자가 트윈 없이 순간 점프».

그런데 같은 빌드에서 `verify58.js` 는 **비행 8개 · 알약 아이콘 중심에 0px 도착 · 연출 길이 691ms ·
플래시가 카드 bbox 와 Δ0 · 토스트/체크/버스트 생성**을 전부 통과했다. 둘 중 하나가 틀린 것이다.

원인은 **캡처였다.** 이 컨테이너에서 `page.screenshot()` 1080×2280 한 장이 **337~629ms** 걸린다.
스크립트에 «90ms 간격» 이라고 적어 놔도 실제 간격은 **430~720ms** 라,
0.3~0.8초짜리 연출이 8프레임 중 1~2장에만 걸린다. 비평가들이 본 «연출 없음» 은 사실이었지만
그건 구현이 아니라 **그 이미지들** 에 대한 사실이었다.
→ 04 교훈 1 «캡처 상태가 레퍼런스와 다르면 그 회차 비평은 통째로 무효» 의 **연출 판**.
1차 비평은 폐기하고 회차만 소모한 것으로 센다.

### 3회차 — 캡처를 CDP 스크린캐스트로 교체

`Page.startScreencast` 로 **렌더된 프레임을 타임스탬프째로** 받아 두고, 트리거 기준
0·90·…·630ms 에 가장 가까운 8장을 골라 저장하도록 `cap58.js` 를 다시 썼다.
결과: 목표 대비 **최대 ±63ms**, 원본 프레임 20~37장. 이제 8장이 실제로 0~0.65초를 덮는다.

같이 넣은 결정성 장치(앞 세션 교훈의 재적용):
- `window.step = () => {}` 로 **게임 로직만 정지**시킨다 — 캔버스의 스킬 이펙트·경험치·자동 진행이
  프레임마다 바뀌면 «연출 때문에 바뀐 것» 과 구분이 안 된다. `draw()`/`fxTick()` 은 계속 돈다.
  (1차 비평가 A 가 «정체불명의 회색 스우시가 HUD 반대 방향으로 표류한다» 로 잡은 것이 이 노이즈였다)
- 적은 **비우지 말고 멀리 주차** + `player.inv` (42 교훈 1·2).
- 씬1 의 `t0` 는 «S 증가 시각» 이 아니라 **«첫 비행 아이콘이 생긴 시각»** 으로 잡는다 —
  `fxWatch` 의 묶음 디바운스(180ms)만큼 앞이 비면 8프레임 중 앞 두 장이 정지 화면으로 낭비된다.

`+ 이번 회차에 같이 고친 것`: 비행의 **마지막 프레임을 알약 중심에 «정확히» 세우고** 짧게 사라지게 했다
(`.fx-land`, 140ms). 바로 `remove()` 하면 렌더된 마지막 위치가 `p<1` 이라 도착이 몇 px 모자란 채로 끝난다 —
`verify58` 의 «최근접» 이 8px → **0px** 이 됐다. 전체 길이는 `0.030*7 + 0.43 + 0.14 = 0.78초` 로 스펙(0.3~0.8초) 안.

  같은 파일 구역에 추가하면 된다 — 60 은 «누르는 손맛·팝업 열고 닫기» 라 대상 요소 자체에
