## 2. 왜 흔들렸나 — 산술까지 맞춘 원인

G6 은 제품(`openShopPage(focus)`, index.html ~20833)과 **글자 그대로 같은 식**을 다시 계산해 비교한다:

```
top  = card.offsetTop − children[0].offsetTop
want = clamp(top, 0, scrollHeight − clientHeight)
```

펫 상자는 `SHOP_BOXES` 의 **마지막 칸**이라 `top`(실측 **1916**, 전 표본 고정)이 스크롤 여지를 한참 넘어
**클램프가 항상 이긴다** → `want` 는 사실상 `scrollHeight − clientHeight` 하나다.
즉 흔들린 값은 `#shopList.scrollHeight` 뿐이다.

프레임 단위 표본(`tools/probe226.js` · `tools/probe226b.js`):

```
   0~200ms  sh=2428 …                      (기준)
 300~410ms  sh=2429 ~ 2433  ← 이 프레임에서만 튄다
            바닥을 미는 노드 = DIV.shp-card jz-st  (마지막 칸)
```

원인은 **136 이 `verify102` 에서 잡은 것과 같은 연출**이다 — 60 `jzStagger` 의 카드 등장
`.jz-st{animation:jzSt .2s}`(index.html 10184)는 키프레임이 `scale:.94 → 1.02 → 1` 이고,
**CSS 의 «스크롤 가능 오버플로 영역» 은 변환된 박스들의 합집합**이라 `scale(1.02)` 이 걸린 동안
마지막 카드가 자기 중심 아래로

```
450px(카드 높이) × 0.02 / 2 = 4.5px
```

삐져나온다 → `scrollHeight` **+4~5** → `want` **+4~5**. 보고된 어긋남(+4 / +5)과 산술이 정확히 맞는다.

`tools/probe226d.js`(클릭 후 1.2초를 프레임마다 훑는다)로 그 프레임을 직접 잡았다:

```
  538ms  scrolled=586 want=589 (Δ3)  sh=2431  jz-st=true  scale=1.01276
  552ms  scrolled=586 want=591 (Δ5)  sh=2433  jz-st=true  scale=1.02      ← 등재된 FAIL 값과 동일
```

- **`scrollTop` 은 전 프레임 586 고정**(값 집합 `[586]`) — 흔들린 쪽은 오직 **게이트가 재는 시점**이다.
- 마지막 칸의 위상은 `--jzd = 60 + 4×25 = 160ms` · 길이 `.2s` 인데, 실측 **절대** 시각은 클릭 후 **≈530~560ms**
  다(스태거는 `openShopPage()` 의 렌더·`jz-pg` 뒤에 출발한다). 게이트의 고정 대기가 **500ms** 라
  **창의 바로 앞턱**에 서 있었고, 부하에 따라 물기도 비켜 가기도 했다 = «간헐».
- 헤드리스에서 rAF 가 ~70ms 로 throttle 돼 1.2초에 15~17 프레임뿐이라 **한 프레임이 그대로 한 회**다.

## 3. 제품은 왜 무결인가

제품이 연출 중의 부푼 `scrollHeight` 로 `scrollTop` 을 넣어도, 연출이 끝나면 브라우저가
**실제 최대치로 다시 클램프**한다. 착지점은 언제나 586 이고 그것이 옳은 값이다
(`G6b` 로 «펫 칸이 리스트 안에 통째로 보인다 450/450px» 를 별도 단언으로 못 박았다).
따라서 등재문의 갈래 중 **ⓑ 게이트 부패(재는 시점)** 가 맞고, ⓐ 제품 4px 밀림은 **반증**됐다.

## 4. 고친 것 — `tools/verify106.js` 만

1. `settleList()` 신설 — `#shopList` 의 `scrollHeight · clientHeight · scrollTop` 과
   **마지막 카드 rect** 가 **4 프레임 연속 같아질 때까지** 폴링(상한 4s). 102/136 의 `settle` 선례를 따랐다.
   고정 대기를 늘리는 처방은 쓰지 않았다 — 102 가 이미 기각했고(시작 시각이 부하로 100ms 넘게 밀린다),
   221-③ 의 «대기 ms 를 늘리는 것은 고치는 게 아니라 확률을 낮추는 것» 과 같은 이유다.
2. `G5b` 신설 — «잰 순간이 연출 도중이 아니었다» 를 **단언으로 못 박는다**(221-③). 수렴 실패는 FAIL 이다.
   rect 를 움직이는 무한 연출이 앞으로 붙으면 조용히 새는 대신 여기가 빨개진다.
3. `G6b` 신설 — 클램프 산술과 **무관하게** 성립해야 하는 사용자 쪽 뜻(«펫 칸이 리스트 뷰포트에 통째로
   들어왔나»)을 따로 잰다. G6 이 언젠가 또 산술 문제로 흔들려도 «스크롤이 실제로 됐나» 는 여기서 지킨다.

`index.html` 은 **한 글자도 안 바꿨다.**
