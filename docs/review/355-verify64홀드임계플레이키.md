## 1. 등재문의 가설을 재현으로 **확인**했다 (338 규칙 — 처방을 따르기 전에 재현)

등재문: «하네스가 «300ms 동안 누르고 있음» 을 `waitForTimeout` 으로 재는데, 머신이 밀리면 실제 접촉이
350ms 임계를 넘겨 반복이 한 번 더 돈다(Δ2). 제품이 아니라 **자가 타이밍 경합**이다.»

`tools/probe355.js` 를 신설해 페이지가 **스스로 찍은** 시각으로 두 가지를 잡았다 —
ⓐ 실제 접촉 구간(`pointerdown`→`pointerup`, capture 리스너) ⓑ `trainBuy` 가 **성공한** 시각(접촉 시작 기준 상대 ms).
왕복 지연이 섞이지 않는다.

### 한가할 때 (10회) — 이미 여유가 10ms 밖에 없다

```
접촉 311.2 · 315.9 · 317.3 · 321.9 · 322.3 · 327.5 · 328.9 · 331.6 · 334.2 · 339.8 ms   (요청 300ms)
임계(350ms) 초과 0/10 · 옛 단언이 빨개지는 실행 0/10
```

**요청 300ms 는 한 번도 300ms 가 아니었다** — 최소 +11ms, 최대 +40ms 로 이미 밀려 있고
임계까지 남은 여유는 **10ms** 다. 게이트는 처음부터 동전 던지기 위에 서 있었다.

### 부하를 걸었을 때 (`--load`, 코어 4개 점유 · 10회) — 재현

```
# 1  접촉  441.7ms · Δ2 · 구매 t=[1, 382]     ← 옛 단언 빨강
# 6  접촉  359.2ms · Δ1 · 구매 t=[1]          ← 임계를 넘겼는데 반복은 안 돌았다(초록)
그 밖 8회 접촉 313~338ms · Δ1
임계 초과 2/10 · 옛 단언이 빨개지는 실행 1/10   (= 등재문의 «5회 중 1회» 와 같은 자리)
```

**#1 은 제품이 규약대로 동작한 실행이다** — 접촉이 441.7ms 였고 첫 반복이 **382ms**(≥350) 에 돌았다.
즉 빨간 것은 제품이 아니라 **자**였다. #6 은 그 반대편 동전 — 접촉이 359ms 로 임계를 넘겼는데도
타이머 콜백이 뗌보다 늦어 Δ1 로 초록이었다. **양쪽 다 «운»** 이라는 것이 이 결함의 전부다.

제품 무결의 직접 증거도 같은 실행에서 나왔다 — **임계 전에 반복이 돈 실행 0/20**(한가할 때·부하 때 전부).

## 2. 처방 — 벽시계를 버리고 **실측 접촉 구간**에서 센다

등재문이 준 두 방향(«§4 방식으로 접촉 구간 안의 횟수를 센다» / «접촉이 350ms 를 넘은 실행은 측정 무효로 다시 던진다»)을
**둘 다** 썼다. 둘은 배타적이지 않고, 각각 다른 단언을 지킨다.

`verify64.js` 에 공용 도구 셋을 신설했다(§4 가 이미 쓰던 방식의 공용화):

| 도구 | 하는 일 |
|---|---|
| `holdM(page, sel, ms)` | 누르고 떼되, **페이지가 찍은** `{ hold: 실측 접촉 ms, t: [구매 시각…] }` 을 돌려준다 |
| `holdValid(…, valid)` | 접촉이 원하는 구간에 못 들면 «측정 무효» 로 최대 4회 다시 던진다(305·303·344 계열) |
| `beforeThr(m, THR)` | 임계 **전** 에 성립한 구매 수 |

### §3 이 원래 재려던 것 = «임계 전에 반복이 도는가»

| 옛 단언 | 새 단언 |
|---|---|
| `waitForTimeout(300)` 뒤 `Δ === 1` | `TR_HOLD_DELAY === 350` (임계 상수 못 pin) |
| | 접촉 시작~임계 구매 **1회뿐**(`beforeThr === 1`) — 기계 속도 무관 |
| | 뗀 뒤 구매 0(`t ≤ hold + 40`) |
| `waitForTimeout(420)` 뒤 `Δ === 2` | 접촉이 **임계+60ms 이상인 실행**(아니면 다시 던진다)에서 반복 ≥1 |
| | 첫 반복이 임계 직후다(≥350ms · 임계+200ms 이내) |

새 단언은 **접촉이 얼마나 밀리든 부호가 안 바뀐다.** 밀린 접촉에서 반복이 한 번 더 도는 것은
규약이 그렇게 시킨 것이므로 이제 초록이고, **임계 자체가 무너지면 즉시 빨개진다.**

### 무르게 푼 것이 아님 — 되돌림 시험

`probe355` 는 마지막에 임계를 **100ms 로 낮춘 제품**을 주입한다(`trHoldStart` 를 감싸 타이머만 100ms 로).

```
되돌림(임계 100ms): 접촉 342ms · 구매 t=[1, 127, 308]   → «임계 전 구매 1회» 3회로 깨짐 = 빨강
원복 후                                                  → 다시 1회 = 초록
```

옛 자도 이 회귀에서는 빨개진다(Δ3). 다른 점은 **거짓 빨강이 없다는 것**이다 —
옛 자는 «임계가 무너진 제품» 과 «접촉이 밀린 건강한 실행» 을 **같은 빨강**으로 찍어 구별할 수 없었고,
새 자는 앞의 것만 빨갛다.

## 3. 전수 스윕 — 같은 병을 앓던 자리가 셋 더 있었다

`verify64` 안에서 «고정 대기 시간을 눌러 둔 시간으로 믿고 **정확한 횟수**를 단언» 하는 자리를 전부 셌다.

| 절 | 옛 단언 | 처리 |
|---|---|---|
| §2 | `hold 80` → `Δ === 1` | 접촉이 임계 밑인 실행에서만 판정(`holdValid`) + «접촉 밖 구매 0» |
| §3 | `hold 300` → `Δ===1` · `hold 420` → `Δ===2` | 위 표대로 재작성 |
| §7 | `hold 420` → `Δ === q × 2` | **`Δ === q × 실측 구매 수`** — 배수 규약은 그대로 지키고 밀린 접촉에 안 흔들린다 |
| §8 | `hold 420` → `Δhp === 2` | 임계 전 1회 + 반복 ≥1 + `Δhp === 실측 구매 수` |

건드리지 않은 자리(같은 병이 아니다): §6 은 **골드·상한이 횟수를 정한다**(3회분 골드 → 정확히 3회 · cap−2 → 100 에서 정지)
— 시간이 아니라 자원이 상한이라 접촉이 밀려도 값이 안 변한다. §9(`> 1`)·§8 회복 카드(`≥ 5`)는 부등호라 밀림이 도움만 된다.
§4 는 처음부터 타임스탬프로 재고 있었다(132 가 같은 이유로 고쳐 둔 자리 — 이번 처방의 원본이다).

## 5. 교훈 (LESSONS 355)

1. **`waitForTimeout(n)` 은 «n ms 눌렀다» 가 아니다.** 한가한 컨테이너에서도 +11~40ms, 부하에서 +142ms 밀렸다.
   임계를 재는 단언이 그 위에 서면 «여유 10ms 짜리 동전 던지기» 가 된다.
2. **간헐 FAIL 을 «임계를 넉넉히» 로 풀지 마라.** 요청값을 300 → 200 으로 낮춰도 부하 밀림(+142ms)이
   여유를 다시 먹는다. 고칠 것은 값이 아니라 **무엇을 재는가** 다 — 벽시계 대신 페이지가 찍은 실측 구간.
3. **«제품이 규약대로 동작한 실행이 빨간가» 를 먼저 물어라.** 355 는 Δ2 인 실행이 전부 접촉 > 임계였고,
   그 사실 하나로 제품 수리 후보가 통째로 지워졌다(제품 0줄). 338 의 «등재문 가설을 재현으로 검사» 의 반대 결과판 —
   여기서는 가설이 **맞았다**.
4. **자를 고쳤으면 되돌림 시험으로 못 박아라.** «밀린 접촉에서 초록» 은 무르게 푼 것과 겉모습이 같다.
   임계를 100ms 로 낮춘 제품을 주입해 빨개지는 것을 보여야 «헛초록» 이 아님이 증명된다.
