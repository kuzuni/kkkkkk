## 2. 원인 — 입장 연출 도중에 쟀다. ÷s 는 «크기» 만 되살리고 «절대 x» 는 못 되살린다

`tools/repro221.js`(임시 계측기, 원인 확정 후 삭제)로 대기 시간을 120~800ms 로 흔들며 32회 재현:
**8/32 재현**. 스냅샷 순간에 바의 **조상**에서 돌고 있던 애니메이션은 하나뿐이었다 —

```
jzPgIn @ DIV.on jz-o jz-pg   (up: true = 바의 조상)
```

index.html 의 60·122 쥬시 입장 연출이다:

```css
.jz-o.jz-pg{animation:jzPgIn .12s ease-out both}
@keyframes jzPgIn{0%{opacity:0;scale:.985}35%{opacity:1}100%{opacity:1;scale:1}}
```

**호스트(#dunw·#shopw)를 통째로 scale .985 → 1 로** 띄운다. 게이트의 `SNAP` 은 이 축소를
`s = bar.rect.width / bar.offsetWidth` 로 구해 모든 값을 `÷s` 하는데 —

* **크기**(w·h)는 `÷s` 로 정확히 되살아난다 → 그래서 `Δw` 는 늘 0.0 이었다.
* **`rect.x` 는 «화면 절대 좌표»** 라 축소 중심(프레임 중앙 **540**)이 같이 들어가 있고, `÷s` 로도 안 지워진다:

```
x' = 540 + (x − 540)·s
x'/s − x = 540·(1/s − 1)          ← x 와 무관한 상수!
s = .985  →  540·(1/.985 − 1) = 8.22px
```

**어긋남이 x 에 무관**하므로 두 바·모든 칸이 **똑같이 8.2** 밀렸던 것이다.
계측기 32행 전부에서 «옛 판정 worst» 가 이 닫힌 식과 **소수 둘째 자리까지 일치**했다:

| 대기 | s | 옛 판정 worst | 540·(1/s−1) | 새 판정 worst |
|---|---|---|---|---|
| 120ms (dun) | .985 | **8.22** | **8.22** | 0.00 |
| 120ms (shop) | .985 | **8.22** | **8.22** | 0.00 |
| 200ms (dun) | .9913 | 4.78 | 4.78 | 0.00 |
| 200ms (shop) | .9961 | 2.10 | 2.10 | 0.00 |
| 280ms (shop) | .9993 | 0.36 | 0.36 | 0.00 |
| 360~800ms | 1 | 0.00 | 0.00 | 0.00 |

**간헐인 이유**: 대기 650ms 는 연출 120ms 를 충분히 넘기지만, 그건 «연출이 제때 시작됐을 때» 다.
클라우드 러너가 붐비면 `open` 이 실제 렌더로 넘어가는 시점이 밀려 650ms 안에 연출이 끼어든다.
한 회차에 03 만 걸리기도 하고 03+10 이 같이 걸리기도 하는 것(124/125 로 갈림)이 그 증거다.

> 파일 머리말이 «03·10 은 전체화면 페이지가 `transform:scale()` 로 앉는다(바 h 99 → 실측 97.5)» 라고
> 적어 둔 것도 **오독**이었다. 1080x2280 뷰포트에서 `#app` 스케일은 정확히 1 이고,
> 97.5 = 99 × .985 는 **입장 연출의 첫 프레임**이다. 주석을 사실로 고쳐 적었다.
