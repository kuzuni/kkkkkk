# 163 — 첫 접속 로딩 화면 «플레이어 등장» 연출

> 주인 지시(2026-08-27): «처음 접속할 때 스프라이트 로딩 화면에 애니메이션이 좀 있으면 좋겠음 —
> 플레이어 나오는 애니메이션 느낌으로». T2 기능(연출).
> **레퍼런스 이미지 없음**(신설 화면) → 지시서 [3]-(다) «연출 작업»: 연속 프레임 6~8장을
> 독립 비평가 2명에게 주고 ①타이밍 ②크기 비율 ③위치·경로 ④가독성·일관성 을 채점, 최저 8 통과.

- 구현 구간: `index.html` 맨 앞 **«163 로딩 화면» script**(`atlas-data.js` 뒤 · 본 스크립트 앞) · CSS `#loading`·`#ldStage`·`#ldGr`·`#ldSh`·`#ldHero`·`#ldTx`·`#ldBar`·`#ldNum` · 본 스크립트의 `loadAtlases`(→ `ldReady`)·부팅 콜백(→ `ldFinish`)
- 하네스: `tools/cap163.js`(연속 프레임) · `tools/probe163.js`(시간축 실측) · `tools/scan163.py`(잉크 bbox)
- 게이트: `node tools/verify163.js`

## 연출 (무엇을 만들었나)

1. 페이지가 뜨자마자 — 제목 «스프라이트 불러오는 중...» 이 1.4s 주기로 숨 쉬고, 진행바에
   1.15s 주기 하이라이트가 훑고 지나간다(아직 그릴 스프라이트가 없는 구간).
2. `knight` 아틀라스(25KB, 제일 작아 먼저 온다)가 도착하면 — **캐릭터가 왼쪽 프레임 밖에서
   달려 들어온다.** 420ms · easeOutCubic · 이동 450px · 달리기 8프레임 × 52ms(스트라이드 1회 완결) ·
   달리는 동안 상하 아치 26px · 그림자는 공중에서 작고 옅어진다.
3. 도착 — 착지 스쿼시(몸통 ±6% · 그림자 ±30%, 160ms) 후 `idle` 8fps(전투와 같은 속도)로 대기.
   그동안 진행바가 «n/8» 로 찬다.
4. 아틀라스가 전부 오면 — 게임이 부팅되고 오버레이는 110ms 페이드로 빠진다.

## 설계에서 «시간» 이 제약이 된 이유 (이 작업의 본체)

이 화면은 «오래 보여 줄수록 좋은» 연출이 아니다. 두 개의 벽 사이에 있다.

| 벽 | 값 | 근거 |
|---|---|---|
| 캐릭터를 그릴 수 있게 되는 시각 | **≈380~450ms** | 본 인라인 스크립트가 **672KB** 라 파싱에만 ~350ms. 그동안 메인 스레드가 막혀 이미지 `onload` 도 못 돈다 |
| 오버레이가 **안 보여야** 하는 시각 | **≈850ms** | load 이벤트 **550ms**(아틀라스까지 다 받은 시점) + 저장소 게이트의 최단 대기 **300ms** |

1회차에는 연출 모듈이 본 스크립트 **안에** 있어서 캐릭터가 400ms 에야 나타났고, 아틀라스가 다 오는
450ms 까지 **50ms** 밖에 못 썼다 — 비평가 A·B 가 독립적으로 «보이는 달리기가 38px / 145ms»,
«인지 가능한 창이 155ms» 로 같은 자리를 짚었다.

**2회차에 모듈을 `atlas-data.js` 바로 뒤로 옮겼다.** 아틀라스 로딩도 거기서 시작하고(본 스크립트는
`ldReady()` 로 결과만 넘겨받는다), 부팅 시각은 그대로다. 그래도 파싱 벽 때문에 **캐릭터 등장 시작은
여전히 ~400ms** 다 — 자바스크립트는 파싱 중에 못 돈다. 그래서 남은 것은 «퇴장을 언제 하느냐» 뿐이다.

→ `LD_HARD = 620ms`: **«이 시각을 넘겨서까지 등장을 기다리지는 않는다»**.
- **전부 캐시된 재방문**(로컬 file:// 포함): 부팅이 ~420ms 라 등장이 ~200ms 지점에서 잘린다.
  그때 캐릭터는 이미 이동의 **94%** 를 지나 사실상 서 있다(easeOutCubic 이라 뒤가 평평하다).
- **주인 지시가 가리키는 첫 접속**(1.8MB 를 네트워크로 받는 경우): 부팅이 훨씬 늦으므로
  등장 420ms + 착지 + 대기 idle 이 **통째로** 보인다. 비평 표본(`cap163.js`)이 이 경우를 찍는다.

게임 부팅 시각은 **1회차·2회차 모두 옛날 그대로**다. 오버레이는 부팅 순간 `.thru`
(pointer-events:none)가 되어 남은 체류 동안에도 아래 UI 로 탭이 통과한다.

## 게이트 `tools/verify163.js` — 무엇을 지키나

| 절 | 지키는 것 |
|---|---|
| §1 | `#loading` 구조 9종 · 캔버스 720×512 · `image-rendering:pixelated` · 문구 유지 |
| §2 | 상수 정합 — **JS `LD_FADE` = CSS `transition-duration`**(두 곳에 적힌 값) · `LD_HARD + LD_FADE < 850` · **스트라이드(아틀라스에서 프레임 수를 다시 세서) ≈ 등장 길이** · 배율이 정수이고 ≥7 · 모듈이 본 스크립트보다 앞에 있다 |
| §3 | ★ **850ms 전에 «안 보이게» 된다** — 이 저장소 게이트 40여 개의 캡처를 지킨다 |
| §4 | 궤적 — `LD.at(t)` 가 easeOutCubic 과 ±1px · 단조 감속 · 등속이 아님 · **t=0 에 잉크가 완전히 프레임 밖**(아틀라스에서 재계산) · DOM transform 이 그 함수를 따라간다 |
| §5 | 부팅 뒤 오버레이가 탭을 안 막는다(`.thru` = pointer-events:none, elementFromPoint 로 확인) |
| §6 | 진행 표기 «n/총계» 의 총계가 **ATLAS 에서 파생**(마크업 하드코딩 금지) |
| §7 | **무한 로딩 방지** — knight 가 깨져도 로딩이 끝난다(«등장이 끝나야 나간다» 로 되돌리면 빨개진다) |
| §8 | 부팅 분리 — 오버레이가 떠 있어도 게임은 이미 돌고 있다 · 본 스크립트가 아틀라스를 **다시 안 받는다** |
| §10 | ★ **앵커 산식이 게임과 같다** — 로딩의 `ldDraw` 와 79/80 의 `drawHeroTo` 를 같은 프레임·배율로 돌려 **drawImage 인자와 변환행렬**을 대조(file:// 는 캔버스가 tainted 라 픽셀 비교 불가) |

### 계측이 대상을 흔든 사고 (게이트를 두 번 다시 만든 이유)

1. 1차 게이트는 «전이 시각 관찰 + rAF 궤적 추적» 을 **한 페이지에서** 했다. 그 rAF 루프가 이미
   포화된 메인 스레드를 더 밀어 `hero 413→645ms · gone 758→1204ms` 로 **계측 없는 실제보다
   450ms 늦게** 나왔고, 그대로 «800ms 초과» FAIL 을 냈다. → 시간축은 MutationObserver 만,
   궤적은 별도 페이지.
2. 그 다음엔 «표본으로 이징을 재려» 했는데, 로딩 구간에서는 rAF 콜백이 프레임 시각보다
   최대 **140ms** 늦게 실행돼 찍은 x 가 «언제의 값인지» 를 표본 쪽에서 못 정한다(오차 **322px**).
   → 이징을 **순수 함수 `LD.at(t)`** 로 빼서 곡선은 직접 재고, 배선은 한 번만 확인.
3. `display:none` 시각을 기준선으로 삼은 것도 틀렸다. 캡처를 오염시키는 건 «언제 안 보이나» 이고
   불투명도 전이는 **컴포지터**가 돌린다. `display:none` 을 붙이는 타이머는 부팅 직후 메인 스레드에
   밀려 100~350ms씩 늦어 **실행마다 뜨고 지는 FAIL** 이 된다. → 기준은 «페이드 시작 + LD_FADE».
