# 65 — 룰렛 회전 중 팝업 흔들림 제거

- 세션 `sess-0143-14999` (워커 C) · 2026-08-25
- 지시서 [3]-**(가) 기계적 작업** — 레퍼런스 대조가 필요 없는 «움직임 제거» 라 **비평가를 띄우지 않았다.**
  검증은 전부 수치다: `node tools/verify65.js` (신설) + `node tools/smoke.js`.
- 편집 구간: `.rlt` CSS 블록 끝(`#modal.rou-spin` 규칙 3줄) · `roulSpinTo`/`roulFinish`/`openRoulette`.
  60(쥬시)·58(fx) 모듈 코드는 **한 줄도 건드리지 않았다** — 그 구간은 다른 워커가 선점 중이다.

## 1. 무엇이 실제로 흔들리고 있었나 (수정 전 실측)

`#modal` 안 **모든 요소**를 rAF 단위(186프레임/4.6초)로 훑어 회전 중 움직이는 것을 전수 조사했다.

| 요소 | 회전 중 변화 | 원인 |
|---|---|---|
| `.mbox` (모달 박스) | **Δ0** | — (박스 자체엔 원래 흔들림이 없었다) |
| `#modal` 딤 | **Δ0** | — |
| `.rlt` (원판 자리) | **Δ0** | — |
| `#app` (배경 프레임) | **Δ0** | — |
| **`#rouBtn` (돌리기 버튼)** | **bbox Δ24.6px(위치)·Δ49.2px(크기)**, `scale` .94 → 1.049 | 60 쥬시 `jz-dn`(.94) + `jz-up` 스프링(1.04 오버슈트)이 **회전 첫 290ms** 를 먹는다 |
| **`#rouBtn`·`#rouClose` (재터치 시)** | `jz-sh` = **좌우 6px 흔들림 3회 + brightness(.82)** | 회전 중 두 버튼은 `disabled` 인데, 60 은 «비활성을 누르면 흔들림» 을 전역으로 건다 |

즉 «팝업이 흔들린다» 의 정체는 박스가 아니라 **버튼**이었다. 특히 두 번째 항목 —
돌아가는 동안 조바심에 버튼을 다시 누르면 **누를 때마다 흔들린다.**

> 주의 — `document.getElementById('rouBtn').click()` 로는 **재현되지 않는다.** `click()` 은 pointerdown 을
> 발생시키지 않아 60 의 누름 위임이 걸리지 않는다. 이 조사는 **진짜 포인터 이벤트**로 해야 한다
> (`page.click()` 또는 `PointerEvent` 디스패치). 처음 `.click()` 으로 훑었을 때 «움직이는 요소 0개» 가 나왔다.

## 2. 수정

### (가) 회전 중 정지 표식 — `#modal.rou-spin`

`roulSpinTo` 시작에서 `#modal` 에 `rou-spin` 을 붙이고, `roulFinish`·원판 소실·`openRoulette` 재렌더에서 뗀다
(붙이고 떼는 지점은 `roulSpinMark()` 한 함수뿐이다). CSS 는 3줄:

```css
#modal.rou-spin,#modal.rou-spin .mbox,#modal.rou-spin .mbox *{
  animation-name:none;scale:none;translate:none;rotate:none}
#modal.rou-spin .jz-sh,#modal.rou-spin .jz-bad{filter:none}
```

**이게 원판을 안 멈추는 이유**: 60 은 설계상 `transform` 을 절대 안 쓰고 **독립 변형 속성(scale/translate/rotate)과
animation** 만 쓴다. 반대로 원판·세그먼트는 `transform:rotate` 다. 그래서 위 네 속성만 끄면
**쥬시 애니메이션은 전부 죽고 원판 회전은 그대로 산다.** 두 모듈이 서로 다른 속성을 쓰는 덕에
60 쪽 코드를 건드리지 않고 룰렛에서만 끌 수 있었다.

`!important` 는 쓰지 않았다. id 1개가 있어 `.jz-o.jz-dlg>.jz-bad`(0-3-0)를 특이도(1-2-0)로 이긴다 —
LESSONS 60 의 «`!important` 로 누르면 반대쪽 애니가 죽는» 사고를 피하기 위해서다.

### (나) 오버슈트는 원판에만 — 2단 이징

지시의 «원판 감속 시 오버슈트(살짝 되감기)도 원판 자체에만» 을 그대로 구현했다.

1. **1단** `ROUL_MS`(3.6s) easeOutQuart 로 `target + ROUL_OVER` 까지 — 즉 목표를 **6° 지나쳐** 감속
2. **2단** `ROUL_BACK_MS`(260ms) easeOutCubic 으로 `target` 까지 **되감기**

6° 는 반칸(22.5°)의 1/4 이라 되감는 동안에도 **포인터가 당첨 칸 밖으로 나가지 않는다.**
되감기 260ms 동안도 `rouSpinning` 은 `true` 이므로 정지 표식·버튼 잠금이 유지된다.

## 5. 교훈 (다른 화면에도 그대로 재발한다)

1. **«전역 부착» 모듈은 특정 상황에서 반드시 «꺼야 할» 순간이 생긴다.** 60 은 화면별 워커가 각자
   만들지 않게 하려고 전역 위임으로 만든 건데, 그 대가로 **회전·진행 중인 화면에서도 자동 편입**된다.
   끄는 방법은 모듈을 고치는 게 아니라 **상태 클래스 한 개 + 특이도로 이기는 CSS 3줄**이다
   (28 교훈의 «기본 상태를 안 건드리려면 상태 클래스로만 덮는다» 의 입력 판).
2. **`el.click()` 로는 포인터 기반 연출이 재현되지 않는다.** 60·58 같은 pointerdown 위임 모듈이 붙은 뒤로는
   자체 검증 스크립트도 **진짜 포인터 이벤트**를 써야 한다. 안 그러면 «움직이는 요소 0개» 라는
   거짓 통과가 나온다(이번에 실제로 한 번 났다).
3. **29 교훈 2가 그대로 재발했다** — 오버슈트 폭을 재는데 마지막 프레임의 `rouRot` 이 `mod 360` 으로
   정규화되며 2368→202.5 로 점프해 «되감기 2166°» 라는 오판이 나왔다. **회전 중 프레임만으로 재야 한다.**
4. 자체 검증 프로브가 읽는 세이브 필드명을 틀리면(`S.rel` ↔ 실제 `S.relic`) `NaN` 이 합계를 오염시켜
   **«보상 지급 안 됨» 이라는 가짜 버그**가 나온다. 수치가 이상하면 게임을 의심하기 전에 **프로브부터 검산**할 것.
