## §2 원인 — 제품이 멈춘 게 아니라 **게이트가 시간을 재고 있었다**

계측판(고정 대기 900ms 를 100ms×9 폴링으로 바꾼 사본)을 같은 순서로 돌리자 **85/85 PASS** 였고,
클래스가 갈리는 순간이 그대로 찍혔다:

```
live  snaps: rich@100  rich@201  lack@301  lack@401 …        ← 301ms 에 전환
live2 snaps: lack@103  lack@203  rich@303  rich@414 …        ← 303ms 에 전환
saverOn=false · document.hidden=false · rafAlive=3 · shopwOn=true · cost30=3000 · dia=99999
```

즉 **제품은 정상**이고(같은 프레임에서 `syncShopSumBtns()` 를 손으로 불러도 결과가 같다), 갈리는 것은
**그 틱이 900ms 창 안에 들어오느냐**뿐이다. 사슬은 셋:

1. `syncShopSumBtns()` 는 `renderUI()` 안에서만 돈다 — `index.html` **34907**
   `if($('shopw').classList.contains('on')) syncShopSumBtns();`
2. `renderUI()` 는 `loop()` 의 `uiT += dt; if(uiT > 0.35){ uiT = 0; renderUI(); }` — `index.html` **38594**
3. `loop()` 는 rAF 에 실려 있다 ⇒ **크로미움이 여럿 붙어 렌더러가 굶으면 벽시계 900ms 에 그 틱이 0회**일 수 있다.

⚑ **가장 짧은 증거는 같은 파일 안에 있다.** ①(12 팝업)·②(10 상점) 절은 **136** 이 이미
고정 대기를 `settle()` 폴링으로 갈아 놓았고 이 절들은 부하에서도 **한 번도 안 흔들렸다**.
남은 고정 대기가 정확히 ③ 절 둘(`await new Promise(r => setTimeout(r, 900))` ×2)이었고,
빨간 항도 정확히 그 둘이 지키던 자리다.

## §3 처방 — 136 이 ①② 에 쓴 길을 ③ 에도

기다리는 대상을 «시간» 에서 **«틱»** 으로 바꿨다. `settle()`(기하 정지 폴링) 옆에 `__live` 를 두고
`live`·`live2` 의 고정 대기를 그것으로 바꿨다(`LIVE_CAP = 5000`).

```js
const LIVE_WAIT = cap => { window.__live = async test => { … rAF 폴링 … }; };
```

- ⚠ **상수를 키우는 처방은 쓰지 않았다.** 이 파일 38~55행의 136 주석이 같은 이유로 이미 금지해 뒀다 —
  「어떤 상수를 골라도 언젠가 다시 깨진다」. 실측이 그 말을 그대로 확인했다(아래 §4 의 **1,323ms**).
- ⚠ **폴링은 읽기만 한다.** `syncShopSumBtns()` 를 폴링 안에서 부르면 «제품이 안 돌아도 초록» 인
  자가 된다. 제품이 정말 멈추면 상한까지 안 바뀌고 `ok:false` 로 **빨개져야** 한다.
- 걸린 시간은 항 이름에 찍는다(`…(폴링 466ms)`) — `settle()` 이 `ms` 를 찍는 것과 같은 규약이라,
  앞으로 이 창이 늘어나면 **점수가 아니라 숫자로** 먼저 보인다.

## §4 무르게 풀지 않았다 — §R 되돌림 시험 7항 신설

「대기를 늘린 것과 무엇이 다른가」 에 답하는 절이다. 갱신 주체만 무력화(`syncShopSumBtns = () => {}`)하고

|---|---|
| §R 무력화 · 상한까지 안 바뀐다 | `ok = false` (want false) |
| §R 무력화 · 클래스 그대로 rich | `cbtn b3 rich` |

⇒ 제품이 갱신을 멈추면 이 자는 **빨개진다.** 허용 오차는 한 칸도 안 넓혔다(클래스 단언은 그대로 등호다).
