# 326 — 23 훈련 단계 요구치를 «증가식» 으로 (300 → 600 → 900 …)

> **T2 주인 지시 · 1회차 · 2026-08-28 · sess-1400-17098 (루틴 워커 D)**
> 검증은 지시서 [3]-(가) **기계·기능 검증**(비평가 없음) — 레퍼런스 대조가 아니라 «식이 맞는가 · 실제로 눌러서 되는가» 다.

## 0. 주인 원문

> «훈련단계 계속 300 채워지면 올라가게 되있는데 600, 900 이런식으로 점점 늘어나는식으로.
>  각각의 스탯들 업글을 200 300 이런식으로 업글해야 훈련단계 업글되는 그런식»

## 1. 계약 한 줄

**단계 n 을 돌파하는 «그 단계 몫» = 스탯당 `100×n`** (3종 합 `300×n`).
따라서 상한은 그 몫의 **누적합**이다.

```
trainCapAt(n) = 100 · n(n+1)/2          ← 스탯당 절대 상한(저장값과 같은 축)
trainCapAt(n) − trainCapAt(n−1) = 100n  ← 항등식. «이번 단계 몫» 은 언제나 100n
trainMax()    = 300 × n                 ← 진행도 분모(3종 합)
```

| 단계 n | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 이번 단계 몫(스탯당) | 100 | **200** | **300** | 400 | 500 | 600 |
| 진행도 표기 | 0/**300** | 0/**600** | 0/**900** | 0/1200 | 0/1500 | 0/1800 |
| 누적 상한(스탯당) | 100 | 300 | 600 | 1000 | 1500 | 2100 |

주인이 말한 «200 300 이런식» 이 **몫** 열이고, «600, 900 이런식» 이 **표기** 열이다. 두 문장이 같은 곡선의
두 얼굴이라 하나로 푼다 — 1단계 300 은 그대로 두고 그 위로만 늘어난다.

## 2. 바꾼 것 (index.html — 4줄)

```js
const trainCapAt = n => TRAIN_CAP_STEP * n * (n + 1) / 2;      /* 신설 — 누적합 */
const trainCap   = () => trainCapAt(trainStage());             /* 구: trainStage() * TRAIN_CAP_STEP */
const trainBase  = () => trainCapAt(trainStage() - 1);         /* 구: (trainStage()-1) * TRAIN_CAP_STEP */
const trainMax   = () => TRAIN_STATS.length * TRAIN_CAP_STEP * trainStage();   /* 구: 300 고정 */
```

`TRAIN_CAP_STEP` 은 **이름의 뜻만 바뀌었다** — «단계당 상한 증가폭(고정)» → «단계 n 몫의 계수(100×n)».
값 100 은 그대로다(게이트 [G] 가 지킨다).

**안 건드린 것**: `trainStage()` · `trainLv` · `trainLvRel` · `trainProg` · `trainReady` · `trainBuyInfo` ·
`trainBuy` · `trainUp` · `autoBuyTick` · `TRAIN_BONUS` · 단계 보너스 적용식(`1 + 0.10×(단계−1)`) ·
비용 곡선(`trainCost`/`TRAIN_KNEE`/`TRAIN_COST_R`) · 적 곡선(`eHp`/`eDmg`/`eScale`) · 세이브 KEY.
**밸런스 계수는 한 줄도 안 건드렸다** — 지시서 ① 대로 재실측만 하고 수치 확정은 199 로 넘긴다(§4).

### 183 규약은 한 글자도 안 바뀌었다

183 이 못 박은 것은 «단계 업 직후 정확히 **0** 에서 시작하고 꽉 차면 돌파» 다. 그 규약은
`trainCapAt(n) − trainCapAt(n−1) = 100n` 항등식 위에서 그대로 성립한다 — **눈금의 길이만 단계마다 길어진다.**
183 게이트의 «0/300» 을 전부 «0/분모(단계)» 로 일반화했고(`verify183` 27/27), 고정 300 을 다시 박지 말라고
파일 서두에 적어 뒀다.

## 3. 세이브 이관 — «없음» 이 정답이다

n≥1 에서 **구 상한 `100n` ≤ 신 상한 `100·n(n+1)/2`** 이므로(등호는 n=1 에서만) 기존 `S.lv.*` 절대값이
새 상한을 넘는 경우가 **구조적으로** 없다. 단계는 유지되고 진행도만 «이번 단계 몫이 커진» 쪽으로 재해석된다.
레벨 손실·강제 강등이 0 이라 **KEY 를 올리지 않았다.**

`verify326` [F] 가 단계 2·4·8 에서 «구 상한까지 채운 구 세이브» 를 직접 심어 레벨·단계·localStorage·
진행도 상한 넘침을 전수 확인한다. (단계 4·8 처럼 구 상한이 `trainBase()` 보다 낮은 자리는 진행도가
`0/분모` 로 읽힌다 — `trainLvRel` 의 `Math.max(0, …)` 가 음수를 막는다. 확인함.)

## 4. ⚑ 밸런스 재실측 — **수치 확정은 199 몫** (계수 0줄 변경)

### 4-2. ⏸ 199 가 정해야 할 4칸 (여기서 고치지 마라)

적 곡선(112/177/249 계수)은 «훈련만 축 ×1.30» 위에서 역산된 값이다. 그 배수가 ×1.20 이 되자 네 칸이

`ck199` 를 신설해 **실패로 세지 않되 값과 초과분은 크게 찍는** «⏸199» 상태로 두었다.

### 4-3. ★ 199 가 **반드시** 볼 것 — 단계 축이 사실상 3에서 멈춘다

비용 곡선이 레벨당 ×1.05(무릎 위) 지수라, 상한이 «누적합» 이 되면 **단계당 비용이 곱셈으로 폭발**한다.
새 단계 n 은 레벨로는 옛 단계 `n(n+1)/2` 와 같은 자리다(새 4단계 ≡ 옛 10단계).

4단계에 필요한 Lv 1000 은 2.5e25 골드 — **그 지평 안에서는 사실상 도달하지 않는다.**
즉 **«단계당 전 스탯 +10%» 축이 s80 부근에서 +20% 로 굳는다.** 주인 지시(«점점 늘어나는식»)를
