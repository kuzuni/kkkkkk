## 4. 연출 — [3]-(다) 비평 루프

### 4-1. 캡처 하네스 (1회차에서 얻은 교훈 — **다른 화면에도 그대로 적용된다**)

1회차 캡처는 지시서 [3]-(다) 문구대로 «80~100ms 간격 연속 프레임» 을 `waitForTimeout` + `screenshot`
으로 찍었다. **그렇게 하면 짧은 연출은 절대 못 찍는다** — `page.screenshot()` 한 장이 100~200ms 걸려서
«+35ms 프레임» 이 실제로는 +300ms 에 찍힌다. 결과는 아래와 같았다:

- 비평가 A: «260ms 짜리인데 관측 지속시간 ≤70ms — 73% 짧게 끝난다», «m5 가 한 프레임에 331px 순간이동»
- 비평가 B: «260ms 예산 중 210ms(81%)가 아무 변화도 렌더하지 않는다»

**둘 다 캡처 아티팩트다.** 실제 타임라인을 RAF 프로브로 재 보니 애니메이션은 정확히 260ms 동안
147 → 136 → 70 → 9 → 0 으로 접히고 있었다. 비평가 2명이 **독립적으로 같은 오독**을 했다는 것이
이 함정의 위험도를 말해 준다.

→ 하네스를 **Web Animations API 정지·탐색** 방식으로 바꿨다(`tools/cap92fx.js`):
1. 클릭 → **레이아웃을 강제로 플러시한 뒤**(`void document.body.offsetHeight` — 이게 없으면
   `getAnimations()` 가 새 애니메이션을 아직 몰라서 **0개**가 나온다) 해당 애니메이션을 골라 `pause()`.
   상자(`mlOut`)와 내용(`mlOutIn`)을 **같이** 잡아야 알파가 프레임과 어긋나지 않는다
2. `currentTime` 을 0·75·150·…·540ms 로 **정확히** 옮겨 가며 1장씩 찍는다
3. 연출 뒤 재렌더 `setTimeout` 은 가로채 붙잡아 뒀다가 마지막에 손으로 실행(착지 프레임)

이제 파일 이름의 ms 가 실제 진행 시각과 일치하고, 프레임마다 `h`(높이)·`x`(translateX)·`a`(opacity)
실측값을 같이 찍어 비평가에게 **근거 수치**로 준다.

| ⓓ | 210→320ms(34%)가 «보이는 잉크» 1.51%→0 만 처리 | 210~320ms 는 판독 불가 얼룩 | ❌ **반영 안 함**(아래) |

### ★ 이 회차의 교훈 — **변환은 자기 위에 얹힌 값을 «먹는다»**

6·9·11회차가 **세 번에 걸쳐** 이 림 플래시의 진폭과 창을 튜닝했다(16px → 8px → 12px, 32ms → 60ms → 36ms).
그런데 12회차부터 카드 전체가 `scale()` 되기 시작했고, **선언한 링 두께는 그 scale 에 곱해져서 화면에 나간다.**
즉 «12% 에서 링을 11px 로 키운다» 는 선언은 화면에서 11×0.847 = **9.3px** 이 되고, 같은 프레임에
면적이 줄어드니 **강조가 아니라 축소로 읽힌다.** X·Y 가 서로 다른 방식으로(X 는 시계열 실측, Y 는 겉실루엣 계산)
같은 결론에 도달했다.

> **`transform` 아래에서 px 를 선언하면 그 px 는 «화면 px» 이 아니다.**
> 두께·반경·그림자처럼 «보이는 크기» 가 의미인 값은 **scale 로 나눠 선언**해야 의도한 화면값이 나온다.
> 실측 결과: 6.00 → **11.01(+83%, t=36ms)** → 7.75 → 5.98 → 6.00 → 6.00 (이웃 3행과 두께 일치)

### 반영하지 않은 것 ⓓ 와 그 이유 (다음 세션에 넘긴다)

X 는 «상자 α·scale 을 h 곡선에서 **떼어** 220ms 에 끝내고 h 만 320ms 유지» 를 처방했다.
그렇게 하면 **카드가 자기 슬롯보다 작아진다** — 50% 시점에 슬롯은 784×60 인데 카드는 170×32 라
카드와 다음 행 사이에 ~28px 의 빈 틈이 생긴다. 12회차에 «카드 = 슬롯» 을 맞춰서 없앤 것이 그 틈이다.
Y 의 대안(스태거 복원)은 **합산 상승 단차**를 0.34 → 0.85 로 되돌린다(11회차에 측정해 둔 값).
**둘 다 이미 0 으로 만든 지표를 깎는 교환**이라 이 세션에서는 손대지 않았다 — §6-14 에 남은 문제로 적는다.

## 6-15. 14회차 — 높이 커브를 **지수 감속 → «등속 + 착지»** 로

13회차가 남긴 «남은 문제» 1·2·3 은 서로 **처방이 다른 지표를 깎는** 관계로 등재돼 있었고,
지시서대로 «세 축이 동시에 만족되는 값이 있는지부터 산수로» 확인한 결과 **있었다.**
셋을 따로 고치는 게 아니라 **커브 하나를 바꾸면 셋이 같이 풀린다.**

### 산수 — 왜 지수형이 세 축을 동시에 깎고 있었나

13회차 커브는 `h = 147(1−p)^1.6` 이다. 이 모양은 **시작 속도가 평균의 1.32배**이고 끝이 0 으로 잦아든다.

| 축 | 지수형이 만드는 결과 |
|---|---|
| 합산 상승 피크 | «시작 속도 × 겹침(스태거 0 이라 ×2)» 이므로 앞이 빠를수록 커진다 → **1.44** |
| 뒤쪽 110ms 가 «일을 안 한다» | 그 대가로 뒤가 느려져 **남는 행 3장이 마지막 110ms 동안 사실상 멈춘다** |
| 틴트 식별 창 | 첫 60ms 에 37px(25%)을 쏟아 카드가 곧바로 작아진다 |

**«보이는 잉크가 안 움직인다» 의 정체는 삭제 카드가 작아서가 아니다.** 잉크는 면적이라 `h²` 에
비례하고, 어떤 커브를 써도 꼬리에서는 작다 — 즉 그 지표는 커브로 못 고친다. 실제로 그 구간에
움직여야 할 잉크의 대부분은 **«남는 행 3장 × 전면 불투명»** 쪽이고, 그게 멈춘 이유가 **감속**이었다.

⇒ **앞을 늦추면 피크가 내려가고, 뒤를 살리면 죽은 꼬리가 없어진다. 같은 한 번의 수정이다.**

### 새 커브

`h = 147(1 − 1.0417u)` 를 `u ≤ 0.92` 까지 **등속**으로 깔고, 마지막 8%(6.1px)만 2차 감속으로 착지시킨다
(3회차 ⑨ «착지 감속» 요구는 유지). 피크/평균 **1.32 → 1.042**.
구간 속도 `0.510 ×9 → 0.383 → 0.128` **단조 하강** — 재가속 0 은 그대로다(11회차 V·W 가 세운 값).
알파는 중간 키프레임을 **아예 안 적어** CSS 선형 보간에 맡겼다 → 기울기가 **정확히** 균일하다.

### ★ 홀드는 시도했고 **실측으로 기각**했다

Y 의 «‹이 2통이 대상› 을 정지 상태로 읽을 시간이 25ms» 에 답하려고 0~30ms 를 h·scale 정지로 둬 봤다.

| 지표 | 홀드 없음 | **홀드 30ms** |
|---|---|---|
| 합산 상승 피크 | 1.141 | **1.266** (홀드만큼 나머지가 빨라진다) |
| 재가속 최대 | 0.003 | **+0.634** (정지→등속으로 올라서는 단차) |
| 정지 구간 | 40ms | **60ms** (8회차 P-① «정지 행» 재발) |
| 식별 창 | 25ms | 30ms (**1.4프레임**) |

셋을 깎고 얻는 게 1.4프레임이라 버렸다. 그리고 **애초에 홀드가 필요 없다** —
**식별 창을 늘리는 건 등속화 자체**다. «h>100 ∧ α>0.7» 인 «크고 진한» 구간이
**77ms → 92ms(+19%)** 로 늘어난다(h=100 도달 76.7 → 92.1ms · α=.7 도달 117 → 122ms).
정지가 아니라 «천천히 줄어드는» 형태로 읽을 시간을 준다.
림 플래시도 홀드가 필요 없다 — 13회차의 «scale 로 나눠 선언» 이 이미 화면 두께를 지킨다(피크 36 → **30ms**).

### ⚠ 같이 회수한 구조 결함 — 카드가 슬롯보다 **2.55px** 컸다

`mlOut` 은 **35%** 에 키프레임이 있는데 `mlOutIn` 은 **33%** 에 있었다. 둘은 `scale = height ÷ 147` 로
묶여 있는데 **퍼센트 목록이 어긋나** 그 사이 구간에서 두 커브가 갈라졌다 —
t≈100ms 에서 카드 렌더 높이가 자기 행보다 **+2.55px**, 하변 초과 **2.5px**.

13회차 기록의 «잘림 0 · 카드=슬롯» 은 **키프레임 «위» 에서만 잰 값**이었다(키프레임에서는 당연히 일치한다).

> **★ 교훈 — 두 커브를 «식» 으로 묶어 놨으면 «샘플링 지점» 도 같이 묶어야 한다.**

> 퍼센트 목록이 하나라도 다르면 그 구간이 통째로 어긋난다. 그리고 **키프레임 위에서 검증하면 영원히 안 보인다.**

하므로 순항 속도가 오른다. 예산을 맞춰 잡았다:

> 이즈인 50ms(변위 16.1px) + 순항 210ms + 착지 40ms(변위 12.9px) = **255·v = 164 → v = 0.6431px/ms**
> → 두 행이 겹칠 때 합산 피크 **1.286** (7·8·11·14회차가 지켜 온 «≤1.30» 안. 실측 1.288)

**커브는 pitch P(= height + margin)에 대해 설계하고 h 를 거기서 뽑았다.** h 에 직접 이징을 걸면
margin 이 17 로 고정된 구간에서 P 의 이징이 h 의 것과 달라져 **남는 행이 이징을 안 받는다** —
눈이 보는 것은 h 가 아니라 P 다. h = P − 17 (P ≥ 17), 그 아래는 80% 시점 비(8.75 : 17)로 함께 0 으로
(16회차의 self-collapsing margin 규칙 유지 — h 는 100% 전에 0 이 되지 않는다).

**뜻밖의 회수 — 스태거의 계단이 같이 사라졌다.** 18회차가 «대가» 로 적어 둔 재가속 **0.570 → 0.195**.
두 번째 행이 이즈인으로 «부드럽게 올라타므로» 합산 속도가 계단이 아니라 경사가 된다.
18회차 §7-8 이 «다음 회차가 되돌리려거든 이즈인을 먼저 보라» 고 적어 둔 바로 그 자리이고,
이번엔 **다른 이유로 넣은 수정이 그것을 공짜로 해결했다.**

### ② 바깥 링 고정 (ⓓ·ⓔ) — 그리고 ⓒ 처방을 **안 받은** 이유

18회차의 «h<48 부터 링을 h/48 배» 는 두 사람이 같은 픽셀 좌표로 잡은 결함 셋의 **단일 원인**이었다.
**대칭 링은 «두께만» 줄일 수 없다** — 바깥 경계가 곧 두께다(shadow y-오프셋으로 윗변을 고정하면
아랫변이 그만큼 안으로 들어와 결함이 아래로 옮겨 갈 뿐이다).

→ **바깥 링 6px 고정**(h<8 만 예외). 폭 796 · 상변 776 · 거터 5px 이 **보이는 전 구간 불변**이 된다.
덤으로 Χ ①-3 «끝나는 시각이 3개(도색 268 / 슬롯 290 / 알파 300)» 도 사라진다 — «도색 268» 은
링이 얇아져 사라진 시각이었다. 이제 셋 다 **300ms** 다.

**두 사람이 같이 낸 ⓒ 처방(임계를 48 → 108/120px 로 올려라)은 받지 않았다.** 그 처방과 ⓓ·ⓔ 가
**같은 원인을 공유**하기 때문이다 — 임계를 올리면 인셋이 더 일찍 시작돼 폭 위반·상변 역행·거터
출렁임이 **더 커진다.** 둘은 양자택일이고, 두 사람이 «픽셀에서 직접 본» 쪽은 결함 셋이고
«비중 46%» 는 산술로 유도한 값이다. 대신 인셋을 안 만드는 축으로만 줄였다 —
**안쪽 빛 테두리(5px)를 h<60 부터 5·h/60 로.** 이건 상자 «안» 이라 외곽 기하를 1px 도 안 건드린다.

> ★ 교훈 — **두 비평가가 «독립 일치» 로 낸 처방 두 개가 서로를 무효화할 수 있다.**
> 둘 다 반영하려다 보면 한쪽이 조용히 되살아난다. 처방끼리 **원인을 공유하는지** 먼저 보고,
> 공유하면 «둘 다» 가 아니라 «어느 쪽이 렌더된 픽셀에서 직접 관측됐는가» 로 고른다.

### ③ 소거 재타이밍 (ⓘ·ⓕ) · ④ 발자국 편입 (ⓖ) · ⑤ 틴트 스태거 (ⓗ)

새 클립선(h − 빛 − 플래시)과 이즈인으로 커진 h 로 다시 잡았다. 림 플래시도 피크 4→**3px** · 창 130→**120ms**
로 낮췄다 — «강조가 과해서» 가 아니라 **플래시가 클립선을 자기 두께만큼 끌어올리기** 때문이다.

## 7-11. ⓑ 빈 띠와 ⓕ 우측 조기 소거는 **구조적이다** — 산술을 남긴다

다음 회차가 이걸 «튜닝으로 없앨 수 있다» 고 착각하지 않게 계산을 적어 둔다.

**ⓑ 빈 띠** = «내용 소멸» 과 «상자 소멸» 사이. 내용의 마지막 생존자는 제목(로컬 하변 58)이고,
제목이 가려지는 시점은 h ≈ 58 + 빛 5 = **63px**. 거기서 h=0 까지는 순항 속도로 **63 / 0.6431 ≈ 98ms**,
착지를 더하면 **≈110ms**. 즉 **빈 띠 ≈ 110ms 는 «순항 속도» 하나로 결정된다.**
- 줄이려면 v 를 올려야 하고, v 를 올리면 합산 피크 2v 가 **1.30 상한**을 넘는다(v=1.0 이면 피크 2.0).
- 제목을 위로 올리면 되지만 그건 69 의 확정 레이아웃이다(우리 구간이 아니다).
- 제목을 축소·이동시키면 10~11회차가 폐기한 «찌그러짐 / 상변 이탈» 로 되돌아간다.
- 상자만 먼저 죽이면 17회차 Σ·Φ 가 «90ms 동안 빈 구멍이 저절로 닫힌다» 로 감점한 그 결함이다.
→ **v 상한(1.30/2)과 제목 하변(58)이 정해진 이상 빈 띠의 하한은 ≈110ms 다.** 19회차 실측도 그 값이다.

**ⓕ 우측 조기 소거** — 썸네일 하변 127.5 · 버튼 118 은 카드 높이 147 의 **87%·80%** 지점이다.
상변 앵커 세로 접힘에서 이들이 가려지는 시각은 h가 128·123 이 되는 때, 즉 **43ms·57ms(수명의 14%·19%)**.
어떤 알파 스케줄로도 이보다 늦출 수 없다 — 늦추면 «읽히는데 잘림»(ⓘ)이 된다. 둘은 **정확히 상충**한다.
→ 해소하려면 세로 접힘 자체를 버려야 하는데, 그건 일곱 명이 요구해서 18회차에 온 자리다.

**남은 진짜 선택지는 하나다: 총 길이를 줄여 v 를 올리고 «합산 피크 ≤1.30» 을 완화하는 것.**
그 상한은 7회차 비평가 M·N 이 세운 값이고, **그 뒤로 아무도 재검하지 않았다.** 20회차가 이 문제를
다시 잡는다면 «빈 띠를 줄이는 튜닝» 이 아니라 **«1.30 이 아직 유효한 상한인가» 를 비평가에게 직접 묻는 것**이
정확한 질문이다(예: 수명 300 → 230ms 는 v=0.84 · 피크 1.68).
