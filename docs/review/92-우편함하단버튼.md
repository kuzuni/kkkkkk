## 4. 연출 — [3]-(다) 비평 루프

### 4-1. 캡처 하네스 (1회차에서 얻은 교훈 — **다른 화면에도 그대로 적용된다**)

1회차 캡처는 지시서 [3]-(다) 문구대로 «80~100ms 간격 연속 프레임» 을 `waitForTimeout` + `screenshot`
으로 찍었다. **그렇게 하면 짧은 연출은 절대 못 찍는다** — `page.screenshot()` 한 장이 100~200ms 걸려서
«+35ms 프레임» 이 실제로는 +300ms 에 찍힌다. 결과는 아래와 같았다:

- 비평가 A: «260ms 짜리인데 관측 지속시간 ≤70ms — 73% 짧게 끝난다», «m5 가 한 프레임에 331px 순간이동»
- 비평가 B: «260ms 예산 중 210ms(81%)가 아무 변화도 렌더하지 않는다»

**둘 다 캡처 아티팩트다.** 실제 타임라인을 RAF 프로브로 재 보니 애니메이션은 정확히 260ms 동안
147 → 136 → 70 → 9 → 0 으로 접히고 있었다. 비평가 2명이 **독립적으로 같은 오독**을 했다는 것이
이 함정의 위험도를 말해 준다.

→ 하네스를 **Web Animations API 정지·탐색** 방식으로 바꿨다(`tools/cap92fx.js`):
1. 클릭 → `getAnimations()` 에서 해당 애니메이션을 골라 즉시 `pause()`
2. `currentTime` 을 0·70·140·…·500ms 로 **정확히** 옮겨 가며 1장씩 찍는다
3. 연출 뒤 재렌더 `setTimeout` 은 가로채 붙잡아 뒀다가 마지막에 손으로 실행(착지 프레임)

이제 파일 이름의 ms 가 실제 진행 시각과 일치하고, 프레임마다 `h`(높이)·`x`(translateX)·`a`(opacity)
실측값을 같이 찍어 비평가에게 **근거 수치**로 준다.

### 4-3. 2회차 — 고친 것

```
.ml-r.out{animation:mlOut .42s both;animation-delay:var(--mld,0ms)}   /* .26s → .42s */
@keyframes mlOut{
  0%  {h147 x0    a1.00  → cubic-bezier(.15,.8,.35,1)}   /* 톡 밀어내는 초동 */
  20% {h147 x38   a.95   → linear}                        /* 등속 이탈 */
  46% {h147 x112  a.62   → cubic-bezier(.4,.02,.4,1)}     /* 여기서부터 접힌다 */
  100%{h0   x168  a0  margin0}
}
.ml-r.flip{animation:mlFlip .26s cubic-bezier(.2,.8,.3,1) both}        /* 남는 행 FLIP */
```

1. **길이 .26s → .42s**(58 «0.3~0.8초» 규칙 안). 2행 스태거 90ms 포함 총 **510ms**.
2. **구간별 이징** — 단일 ease-in 을 버리고 초동/등속/수축 3구간에 각각 커브를 줬다.
3. **높이를 46% 지점까지 붙잡고** 남은 54%(227ms)에 걸쳐 접는다 → 수축이 4프레임에 걸쳐 표본된다.
4. **이탈 40px → 168px**(카드 폭 784 의 **21%**).
5. **행마다 90ms 스태거**(`--mld`) → «두 통이 차례로 치워진다» 는 순차감.
6. **남는 행 FLIP** — 재렌더는 DOM 을 새로 만들어 자리 이동이 0ms 점프가 된다. 클릭 시점의 행 top 을
   재 뒀다가 재렌더 직후 옛 자리로 되돌리고 `.26s` 로 보간한다.
7. **`fxCheck` 제거** — «보상 확인» 표식이라 삭제에 의미가 안 맞고, `.6s` 라 카드보다 오래 살아
   버튼 라벨을 덮었다. `fxPop`(눌림) 으로 교체.
8. **행별 미니 버스트** — 버튼 버스트를 8 → 6 으로 줄이고, **사라지는 행마다** `fxBurst(행, 5)` 를
   90ms 스태거로 붙여 시선을 «무엇이 사라지는지» 에 묶었다.
